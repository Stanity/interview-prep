# 2.3 多智能体动态检索（第三主讲项目｜唯一没有论文的项目）

> **定位**：这是你三个项目里**唯一没有论文**的（在研），也是和 Agent 岗**最直接对口**的一个。
> **风险提示**：没有论文 = 没有公开的实验细节可以背书。所以这篇的重点不是"讲得多漂亮"，而是**划清哪些能说、哪些不能说**，避免被追问到露馅。
> **用法**：§1 背 30 秒版 → §2 主线 → **§3 诚实边界先立规矩** → §4–§11 技术细节 → §12 追问预答 → §14 自测。

---

## 1. 30 秒口述版

:::card 30 秒版
「这是一个在研的工作，目标是**复杂事实声明的核查**。

难点在于：真实世界的声明往往需要跨多个证据源核查，而**单轮静态检索**覆盖不了 —— 证据可能分散、可能互相冲突、还需要多跳才能定位到关键事实。

我的做法是把一次性检索变成**由状态反馈驱动的多轮决策**：先把复杂声明拆成多个**可验证子目标**，用一个共享的**证据状态**记录每个子目标覆盖到什么程度、有没有冲突；然后由三类子智能体分工 —— **补全**找缺失证据、**反驳**主动找反证、**冲突消解**处理矛盾；再用一张**事实依赖图**决定检索顺序（哪些事实先查、哪些依赖前面的事实），并按当前状态动态选择检索策略。

在三类事实验证数据上，Macro-F1 比同期方法平均高 **3.7 个点**。这个工作的重点不是"多智能体"这个形式，而是**用证据状态决定什么时候继续检索、下一步该谁执行**。」
:::

**最后一句是灵魂**：把你的项目从"我搭了几个 Agent"提升到"**我用状态做调度**"。这也是我在 06-Agent工程 里反复强调的差异化。

## 2. 3 分钟版（按这个顺序讲）

1. **问题**（25s）：单轮静态检索的四种失败模式（见 §4）
2. **为什么是"多轮"**（20s）：证据覆盖是**逐步逼近**的，第一轮检索不可能知道还缺什么
3. **为什么是"多智能体"而不是"一个 Agent 多轮"**（30s）：不同证据需求的**目标函数不一样**（找缺失 vs 找反证 vs 消矛盾），混在一个角色里会互相干扰；而且**上下文可以隔离**
4. **架构五层**（30s）：拆解层 → 状态层 → 子 Agent 层 → 策略层 → 聚合层
5. **核心：证据状态**（40s）：字段 + 它如何驱动调度（这是你要重点讲的地方）
6. **实验**（25s）：三类数据、+3.7pp、消融、成本

## 3. ⚠️ 诚实边界（面试时必须守住的三条）

:::card 这个项目的三个"不能装"
**① 不能暗示有论文/投稿**
说：「这是**在研**的工作，还没有成稿。」——不要说"在投""准备投"，除非真的投了。面试官问"发哪了"时含糊，比直接说"在研"减分得多。

**② 不能说有跨会话长程能力**
你的循环是**单轮复杂任务内**的"规划—执行—评估"循环，**不涉及**跨会话的长期记忆累积和断点恢复。被问 long-horizon 时照实说，然后补一句：「这是我和生产级 harness 的差距。」

**③ 不能编实验细节**
- **能说**：三类事实验证数据、平均 +3.7pp、设计了消融（🟡按你实际做过的说）
- **不能说**：具体数据集名（除非你确知）、每个数据集的分数、消融的具体掉点、成本数字 —— **这些我不知道，别猜**
:::

:::card 一个可以主动说的"坦诚加分项"
面试官问"这个项目的局限" 时，主动说：
> 「它最大的局限是**工程化程度不够**：我有状态管理和循环控制，但没有生产级的 trace、没有沙箱、没有并发调度。所以它证明的是"这个思路有效"，不是"这个系统能上线"。」
**为什么加分**：说明你知道科研原型和生产系统的差距在哪，而不是以为加几个 Agent 就叫系统。
:::

## 4. 问题定义：单轮静态检索的四种失败模式

:::card 这四种是你要能举具体例子的（面试官很吃这个）
| 失败模式 | 表现 | 举一个声明例子（🟡换成你自己准备的真实例子） |
|---|---|---|
| **① 覆盖不全** | 一个声明含多个独立事实，一次检索只召回其中一部分 | "A 公司在 2020 年收购了 B 公司，并在 2022 年将其更名为 C" —— 三个事实点，一次 query 很难全召回 |
| **② 证据冲突** | 不同来源给出矛盾信息，模型随机选一个 | 两个来源对同一事件的日期/金额不一致 |
| **③ 需要多跳** | 关键事实不在声明里，要先查出中间实体才能继续 | "这位导演的上一部作品获得了 X 奖" —— 先要确定"这位导演"是谁 |
| **④ 查询与证据错配** | 声明的表述与证据的表述差异大（同义改写、术语差异），检索召不回 | 声明用"裁员"，证据用"人员优化" |

**一句话总结**：「这四种都不是"模型不够强"能解决的，而是**检索过程本身需要反馈控制**。」
:::

## 5. 架构五层（画在白板上最好）

```
① 拆解层   claim ──► 可验证子目标 {g1, g2, …, gn}
                     │
② 状态层   Evidence State（共享黑板）
             ├─ 子目标覆盖状态
             ├─ 证据池（含来源/策略/置信度）
             ├─ 冲突标记
             └─ 预算与边际收益
                     │
③ 子 Agent 层   补全 Agent ｜ 反驳 Agent ｜ 冲突消解 Agent
                     │
④ 策略层   直接检索 ｜ 查询改写 ｜ 对抗检索 ｜ 冲突消解检索
                     │
⑤ 聚合层   覆盖度 + 证据质量 + 冲突是否消解 → 最终标签
```

:::card 五层各自的一句话职责
1. **拆解层**：把复杂声明变成**可独立验证**的子目标（这是后面一切的粒度基准）
2. **状态层**：唯一可信的"当前知道什么"，**所有 Agent 都读写它**，而不是互相传上下文
3. **子 Agent 层**：各自有明确的目标函数（补全/反驳/消解），避免一个角色既要又要
4. **策略层**：把"要查什么"翻译成"用哪种检索方式"
5. **聚合层**：多份证据怎么合成最终判断（不是简单投票）
:::

## 6. 核心：证据状态（Evidence State）设计

:::card 这是全项目最关键的技术点，也是你回答"Memory/状态管理"类问题的接口
下面是我按你的描述重建的**合理字段结构**，你要按**实际代码**核对后再讲（🟡核对）：

| 字段 | 类型 | 作用 | 更新时机 |
|---|---|---|---|
| `subgoals[]` | 列表 | 子目标 + 每个的**验证状态**（未覆盖 / 部分 / 已覆盖） | 每轮证据入库后 |
| `evidence[]` | 列表 | 每条约证据：`doc_id`、来源、**由哪个策略检索到的**、**支撑哪个子目标**、置信度、片段 | 每次检索后 |
| `conflicts[]` | 列表 | 冲突对：哪两条证据在哪个子目标上矛盾、**消解状态** | 冲突检测触发时 |
| `coverage` | 标量 | 已覆盖子目标数 / 总数（**这是最关键的驱动量**） | 每轮重算 |
| `marginal_gain` | 标量 | 上一轮新增的有效证据数（**用于判断边际收益是否趋零**） | 每轮重算 |
| `budget` | 结构 | 已用检索次数、已用 token、剩余轮次 | 每次动作后 |
| `dep_graph` | 图 | 子目标之间的依赖关系（谁必须先查） | 拆解后构建，可动态调整 |
:::

:::card 为什么"状态"比"上下文"更重要（这段能讲出来会很加分）
- 如果把所有检索结果和历史都塞进 context：**几轮之后就爆炸**，而且模型会"忘掉"早期结论
- **状态是结构化的**：只保留"结论 + 指针"（哪条证据支撑哪个子目标），原始长文本按需回取
- **状态是可查询的**：调度逻辑可以问"覆盖率是多少""还有几个子目标没覆盖""有没有未消解的冲突" —— **这些都是 prompt 里读不出来的**
- 状态还让**多个 Agent 可以并行**：它们不需要共享上下文，只共享状态

**一句话**：「**上下文是给模型看的，状态是给调度器看的。**混在一起就没法做精细控制了。」
:::

## 7. 三类子 Agent（为什么是三类，不是一类）

:::card 三个角色 + 各自的目标函数
| 角色 | 目标函数（本质） | 典型动作 | 触发条件 |
|---|---|---|---|
| **补全 Agent** | 最大化**覆盖率** | 为未覆盖子目标生成检索 query、查询改写、扩展同义词 | `coverage < 1` 且还有预算 |
| **反驳 Agent** | 最大化**证据对抗性**（找反证） | 用"否定式/对立面"表述检索（对抗检索）、查不同来源 | 某个子目标"已覆盖"但置信度低，或声明本身可疑 |
| **冲突消解 Agent** | 最小化**未消解冲突数** | 针对性检索（用冲突双方的实体/数值再查）、来源可信度比较、时间戳比较 | `conflicts[]` 非空 |

**为什么不能合并成一个 Agent**（必答，见 §12 第一题）：
1. **目标冲突**：补全想"多找支撑"，反驳想"多找死磕"，混在一起模型会摇摆
2. **上下文污染**：找反证的上下文会干扰"找缺失"的判断
3. **可评测**：分开之后才能做"去掉反驳 Agent 掉多少"这种消融
:::

## 8. 事实依赖图（调度的骨架）

:::card 图怎么建、怎么用
**节点**：子目标（关键事实）
**边**：依赖关系 —— "要验证 g3，需要先知道 g1 的结果"
**建图方式**（🟡按你实际做法核对）：LLM 抽取 + 规则校验（比如要求中间实体必须出现在两端子目标里，否则拒掉这条边）

**用途**：
1. **决定顺序**：拓扑序优先查"被依赖的"子目标 —— 因为它的结果会改变后续子目标的表述
2. **剪枝**：如果 g1 已经判定为假，依赖它的 g3 可能**不需要再查**（省预算）
3. **解释性**：最后给出的判断可以说清"结论依赖哪条链"

**面试话术**：「依赖图解决的是"**先查什么**"。没有它，多轮检索就是无头苍蝇 —— 会出现"反复查同一个事实的不同说法"这种浪费。」
:::

## 9. 策略层：把"要查什么"翻译成"怎么查"

:::card 四类策略 + 触发条件
| 策略 | 做什么 | 什么时候用 |
|---|---|---|
| **直接检索** | 原样用子目标当 query | 默认，子目标表述与证据表述接近时 |
| **查询改写** | 同义改写、术语扩展、拆成子问题 | 直接检索**召回为 0 或很低** |
| **对抗检索** | 用否定/对立表述检索（"X 没有…"、"X 是否…"） | 需要**验证反面**，或证据一致得可疑 |
| **冲突消解检索** | 用冲突双方的**具体实体/数值**再查 | `conflicts[]` 非空 |

**关键设计**：策略不是 Agent 自己随便选，而是**由状态驱动分发**（`coverage` / `marginal_gain` / `conflicts` 决定），这样**可复现、可调试**。

> 这和 **Function Calling 里的 tool router** 是同一个东西，只是你的"工具"是检索策略。面试时可以直接这么映射（见 §11）。
:::

## 10. 控制流与终止条件（面试必问"怎么停"）

:::card 三类终止 + 一个兜底
| 条件 | 判据 | 触发后动作 |
|---|---|---|
| **证据充分** | `coverage == 1` 且 `conflicts` 已消解（或已标记为"不可消解"） | 进入聚合 → 输出标签 + 置信度 |
| **预算耗尽** | 检索次数 / token / 轮次触顶 | 用现有证据输出，**标注"低置信"** |
| **边际收益趋零** | 连续 k 轮 `marginal_gain == 0` | 判定"检索已饱和" → 输出 |
| 兜底 | 检测到**动作重复**（同样 query 出现两次） | 强制换策略或终止 |

**防打转的两个手段**（必答）：
1. **动作去重**：把 (策略, query 归一化形式) 做哈希，重复则不允许再执行同一动作
2. **状态单调性**：要求每轮 `coverage` 或 `conflicts` 至少有一项改善，否则计为"无效轮"，连续无效就终止
:::

:::card 最容易撞的五个工作 + 你的差异化
| 已有工作 | 它做什么 | 你和它的差别 |

| **Self-RAG** | 模型自己判断"要不要检索"、并对检索结果自评 | 它是**单 Agent 自反思**；我是**多角色分工 + 显式状态**，可解释、可消融 |

> 「我是 **Adaptive-RAG 的多智能体实现 + 事实依赖图调度**：策略选择由证据状态驱动（覆盖率、冲突数、边际收益），而不是只按问题难度分档。」

## 12. 与 ReAct / Plan-and-Execute / LangGraph 的映射（把"自研"讲成"懂行"）

:::card 三张对照
**vs ReAct**
- ReAct：`Thought → Action → Observation` 单循环，靠模型自己决定下一步
- 你的：多了一个**显式状态层**，并且**每个子目标可以用不同角色去处理**
- 一句话：「我是 ReAct 的**多角色 + 状态驱动**版本。」

**vs Plan-and-Execute**
- P&E：先出完整计划，再执行，必要时 replan
- 你的：初始计划 = **事实依赖图**（哪些子目标、什么顺序），执行中按**覆盖率**动态插入新的检索动作
- 一句话：「我是 **Plan-and-Execute 的图版本**：计划不是线性步骤，而是一张依赖图，replan 由覆盖率驱动。」

**vs LangGraph**
- LangGraph 的核心概念：**共享 State + 节点/边 + checkpointer**
- 你的：证据状态 ≈ 它的 `State`；三类子 Agent ≈ 三个节点；依赖图调度 ≈ **条件边**
- 一句话：「我没用 LangGraph，但我的实现等价于它的 **State + 条件边 + 子图**这套抽象。」（🟡如果你后来用过 LangGraph，就改成"我用过之后发现映射是……"）
:::

## 14. 12 个追问预答

:::qa 为什么一定要多 Agent？一个 Agent 多轮不行吗（**最高频**）
三条理由 + 一条代价：
1. **目标函数不同**：补全要"多找支撑"，反驳要"主动找死磕"，混在一个角色里模型会摇摆（实证上表现为"检索意图漂移"）
2. **上下文隔离**：找反证的上下文会干扰"补缺失"的判断；分开后每个角色只看它需要的部分
3. **可评测**：分开才能做"去掉反驳 Agent 掉多少"的消融
**代价（主动承认）**：token 成本上升、协调开销、可能出现"两个 Agent 结论冲突"

**收尾句**：「所以我的设计原则是：**不是为了多 Agent 而多 Agent，而是因为三类证据需求的目标函数本来就不一样。**」
:::

:::qa 怎么证明多 Agent 是必要的？你的消融怎么设计的
三个对照（🟡按你实际做的说）：
1. **合并成单 Agent**（同一模型、同一状态、不分角色）→ 看掉多少
2. **去掉某一类角色**（最关键是去掉**反驳 Agent**，因为它决定"能不能发现反证"）
3. **去掉依赖图**（改成随机/固定顺序检索）→ 看顺序的影响

**如果只做过一个**，就说做过的那一个，并说明"其他对照是我下一步要补的"。
:::

:::qa 你说的 +3.7pp 是和谁比
（🟡必须能说出来）三类基线通常是：
- 单轮检索 + LLM 判断（最基础）
- 多轮固定次数检索
- 同期方法（🟡按你实际复现的）

**答不上来怎么办**：诚实说「同期方法里我主要对比的是单轮检索和固定多轮两类，具体的方法名我回去核对一下」——**比含糊说"和 SOTA 比"安全**。
:::

:::qa 循环怎么停下来？会不会一直检索
三类终止：**覆盖充分**（`coverage==1` 且冲突已消解）、**预算耗尽**、**边际收益趋零**（连续 k 轮没新增有效证据）。
再加一个兜底：**动作重复检测**（同一个 query 第二次出现就强制换策略或终止）。
:::

:::qa 怎么防止两个 Agent 打架 / 打转
两层机制：
1. **状态单调性约束**：每轮必须让 `coverage` 或 `conflicts` 至少一项改善，否则记为无效轮，连续无效即停
2. **冲突交给第三个角色**：补全和反驳结论不一致时，不由它们自己吵，而是交给**冲突消解 Agent**按来源可信度/时间戳/证据数量做裁决
:::

:::qa 证据状态会不会也爆掉
会，所以有三个限制：
1. **只存结论 + 指针**（哪条证据支撑哪个子目标），原始长文本按需回取
2. **子目标数量有上限**（拆解时限制个数，超了就合并）
3. **冲突表只存未消解的**，消解完就归档
:::

:::qa 子目标怎么拆？拆得好不好怎么判断
（🟡按你实际做法）通用做法：
- 用 LLM 按"可独立验证"的原则拆：每个子目标应该是**单一事实核**，能用一条证据支持或反驳
- **可验证性检查**：拆完后检查每个子目标能不能构造出检索 query，不能就重新拆
- **粒度控制**：太细 → 检索次数爆炸；太粗 → 又回到"一次检索搞不定"

**加分**：「粒度是这类方法最需要调的超参，我的经验是"一个子目标对应一个实体关系"比较合适。」
:::

:::qa 冲突消解具体怎么做？规则还是模型
（🟡按实际说）通常是组合：
1. **来源可信度**（权威源 > 聚合站）
2. **时间戳**（新 > 旧，尤其是会变化的事实）
3. **证据数量**（多数一致 vs 单条异见）
4. 最后才让 LLM 做语义裁决

**关键点**：「我优先用**规则**，因为规则可解释、可复现；只有规则判不了（比如两条都一样权威）才交给模型。」
:::

:::qa 这和 Self-RAG / CRAG / Adaptive-RAG 有什么区别
见 §11 的对照表。**一句话版**：「我是 Adaptive-RAG 的多智能体实现 + 依赖图调度：策略由**证据状态**（覆盖率/冲突/边际收益）驱动，而不是只按问题难度分档。」
:::

:::qa 你的成本比单轮检索高多少
（🟡按你统计的说）如果没统计过，诚实说：「我没有系统统计过成本，这是我认为该补的一项 —— 因为多轮检索的**收益必须和检索次数的增加放在一起看**才有意义。」
**这个回答比编数字好**，而且体现你懂"代价"这个概念。
:::

:::qa 失败案例有哪些
准备 2–3 个真实类别（不用编具体例子）：
1. **拆解错了**：子目标拆得不合理（比如把"因果"和"时间"混在一个子目标里）→ 后面全歪
2. **检索饱和但覆盖不够**：某些子目标的信息根本不在语料里 → 应该早点判"不可验证"而不是继续查
3. **冲突不可消解**：两个权威源直接矛盾 → 系统应该输出"存在冲突"而不是硬选一个
:::

:::qa 这个项目没有论文，你怎么看
**不要辩解，给判断**：
> 「它还在进行中，我的判断是两件事还没做完：一是**成本与收益的完整对照**（多轮检索多花多少、换回多少），二是**和同期方法的充分对比**。这两块不补齐，我觉得还不到投稿的程度。」
**加分**：说明你对"什么时候算做完了"有标准，而不是凑一个结果就投。
:::

## 15. 陷阱：哪些话不能说

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「我用了 AutoGen / LangGraph 搭了几个 Agent」 | 「编排层是我手写的：状态、角色分工、依赖图调度、策略分发、终止判定」（**除非你真的用过**） |
| 「这是我最成熟的工作」 | 「这是我在研的工作，方法和实验都还在补」 |
| 「比 SOTA 高 3.7 个点」 | 「比同期方法**平均**高 3.7 个点，提升主要来自多跳那类」 |
| 「多 Agent 比单 Agent 好」 | 「**三类证据需求的目标函数不同**，所以分开更合理；代价是 token 成本」 |
| 「我们有长期记忆」 | 「我有**任务内的结构化工作记忆**（证据状态），不做跨会话长期记忆」 |
| 「这是个可以上线的系统」 | 「这是验证思路的原型，缺 trace、沙箱、并发调度」 |

## 16. 自测（6 题）

:::qa 一句话说清这个项目的核心创新
不是"用多 Agent"，而是**用证据状态（覆盖率/冲突/边际收益）驱动"什么时候继续检索、下一步该谁执行"**，把单轮静态检索变成状态反馈驱动的多轮决策。
:::

:::qa 单轮静态检索的四种失败模式
覆盖不全、证据冲突、需要多跳、查询与证据错配。每种都要能举一个声明例子。
:::

:::qa 为什么"状态"比"上下文"重要
上下文是给模型看的、会爆；状态是给调度器看的、可查询可约束（覆盖率、冲突数、边际收益），还让多个 Agent 能共享而不互相污染。
:::

:::qa 你的循环怎么停？怎么防打转
三类终止：覆盖充分、预算耗尽、边际收益趋零；防打转靠**动作去重** + **状态单调性约束**（每轮必须有改善）。
:::

:::qa 你这和 Adaptive-RAG 的区别
Adaptive-RAG 按**问题难度**选策略；我按**证据状态**（覆盖率/冲突/边际收益）选，并且是多角色分工 + 依赖图调度。
:::

:::qa 这个项目最诚实的局限
工程化不够：有状态管理和循环控制，但没有生产级 trace、沙箱、并发调度；另外成本与收益的完整对照还没做完。
:::
