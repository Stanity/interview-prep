# 5.1 RAG 全链路与调优（从索引到引用的每一段）

> **你的位置**：RAG 是你实战过的（四检索器 × 四类 QA × 400 问），所以这篇**跳过入门**，直接讲每一段的**失败模式与对策**。
> **本文的作用**：给你一张"**出问题该改哪一段**"的诊断表 —— 面试官最想看的就是这个。
> **标注**：`★★★`

---

## 1. 30 秒口述版

:::card 30 秒版
「RAG 有五个环节：**索引 → 检索 → 重排 → 生成 → 引用**。

关键在于：**每一环都有专属的失败模式**，所以调优不能凭感觉。我的判断顺序是：
1. **先看检索**：召回里有没有正确答案所在的 chunk（Recall@k）？没有的话，后面再强也没用
2. **有召回但答错**：那是**重排或上下文组装**的问题（噪声太多、位置不对）
3. **召回对、上下文也对，还是错**：才是**生成**的问题（模型没用上证据、或压根不信检索结果）

一句话概括：**RAG 的绝大多数失败发生在检索，而不是生成** —— 但大家往往先去换更大的模型。」

**"绝大多数失败在检索"这句是面试的分水岭**，很多人默认以为是模型不行。
:::

## 2. 五段链路 × 失败模式（这张表是全文骨架）

| 环节 | 做什么 | 典型失败模式 | 对策 |
|---|---|---|---|
| **① 索引** | 解析文档 → 切块 → 向量化 → 入库 | 切块切断语义、表格/多栏解析错、元数据缺失 | 语义切块、父子块、保留标题层级与页码 |
| **② 检索** | 从库中召回 top-k | **召回不到**（表述差异、术语不同、多跳） | 混合检索（BM25+稠密）、查询改写、多查询、HyDE |
| **③ 重排** | 对候选精排 | **排序错**（相关的不在前列）、噪声挤占上下文 | cross-encoder reranker、去重、多样性 |
| **④ 生成** | 基于证据作答 | **不用证据**（凭先验作答）、**过度使用**（把噪声当证据） | 提示约束 + 引用要求 + 拒答机制 |
| **⑤ 引用** | 标注来源 | 引用错位（说的和引的不是一回事） | 生成后逐句核验、引用回填 |

## 3. 索引层：chunking 四种策略

:::card 对比表（面试常问"怎么切"）
| 策略 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **定长切分** | 每 N token 一块，带重叠 | 简单、块大小可控 | **会切断语义**（一句话被劈开） | 兜底方案 |
| **语义/段落切分** | 按段落、句子边界切 | 语义完整 | 块大小不均 | 结构化文档 |
| **递归切分**（recursive） | 按 `\n\n` → `\n` → 句号 逐级降级，尽量在高层边界切 | 兼顾完整与大小 | 实现稍复杂 | **最常用的默认选择** |
| **父子块**（small-to-big） | 索引小块（精度高），生成时取父块（上下文全） | 同时兼顾召回精度与上下文完整 | 需要维护层级 | **推荐用于长文档** |

**两个必说的工程细节**：
1. **重叠（overlap）**：定长切分要加 10–20% 重叠，防止关键句被切断
2. **元数据**：每块必须带 `doc_id / 标题路径 / 页码 / 权限` —— 引用、过滤、审计全靠它
:::

## 4. 检索层：什么时候该加什么

:::card 按"症状"给方案（这张表比罗列技术更有用）
| 症状 | 先试什么 | 再试什么 |
|---|---|---|
| 表述差异导致召回不到（同义词、术语） | **混合检索**（加 BM25） | 查询改写 / 同义词扩展 |
| 问题短、信息少 | **HyDE**（先让模型写假想答案再检索） | 多查询（生成 3–5 个变体） |
| 需要多跳（答案在第二跳文档里） | **多跳检索**（IRCoT / 迭代检索） | 查询分解（拆成子问题） |
| 长尾专业术语 | 领域 embedding 微调 | 加关键词召回兜底 |
| 召回了但排序差 | **加 reranker** | 调整 top-k / 去重 |
:::

## 5. 重排层：cross-encoder 为什么更强

:::card 双塔 vs cross-encoder
| | **双塔（bi-encoder）** | **cross-encoder** |
|---|---|---|
| 计算方式 | query 和 doc **分别**编码，算向量相似度 | query + doc **拼接**后一起过模型 |
| 优点 | 可**预计算** doc 向量 → 快，能扫百万级 | 能建模 token 级交互 → **精度高** |
| 缺点 | 交互信息丢失 | **无法预计算**，只能对候选集精排 → 慢 |
| 用法 | 召回（top-100~1000） | **重排**（top-20~100） |

**所以标准架构是两段式**：先用双塔召回（广），再用 cross-encoder 重排（准）。**不能直接用 cross-encoder 做全库检索**（成本不可接受）。
:::

:::card 重排的两个额外收益（容易忽略）
1. **去重 / 多样性**：同一文档的相邻块会冗余挤占上下文 → 重排时可以加 MMR 一类多样性策略
2. **可解释性**：reranker 的分数能用来做**拒识**（分数都低 → 说明库里没有 → 走"无答案"分支）
:::

## 6. 生成层：两个相反的错误

:::card 过度信任 vs 完全不信任
| 错误 | 表现 | 对策 |
|---|---|---|
| **不用证据**（凭先验答） | 证据里写着 A，模型答 B（因为它"知道"的 B 更常见） | 提示要求"**只依据给定证据**"；要求逐句引用；先抽取后回答 |
| **过度使用**（把噪声当证据） | 检索里有无关块，模型硬凑 | 要求"证据不足时说不知道"；上下文压缩/去噪；降低 top-k |

**一个高价值技巧**：**先抽取、再回答**（extract-then-answer）—— 让模型先从证据里摘出相关句子，再基于摘出的句子作答。这能显著降低"凭先验答"的概率。
:::

## 7. 上下文组装（顺序很重要）

:::card 三条规则
1. **顺序**：最相关的证据放**结尾附近**（利用 lost in the middle 的首尾优势，见 4.2）；开头用一句指令强调"只依据以下证据"
2. **去重**：同一文档的相邻块只留最相关的一个（否则浪费上下文还增加噪声）
3. **压缩**：长块只留包含答案的句子（句子级抽取），可显著提高信噪比

**面试话术**：「上下文组装不是"把 top-k 拼起来就行"—— **顺序、去重、压缩**三件事决定了模型能不能真的用上证据。」
:::

## 8. 诊断顺序（**面试最想看这个**）

:::card 四步定位
```
① Recall@k 够吗？          ── 不够 → 问题在「索引 / 检索」
   ↓ 够
② 正确 chunk 在 top-3 里吗？ ── 不在 → 问题在「重排」
   ↓ 在
③ 塞进 context 后还在吗？   ── 不在 → 问题在「上下文组装」（被截断/被去重掉）
   ↓ 在
④ 模型答对了吗？            ── 没答对 → 问题在「生成」（提示/模型/拒答策略）
```

**这套顺序的价值**：它把"RAG 效果不好"这种模糊抱怨，变成**四个可测量的检查点**。
:::

## 9. 工业级架构（可以画在白板上）

```
文档源 → 解析（PDF/HTML/表格）→ 清洗去重 → 切块(+元数据) → Embedding → 向量库
                                                        ↓
用户 query → 改写/扩展 → 混合检索（向量 + BM25）→ 融合(RRF) → Rerank(top-n)
                                                        ↓
                                  上下文组装（去重/压缩/排序 + 权限过滤）
                                                        ↓
                                            LLM 生成（约束 + 引用）
                                                        ↓
                                  引用回填 + 忠实度校验 → 输出
                                                        ↓
                                    日志/反馈 → 评测集 → 迭代
```
:::

:::card 三个容易被问的工程点
1. **增量更新**：文档会变 → 需要 `doc_id + 版本`，重新嵌入时删除旧块（否则新旧都召回到，答案矛盾）
2. **权限过滤要在检索时做**（metadata filter），**不能先 top-k 再过滤** —— 后者会让召回崩掉且泄露内容（详见 09 号补丁 §6）
3. **缓存**：相同 query 的检索结果可以缓存；embedding 也可以缓存（内容不变就不用重算）
:::

## 10. 十个追问预答

:::qa RAG 效果不好，你先查哪
**先查检索（Recall@k）**。因为绝大多数失败是"正确答案根本不在召回的 chunk 里"，这时换再大的模型也没用。只有确认召回对了，才去看重排、组装、生成。
:::

:::qa chunk 越大越好还是越小越好
都不对，是**权衡**：
- 太小 → 语义不完整、召回精度高但上下文不足
- 太大 → 噪声多、挤占上下文、稀释注意力
**推荐父子块**：用小块检索（精度）、用父块生成（上下文完整）。
:::

:::qa 为什么需要 reranker？直接向量检索不行吗
因为双塔（bi-encoder）**分别编码** query 和 doc，丢失了 token 级交互；cross-encoder 把两者拼接后一起编码，精度明显更高。但 cross-encoder 无法预计算 → 只能对少量候选精排。所以就"双塔召回 + cross-encoder 精排"。
:::

:::qa 混合检索为什么比单一检索好
BM25 擅长**精确词匹配**（术语、编号、人名），稠密检索擅长**语义相似**（同义改写）。两者失效场景互补，用 RRF 融合后召回更稳。
:::

:::qa RRF 是什么？为什么不用分数加权
Reciprocal Rank Fusion：`score = Σ 1/(k + rank_i)`，只用**排名**不用分数。因为不同检索器的分数量纲不同（余弦相似度 vs BM25 分数），加权需要调参且不稳定；用排名更鲁棒。
:::

:::qa 怎么防止模型"不用证据、凭先验回答"
三个手段：① 提示里明确"只依据给定证据，证据不足就说不知道"；② 要求**逐句引用**（引用不到的句子标记为不确定）；③ **先抽取后回答**（先从证据摘句，再基于摘句作答）。
:::

:::qa 上下文里塞多少块合适
不是越多越好：噪声会稀释注意力、挤占上下文。常见做法是 rerank 后取 **3–8 块**，并做去重与压缩。判断依据是"信噪比"，不是"数量"。
:::

:::qa RAG 的引用（citation）怎么做才可靠
两点：① 每块有稳定 id 与页码，生成时要求模型输出 `[chunk_id]`；② 生成后**回填校验**：检查引用的 chunk 里是否真的包含支撑该句的内容，不包含就标记为低置信。
:::

:::qa 文档更新了怎么办
按 `doc_id + 版本` 管理：新增版本时**删除旧块**再插入新块，否则新旧块都会召回到 → 答案矛盾。同时要能追溯"这条答案基于哪一版"。
:::

:::qa RAG 和长上下文怎么选
互补：RAG 便宜、可溯源、可实时更新；长上下文能保留更多上下文但贵且无法溯源。**实务上 RAG 负责"找对"，长上下文负责"看全"** —— 常见组合是"检索出 20 块喂给长上下文模型"。
:::

## 11. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「RAG 效果不好就换个大模型」 | 「先查 Recall@k —— 绝大多数失败在检索，不在生成」 |
| 「chunk 越小召回越准越好」 | 「小 chunk 精度高但上下文不足，推荐**父子块**」 |
| 「有向量检索就不需要 BM25」 | 「BM25 擅长精确词匹配，与稠密检索**互补**，混合检索更稳」 |
| 「top-k 越大召回越好」 | 「越大噪声越多、挤占上下文；要用**信噪比**判断，配合 rerank」 |
| 「引用就是让模型写个来源」 | 「引用要做**回填校验**，检查被引内容真的支撑该句」 |

## 12. 自测（6 题）

:::qa RAG 五个环节，各一句失败模式
索引（切块断语义/解析错）、检索（召回不到）、重排（排序差/噪声）、生成（不用证据或过度使用噪声）、引用（错位）。
:::

:::qa 诊断 RAG 的四步顺序
Recall@k → 正确 chunk 是否在 top-3 → 塞进 context 后是否还在 → 最终答案对不对。依次对应 索引/检索 → 重排 → 组装 → 生成。
:::

:::qa 父子块解决什么问题
小块检索保精度、父块生成保上下文完整，同时缓解"切太细语义不完整"和"切太大噪声多"。
:::

:::qa 为什么 cross-encoder 不能直接做全库检索
它必须把 query+doc 拼接后一起前向，无法预计算 doc 表示 → 扫全库成本不可接受。只能对双塔召回的候选精排。
:::

:::qa 防止模型"凭先验答"的三个手段
提示限定只用证据、要求逐句引用、先抽取后回答。
:::

:::qa 多租户的权限过滤为什么不能"先取 top-k 再过滤"
会把别的租户内容取进来再丢掉：召回崩掉（只剩少量合法块）且内容已进入服务内存/日志，存在泄露风险。必须在检索时带 metadata filter。
:::
