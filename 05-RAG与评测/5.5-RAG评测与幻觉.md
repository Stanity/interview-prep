# 5.5 RAG 评测与幻觉（指标怎么选、幻觉怎么量）

> **为什么这篇重要**：面试官判断"你是不是真的做过实验"，看的就是你会不会评测 —— 尤其"你的指标为什么这么选"。
> **你的优势**：你做过四类数据集的完整评测（Macro-F1、ASR、Retrieval F1、Complete Success），这块你有实盘经验。
> **标注**：`★★★`

---

## 1. 30 秒口述版

:::card 30 秒版
「RAG 评测必须**分两层**，混在一起就说不清问题在哪：

**检索侧**看"该找的有没有找到、排得对不对"：Recall@k（有没有召回）、MRR（第一个正确的排多前）、nDCG（考虑位置的排序质量）。
**生成侧**看"答得对不对、有没有根据"：EM/F1（有标准答案时）、LLM-judge（开放问答）、**忠实度 faithfulness**（答案是否被证据支持）。

RAGAS 把生成侧拆成四个可算的指标：**faithfulness（忠实度）、answer relevancy（相关性）、context precision（检索的精度）、context recall（检索的覆盖）**。

其中**忠实度**是 RAG 特有的、也最关键的一个：做法是把答案拆成若干**原子陈述**，逐条判断"是否被给定上下文蕴含"，比例就是分数。

我的观点是：**只报一个端到端分数是最不可信的** —— 必须能说清"提升来自检索还是生成"。」
:::

---

## 2. 两层评测（这张表是骨架）

| 层 | 评什么 | 指标 | 什么时候必须测 |
|---|---|---|---|
| **检索** | 该找的找到了吗、排序好吗 | Recall@k、Precision@k、MRR、nDCG | 只要改了 chunking/embedding/检索器 |
| **生成** | 答得对不对、有没有依据 | EM/F1、LLM-judge、**faithfulness** | 只要改了 prompt/模型/上下文组装 |
| **端到端** | 用户满意度 | 任务成功率、人工评分 | 上线前/回归 |

:::card 为什么必须分层
因为**同一个端到端分数背后可能是完全不同的问题**：
- 检索差 + 生成强 → 模型在"没证据的情况下硬答"（幻觉，但分数看起来还行）
- 检索好 + 生成差 → 证据给了但模型没用（提示或模型能力问题）

**分层之后，"分数掉了"才能定位到具体环节。**
:::

---

## 3. 检索侧指标（四个要分清）

:::card 定义与适用
| 指标 | 定义 | 特点 |
|---|---|---|
| **Recall@k** | top-k 里是否包含**所有**相关文档（的比例） | RAG 里最关心它 —— **没召回就全完了** |
| **Precision@k** | top-k 里相关文档的比例 | 噪声控制（影响上下文信噪比） |
| **MRR** | 第一个相关文档排名的倒数均值 | 关心"第一个对的排多前" |
| **nDCG@k** | 考虑位置折扣（越靠前权重越高）的排序质量 | 最贴近"排序好坏"，支持多级相关性 |

**RAG 场景的优先级**：
> **先看 Recall@k（能不能找到），再看 nDCG/MRR（排得好不好），最后看 Precision（噪声多不多）。**

**面试话术**：「RAG 里 Recall 是**必要条件** —— 召回里没有正确答案，后面任何环节都救不回来。所以我的调优顺序永远是先提 Recall，再优化排序。」
:::

---

## 4. 生成侧指标

:::card 从严格到宽松
| 指标 | 怎么算 | 适用 | 局限 |
|---|---|---|---|
| **EM（Exact Match）** | 完全匹配参考答案 | 短答案 QA（如 NQ） | 太严格，同义表述判错 |
| **F1（token 级）** | 与参考答案的词重叠 F1 | 抽取式 QA | 不懂语义 |
| **ROUGE** | n-gram 重叠 | 摘要 | 偏重字面重叠 |
| **BERTScore** | 用 embedding 算语义相似 | 生成质量 | 与"正确性"不完全相关 |
| **LLM-as-judge** | 让强模型打分/判定 | 开放问答 | 有偏差（见 §7） |
| **Faithfulness** | 答案是否被 context 支持 | **RAG 必测** | 需要拆陈述 + 验证 |

**关键判断**（面试常问）：
- **有标准答案**（数学、短答、事实核查）→ EM/F1/准确率 + Macro 平均
- **开放问答** → LLM-judge + 忠实度，**并且要人工抽检校准**
:::

## 5. RAGAS 四指标（能逐条解释就够）

:::card 四个指标分别在量什么
| 指标 | 量什么 | 高说明 | 低说明 |
|---|---|---|---|
| **Faithfulness**（忠实度） | 答案的每个陈述是否被 given context 支持 | 没有编造 | **模型在瞎编**（或 context 不够） |
| **Answer Relevancy** | 答案是否切题 | 直接回答问题 | 答非所问/绕圈子 |
| **Context Precision** | 检索到的 context 中"真正有用"的比例（含排序） | 检索精准、噪声少 | 塞了一堆无关内容 |
| **Context Recall** | 参考答案里的信息有多少被 context 覆盖 | 检索覆盖全 | **漏了关键证据** |
:::

:::card Faithfulness 的具体算法（这个细节很值钱）
1. 用 LLM 把答案拆成若干 **atomic statements**（原子陈述，每条只含一个事实）
2. 对每条陈述，判断**是否能被给定的 context 蕴含**（entailment，可用 LLM 或 NLI 模型）
3. `faithfulness = 被支持的陈述数 / 总陈述数`

**为什么这样设计**：它把"整体是否合理"变成**可逐条核查**，所以能定位到"哪一句是编的"。
**局限**：拆陈述和判断都依赖 LLM，本身有噪声；对**多跳推理**（需要组合两条证据才能支持一句）会低估忠实度。
:::

## 6. 幻觉的两类（分清才能对症）

:::card 分类
| 类型 | 定义 | RAG 里的表现 | 对策 |
|---|---|---|---|
| **内在幻觉**（intrinsic） | 输出与给定证据**矛盾** | 证据写 A，模型答非 A | 提高忠实度约束、逐句引用 |
| **外在幻觉**（extrinsic） | 输出包含证据里**没有**的信息（无法验证） | 添加了"额外背景知识" | 限定"只说证据里的"、要求拒答 |
| **事实性错误**（另一维度） | 证据本身就错，模型忠实复述了 | 检索到错文档 | **这不是模型的错**，要治数据 |

**这句话面试很值钱**：
> 「如果 context 本身是错的，模型**忠实复述**反而是"忠实度高但事实错"。所以评测必须**同时看忠实度和事实正确性** —— 只测一个都会漏。」
:::

## 7. LLM-as-judge 的偏差与校准

:::card 四类已知偏差
| 偏差 | 表现 | 缓解 |
|---|---|---|
| **位置偏差** | 偏好第一个/最后一个候选 | 随机打乱顺序、双向评两次取平均 |
| **长度偏差** | 偏好更长的回答 | 控制长度、或在 prompt 里说明"长度不代表质量" |
| **自我偏好** | 偏好自己（同家族模型）生成的答案 | 用不同家族模型做 judge，或多模型投票 |
| **格式偏差** | 偏好排版好看但内容一般的答案 | 统一格式后再评 |

**校准方法**（面试加分）：
1. **人工标注 100–200 条做锚点**，算 judge 与人工的一致性（Cohen's kappa / 一致率）
2. **一致率不达标就不用 judge 做主指标**，只当粗筛
3. 用**成对比较**（A vs B 哪个好）代替绝对打分，稳定性更高
:::

## 8. 端到端 vs 组件评测的分工

:::card 什么时候用哪个
| 场景 | 该用 |
|---|---|
| 定位 bug / 做消融 | **组件评测**（检索、生成分开） |
| 上线前回归 | **端到端**（任务成功率/人工评分） |
| 快速迭代 | 组件 + 小规模端到端抽样 |
| 对外汇报 | 端到端为主 + 组件解释原因 |

**面试话术**：「我一般**用组件评测做优化，用端到端评测做验收** —— 因为组件指标能告诉我改哪里，端到端只能告诉我好不好。」
:::

## 9. 【挂点】你论文里的评测实践怎么讲

:::card 你可以直接说的
| 你的做法 | 对应的评测原则 |
|---|---|
| 四个数据集分别报 **Macro-F1** | 类别不均衡时用 Macro（每类等权，反映难类表现） |
| HoVer 拆成 2-hop / 3-hop / 4-hop 分别报 | **分层报告**：越难的子集越能看出差距 |
| ASR + **Retrieval F1** 双指标 | 同时测"攻击效果"和"检索是否命中"，避免只看结果 |
| 自己补 **Complete Success / Break Failure** | 因为 ASR 不足以说明"依赖关系"，所以**发明更贴合的指标** |
| 消融 / 骨干对比 / 超参敏感性 / 噪声鲁棒性 | **多维度验证**，不靠单一数字下结论 |

**最值钱的一句**：
> 「我在 CausalPoison 里做的事本质上是**指标设计**：发现 ASR 会高估攻击成功率（因为含假成功），于是加了 Complete Success 和 Break Failure。**这跟 RAG 里"不能只报端到端分数"是同一个思路** —— 指标要能支撑你想下的结论。」
:::

## 10. 十个追问预答

:::qa RAG 评测为什么必须分检索和生成两层
因为端到端分数无法定位问题：检索差+生成强会表现为"模型硬答"（幻觉），检索好+生成差表现为"没用好证据"。分层才能知道改哪里。
:::

:::qa Recall@k 和 nDCG 分别关心什么
Recall@k 关心"该找的有没有被找到"（必要条件）；nDCG 关心"排得好不好"（考虑位置折扣）。RAG 里先保 Recall，再优化排序。
:::

:::qa faithfulness 怎么算
把答案拆成 atomic statements → 逐条判断是否被给定 context 蕴含 → 被支持的比例。局限是依赖 LLM 判断，对多跳组合会低估。
:::

:::qa 内在幻觉和外在幻觉的区别
内在：与给定证据矛盾；外在：包含了证据里没有的、无法验证的信息。两者对策不同（前者要强化忠实度约束，后者要限定"只说证据里的"）。
:::

:::qa 如果 context 本身是错的，模型忠实复述算幻觉吗
算"事实错误但忠实度高"。这说明**只测忠实度不够**，必须同时测事实正确性。这类问题的根因在数据，不在模型。
:::

:::qa LLM-as-judge 有哪些偏差，怎么缓解
位置偏差（打乱顺序）、长度偏差（控长度）、自我偏好（换家族模型/多模型投票）、格式偏差（统一格式）。用人工标注算一致性做校准，不达标就不当主指标。
:::

:::qa 什么时候用端到端，什么时候用组件
优化用组件（能定位），验收用端到端（能代表用户体验）。
:::

:::qa 你的论文为什么用 Macro-F1 而不是 Accuracy
四个数据集类别不均衡，Accuracy 会被多数类主导；Macro 对每类等权，能反映难类表现，对"判别边界是否稳"更敏感。
:::

:::qa 怎么证明一个 RAG 系统"不是看起来对"
三件事：忠实度（逐条核查是否被证据支持）+ 引用核验（引用的内容真的支撑该句）+ 人工抽检。只看得分容易被"流畅但错"骗过。
:::

:::qa 你会怎么给一个上线中的 RAG 系统做持续评测
① 固定的回归集（覆盖高频/难例）② 每次改动跑组件+端到端 ③ 线上抽样人工评 + 失败样本回流进回归集 ④ 监控指标分布（长度、拒答率、引用率）而不只看均值。
:::

## 11. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「RAG 评测就是看答案对不对」 | 「要分**检索侧和生成侧**，否则无法定位问题」 |
| 「忠实度高就说明没有幻觉」 | 「context 本身错时，忠实复述是"忠实但事实错" → 必须同时测事实正确性」 |
| 「用 GPT-4 当 judge 就够了」 | 「judge 有位置/长度/自我偏好偏差，要打乱顺序 + 人工一致性校准」 |
| 「指标越高越好」 | 「要说清指标**支撑什么结论**；ASR 高不代表控制了关系（我在 CausalPoison 里补了 Complete Success）」 |
| 「用 Accuracy 就行」 | 「类别不均衡用 Macro-F1，并分层报告难子集」 |
