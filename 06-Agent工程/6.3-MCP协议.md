# 6.3 MCP 协议（Model Context Protocol）

> **为什么必须有一篇**：2026 年 Agent 类 JD 高频出现（小米明确要求"理解 MCP"）；清昴的 JD 也写了"支持 MCP 等标准化工具协议接入"。
> **你的处境**：你**没用过 MCP** —— 所以这篇的目标是"讲清协议 + 准备好诚实话术"，不是假装用过。
> **标注**：`★★☆`

---

## 1. 30 秒口述版

:::card 30 秒版
「MCP 解决的问题是**工具接入的组合爆炸**。

想象有 M 个 AI 应用（IDE、助手、Agent 平台）和 N 个数据源/工具（数据库、文件系统、GitHub、Slack）。没有标准时，每个应用都要为每个工具写一遍适配 → **M×N 个实现**。MCP 定义了一套统一协议，让工具方只写一次 server，应用方只写一次 client → **M+N**。

架构上分三层：**Host（宿主应用，如 IDE）→ Client（协议客户端，通常每个 server 一个）→ Server（工具提供方）**。

它有三个原语：**Tools（可执行的动作）、Resources（可读的上下文/数据）、Prompts（可复用的提示模板）**。

最关键的一句话区分：**MCP 是"工具/上下文的供应协议"，Function Calling 是"模型调用工具的接口"** —— 两者是**正交的两层**，通常搭配使用：MCP 负责"有什么工具可用"，function calling 负责"模型决定调哪个"。」
:::

---

## 2. 为什么需要 MCP（N×M 问题）

:::card 类比 LSP
**M 个宿主 × N 个能力源**，如果两两对接就是 **M×N** 份适配代码。

MCP 的做法是**定一个中间协议**，让双方都实现它 → 降到 **M+N**。

**最好的类比是 LSP（Language Server Protocol）**：编辑器（VSCode / Vim / Emacs）× 语言（Python / Go / Rust）本来也是 M×N；LSP 出来之后，编辑器实现一次 client，语言实现一次 server，就是 M+N。**MCP 就是"给 AI 应用用的 LSP"。**

这个类比面试时说出来，能立刻让人明白你抓住了本质。
:::

---

## 3. 三层架构

:::card Host / Client / Server
```
┌─────────────────────────────────────────┐
│  Host（宿主应用：IDE / Agent 平台 / 助手）│
│   ┌──────────┐  ┌──────────┐            │
│   │ Client A │  │ Client B │  ← 每个 server 一个 client
│   └────┬─────┘  └────┬─────┘            │
└────────┼─────────────┼──────────────────┘
         │ 协议         │ 协议
    ┌────▼────┐   ┌────▼────┐
    │Server 1 │   │Server 2 │  ← 工具/数据提供方
    │(文件系统)│   │ (GitHub) │
    └─────────┘   └─────────┘
```
- **Host**：面向用户的宿主应用，负责**权限决策**（哪个 server 能用、哪些工具要确认）
- **Client**：协议连接器，**一个 client 对接一个 server**（隔离性好，一个 server 崩不影响别的）
- **Server**：暴露 Tools / Resources / Prompts 的那一端（本地进程或远程服务）
:::

## 4. 三个原语（**必须能逐个说清"和什么对应"**）

:::card Tools / Resources / Prompts
| 原语 | 是什么 | 谁来控制 | 类比 |
|---|---|---|---|
| **Tools** | 可执行的**动作**（有副作用） | **模型**决定调用 | function calling 里的函数 |
| **Resources** | 可读的**上下文数据**（文件内容、表结构、日志） | **应用/用户**选择挂载 | REST 里的 GET |
| **Prompts** | 可复用的**提示模板**（带参数） | **用户**主动选择 | 预置的快捷指令模板 |
:::

:::card 为什么区分 Tools 和 Resources（面试常问）
**核心是"谁决定"和"有没有副作用"**：
- **Tools 有副作用、由模型自主决定调用** → 需要权限控制与确认
- **Resources 只读、由应用或用户决定要不要加载** → 更接近"上下文注入"，不经过模型自主选择

这个区分很重要：如果把所有东西都做成 tool，模型会"到处乱调"；把纯数据做成 resource，上下文注入更可控、更省 token。
:::

## 5. 传输方式

:::card 两种主流 + 一个演进
| 传输 | 场景 | 特点 |
|---|---|---|
| **stdio**（标准输入输出） | **本地进程**（如本地文件系统 server） | 最简单：宿主启动子进程，用 stdin/stdout 传 JSON-RPC；无需网络、天然隔离 |
| **HTTP + SSE** | 远程 server | 早期远程方案：客户端 POST，服务端用 Server-Sent Events 推流 |
| **Streamable HTTP** | 远程 server（新） | 取代纯 SSE，支持流式与非流式统一，更适合无状态/有状态混合部署 |

**面试话术**：「本地用 stdio（最省事、天然隔离），远程用 HTTP 系传输。**传输层可换，协议消息格式不变** —— 这是它能被广泛采用的原因之一。」
:::

## 6. 生命周期（能说出 4 步就够）

:::card 四步
1. **initialize**：客户端发协议版本 + 自己支持的能力；服务端返回版本 + 能力
2. **capabilities 协商**：确认双方支持哪些原语（如 server 是否有 tools/resources/prompts）
3. **正常请求/响应**：`tools/list`、`tools/call`、`resources/read`、`prompts/get` 等
4. **通知（notifications）**：单向消息，如"资源列表变了"、"进度更新"（不期待响应）

**注意点**：整个协议基于 **JSON-RPC 2.0**（请求有 id，响应要对应 id，通知没有 id）。
:::

## 7. 和 Function Calling 的关系（**最高频的一问**）

:::card 一句话 + 一张表
> **MCP 是"工具供应协议"，Function Calling 是"模型调用接口"。两者正交，通常搭配。**

| 维度 | Function Calling | MCP |
|---|---|---|
| 解决什么 | 模型**怎么表达**"我要调用谁、参数是什么" | 应用**怎么标准化地发现/连接**工具与上下文 |
| 谁定义 | 模型厂商（OpenAI / Anthropic 各自的格式） | 开放协议（跨厂商、跨应用） |
| 范围 | 单次调用（模型 ↔ 你的代码） | 工具生态（宿主 ↔ 多个 server） |
| 有副作用控制吗 | 无（你要自己加） | 有（权限、确认、资源分离） |

**组合方式**：Host 通过 MCP 从多个 server **发现**工具 → 把工具列表转成 function calling 的 schema 交给模型 → 模型返回 tool_call → Host 通过 MCP 调用对应 server。

**这就是为什么两个概念经常一起出现**：MCP 管"供应"，function calling 管"选择"。
:::

## 8. 最小 server 伪代码（能说清结构就够）

```python
# 伪代码：暴露一个工具 + 一个资源
server = MCPServer(name="filesystem")

@server.tool("read_file", description="读取指定路径的文件内容。仅用于已授权的目录。")
def read_file(path: str) -> str:
    return open(assert_within_sandbox(path)).read()

@server.resource("file://logs/{name}", mime="text/plain")
def get_log(name: str) -> str:
    return read_log(name)

server.run(transport="stdio")   # 本地用 stdio
```

**这段能在面试时手写出来，就足够证明你理解结构了**（即使没实际部署过）。
:::

## 9. 安全边界（会被追问）

:::card 四个风险 + 对策
| 风险 | 说明 | 对策 |
|---|---|---|
| **server 不可信** | 第三方 server 可能返回恶意内容（间接提示注入） | 只接入可信 server；对返回内容做**数据/指令分离**；输出侧校验 |
| **工具副作用** | server 提供的工具可能是写/删操作 | 权限分级 + 人工确认；按 server 做白名单 |
| **数据外泄** | server 拿到的是完整上下文 | 最小权限：只传该工具需要的字段，不把整个对话塞过去 |
| **凭证管理** | server 需要访问外部服务 | 短时凭证、按 server 隔离密钥、审计日志 |
:::

**一句话**：「MCP 让工具接入变容易了，但也把**信任边界**变复杂了 —— 宿主必须决定"信任哪个 server、给它多少上下文、它的写操作要不要确认"。」
:::

## 10. 八个追问预答

:::qa MCP 解决了什么问题？一句话
工具接入的 **M×N → M+N**。用类比：它就是"AI 应用领域的 LSP"。
:::

:::qa MCP 的三个原语分别是什么，谁来触发
Tools（动作，**模型**决定调用）、Resources（只读数据，**应用/用户**决定加载）、Prompts（模板，**用户**选择）。
:::

:::qa Tools 和 Resources 为什么要分开
因为"有没有副作用"和"谁决定"不同：Tools 有副作用、由模型自主调用，需要权限控制；Resources 只读、由应用注入，更可控也更省 token。
:::

:::qa MCP 和 Function Calling 什么关系
**正交两层**：MCP 管"工具/上下文的供应与发现"，function calling 管"模型怎么选择并表达调用"。典型组合是 Host 通过 MCP 发现工具 → 转成 function calling schema → 模型返回 tool_call → Host 经 MCP 调用。
:::

:::qa stdio 和 HTTP 传输怎么选
本地进程用 **stdio**（最简单、天然隔离、无网络开销）；远程用 **HTTP 系**（SSE / Streamable HTTP）。**协议消息格式不变，只换传输层**。
:::

:::qa MCP 的安全风险主要在哪
四类：不可信 server 的返回内容（间接提示注入）、工具副作用、上下文外泄（server 拿到的数据范围）、凭证管理。对策是最小权限 + 数据/指令分离 + 权限确认 + 审计。
:::

:::qa 【挂点】你没用过 MCP，怎么答
照实说没用过，然后给三样东西：① N×M 的动机和 LSP 类比；② 三层架构 + 三原语 + JSON-RPC 生命周期；③ 和 function calling 的正交关系。
**收尾**：「我实现过等效的"工具供应 + 路由"（策略分发 + 依赖校验），所以协议要解决的抽象我理解；缺的是具体的 server/client 实现经验。」
:::

:::qa 如果让你设计公司内部的 MCP 网关，要考虑什么
① **统一鉴权**（server 白名单、凭证隔离）；② **权限分级**（读/写/高危分开，写操作要确认）；③ **审计与回放**（谁调了什么、返回了什么）；④ **上下文最小化**（只传必要字段）；⑤ **限流与超时**；⑥ **工具描述治理**（描述质量直接决定模型选对率）。
:::

## 11. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「MCP 就是 function calling 的升级版」 | 「两者**正交**：MCP 管供应/发现，function calling 管模型选择」 |
| 「MCP 是某个厂商的私有协议」 | 「它是**开放协议**，价值就在于跨厂商跨应用（类似 LSP）」 |
| 「MCP 只有 tools 一种能力」 | 「三个原语：tools / resources / prompts」 |
| 「我用过 MCP」 | 「我理解它的协议设计，但没实际部署过 server/client」 |
