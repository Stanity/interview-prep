# 6.5 多 Agent 编排（拓扑、通信、聚合、成本）

> **这是你的优势项**：你的多智能体动态检索是**手写编排**（不是拿框架搭的），所以这篇要教你"把自研讲成体系"。
> **面试官最爱问的反问**：**"为什么不用一个 Agent？"** —— 这篇给你完整答法。
> **标注**：`★★★`

---

## 1. 30 秒口述版

:::card 30 秒版
「多 Agent 不是"越多越好"，它解决的是**单 Agent 做不到的三件事**：

① **上下文隔离**：不同子任务的上下文互相污染（找反证的证据会干扰"找缺失"的判断）；
② **目标函数不同**：补全要"多找支撑"，反驳要"主动找死磕"，混在一个角色里模型会摇摆；
③ **可评测与并行**：分开才能做"去掉某角色掉多少"的消融，也才能并行。

代价也很实在：**token 成本上升、协调开销、错误传播、可能死锁**。

编排上要定四件事：**拓扑**（supervisor / handoff / 群聊 / 层级）、**通信方式**（共享黑板 vs 消息传递）、**聚合策略**（投票 / 加权 / 辩论）、**成本控制**（并发上限、深度上限、预算分摊）。

我自己的实现是**共享黑板 + 依赖图调度**：三类子 Agent 共享一份证据状态，用事实依赖图决定谁先执行。」
:::

---

## 2. 什么时候**不该**用多 Agent（必须能答）

:::card 四个"别用"的信号
| 信号 | 说明 |
|---|---|
| **任务线性、步骤固定** | 直接 workflow 编排（代码写死的步骤）比 Agent 更可靠、更便宜 |
| **上下文能装得下** | 不需要隔离，单 Agent 就够 |
| **子任务目标一致** | 没有"目标冲突"就不需要多角色 |
| **延迟/成本敏感** | 多 Agent 的协调开销和 token 成本是单 Agent 的数倍 |

**面试话术**：「我判断的标准是：**如果一个问题用单个 prompt 就能稳定解决，加 Agent 只会增加不确定性和成本**。反过来，只有当"需要不同视角""上下文必须隔离""需要交叉验证"三者之一成立时，多 Agent 才划算。」
:::

:::card 一条加分判断
> 「多 Agent 最大的风险不是"做不好"，而是"**看起来很忙但没进展**"—— 多个角色互相确认、互相委派，token 烧了很多但状态没推进。所以我一定会加**状态单调性约束**（每轮必须有指标改善）。」
:::

## 3. 四种拓扑（一张表）

| 拓扑 | 结构 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **Supervisor（主管）** | 一个主 Agent 分派任务给子 Agent，收集结果 | 控制流清晰、易调试 | 主管成为瓶颈与单点 | 大多数场景的**默认选择** |
| **Handoff（移交）** | 当前 Agent 把控制权**移交**给另一个 | 简单、贴近客服场景 | 容易"踢皮球"、丢失上下文 | 客服/工单路由 |
| **Group chat（群聊）** | 多个 Agent 在同一对话里轮流发言 | 便于辩论/互补 | 成本高、容易跑题、需要发言控制 | 需要多视角讨论 |
| **Hierarchical（层级）** | Supervisor 下再有 Supervisor | 可扩展到大任务 | 层级越深，信息损耗越大 | 复杂长任务 |
:::

:::card 你的项目对应哪种
**你的实现接近"共享黑板 + 依赖图调度"**：
- 不是纯 supervisor（没有一个固定的主管角色）
- 更接近**黑板架构**：三类子 Agent 都读写同一份**证据状态**，由**依赖图 + 策略层**决定下一个谁执行

**这件事本身是个加分点**：说明你不是照抄某个框架的拓扑，而是**按问题选了合适的协调方式**。
:::

## 4. 通信：共享黑板 vs 消息传递

:::card 两种范式的本质区别
| 维度 | **共享黑板**（blackboard） | **消息传递**（message passing） |
|---|---|---|
| 数据怎么流 | 所有 Agent 读写**同一份状态** | Agent 之间**互相发消息** |
| 上下文 | 天然共享（只共享状态，不共享全部上下文） | 需要显式打包传过去 |
| 一致性 | 需要处理并发写 / 冲突 | 无共享状态，天然隔离 |
| 可调试 | **容易**（看一份状态就知道全局） | 难（要追消息链） |
| 典型问题 | 状态膨胀、写入冲突 | 信息丢失、消息风暴 |
:::

:::card 关键洞察（面试能讲出这句很值钱）
> **共享黑板共享的是"状态"，不是"上下文"。**

如果共享全部上下文，就等于退化成一个大的单 Agent（还多了协调开销）。**共享结构化状态（结论 + 指针）**才能既协作又隔离。

这句话正好解释了你项目的设计：三类子 Agent 共享**证据状态**（结构化），而不是共享彼此的全部检索结果。
:::

## 5. 聚合策略（多份结论怎么合成）

:::card 四种
| 策略 | 做法 | 适用 | 风险 |
|---|---|---|---|
| **投票** | 多数一致 | 同质 Agent、答案离散 | 系统性偏差时会一致地错 |
| **加权** | 按角色/置信度加权 | 有明确可信度差异 | 权重需校准 |
| **辩论** | 多轮互相质疑后收敛 | 需要严谨结论 | 成本高、可能不收敛 |
| **仲裁** | 专门的裁决角色/规则 | 有冲突需要定夺 | 仲裁者本身可能错 |
:::

**你的做法**：「我的**冲突消解 Agent** 就是一种仲裁：不是让补全和反驳去吵，而是交给第三方按来源可信度/时间戳/证据数量裁决。**先规则、规则判不了才让模型判** —— 因为规则可解释、可复现。」
:::

## 6. 六种失败模式（比"优点"更该准备）

:::card 现象 + 机制 + 对策
| 失败模式 | 现象 | 机制 | 对策 |
|---|---|---|---|
| **死锁 / 循环委派** | A 交给 B，B 又交回 A | 没有责任边界 | 深度上限 + 委派链去重 |
| **责任扩散** | 每个都说"这不是我的活" | 角色定义模糊 | 明确的触发条件与职责 |
| **错误级联** | 一个 Agent 错了，后面全错 | 串行依赖 | 关键节点加校验/交叉验证 |
| **token 爆炸** | 成本是单 Agent 的 5–10 倍 | 每个 Agent 都塞满上下文 | 只共享状态、限制上下文、并发上限 |
| **虚假共识** | 所有 Agent 都说对（同一模型同一偏差） | 同质化 | 用不同提示/不同检索源制造差异 |
| **无法收敛** | 辩论一直不停 | 没有终止条件 | 轮次上限 + 强制仲裁 |
:::

**最值得说的一个**：「**虚假共识**是最隐蔽的 —— 多个 Agent 用同一个模型、看同一批证据，很容易一致地错。所以我在多 Agent 里会刻意制造差异（不同检索策略、不同证据源），而不是让它们做同样的事。」
:::

## 7. 成本控制（真实系统必须做）

:::card 五个旋钮
| 旋钮 | 作用 |
|---|---|
| **并发上限** | 同时最多跑几个子 Agent（防 token 峰值） |
| **深度上限** | 委派链最多几层（防递归） |
| **预算分摊** | 给每个子 Agent 分配 token/步数配额 |
| **早停** | 状态无改善就终止（防"看起来很忙"） |
| **上下文裁剪** | 子 Agent 只拿它需要的状态字段，不给全量 |

**一句话**：「多 Agent 的成本不是"多几倍调用"，而是"**每个 Agent 都要带一份上下文**" —— 所以控制的重点在**上下文大小**，不在调用次数。」
:::

## 8. 【挂点】你的三类子 Agent 怎么讲成体系

:::card 直接可用的对照
| 编排概念 | 你的实现 |
|---|---|
| 拓扑 | **共享黑板 + 依赖图调度**（非固定主管） |
| 通信 | 共享**证据状态**（结构化，不是全部上下文） |
| 角色分工 | 补全（最大化覆盖率）/ 反驳（最大化对抗性）/ 冲突消解（最小化未消解冲突） |
| 聚合 | 冲突消解 Agent 做**仲裁**（先规则后模型） |
| 成本控制 | 预算 + 覆盖率/边际收益触发终止 |
| 防打转 | 动作去重 + 状态单调性 |

**一句话定位（背下来）**：
> 「我的多 Agent 不是"为了多 Agent 而多 Agent"，而是因为**三类证据需求的目标函数不一样**。协调方式是共享黑板 + 依赖图，共享的是**结构化状态**而不是上下文 —— 这样既协作又隔离。」
:::

## 9. 十个追问预答

:::qa 为什么不用一个 Agent 搞定
三个理由：**上下文隔离**（找反证的上下文会干扰找缺失）、**目标函数不同**（找支撑 vs 找死磕，混在一起会意图漂移）、**可评测**（分开才能消融）。
**代价**：token 成本、协调开销、错误传播。
:::

:::qa 多 Agent 一定比单 Agent 好吗
不。任务线性、上下文装得下、目标一致时，**单 Agent 更可靠更便宜**。多 Agent 只在"需要不同视角/上下文必须隔离/需要交叉验证"时划算。
:::

:::qa 多 Agent 的主要失败模式
死锁/循环委派、责任扩散、错误级联、token 爆炸、**虚假共识**（同一模型同一偏差）、无法收敛。
:::

:::qa 共享黑板和消息传递怎么选
共享黑板**易调试、天然一致**（看一份状态就知全局），但要处理写入冲突和状态膨胀；消息传递天然隔离但信息容易丢、链难追。**多数协作型任务用黑板更好**。
:::

:::qa 为什么说"共享黑板要共享状态而不是上下文"
共享全部上下文等于退化成一个大的单 Agent（还多了协调开销）。共享**结构化状态（结论+指针）**才能既协作又隔离、还能省 token。
:::

:::qa 多个 Agent 结论冲突怎么办
优先**规则仲裁**（来源可信度、时间戳、证据数量），规则判不了才让模型裁决。也可以保留冲突呈现给最终输出（像 Memory 里那样，不要静默选一个）。
:::

:::qa 什么是虚假共识，怎么破
多个 Agent 用同一模型、同一批证据，会**一致地错**。破法：制造差异（不同检索策略/不同证据源/不同提示视角），或引入外部验证（测试、检索核验）。
:::

:::qa 多 Agent 的成本怎么控制
控制**上下文大小**（重点）、并发上限、深度上限、预算分摊、早停、按需只给必要状态字段。
:::

:::qa 怎么评测多 Agent 系统
三层次：**端到端任务成功率**、**轨迹级**（步数、工具错误率、成本）、**消融**（去掉某角色掉多少）。只看端到端会掩盖"哪个角色在起效"。
:::

:::qa 【挂点】你的多 Agent 和 AutoGen/LangGraph 搭的有什么区别
「我没用框架，编排层是手写的：三类角色的职责、共享的证据状态、依赖图调度、策略分发、终止条件都是我自己实现的。所以框架要解决的那些坑（状态怎么存、循环怎么停、失败怎么回退、并发怎么共享上下文）我踩过。**真要上框架，我的成本是 API 熟悉度，不是设计能力。**」
:::

## 10. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「多 Agent 比单 Agent 强」 | 「只在需要隔离/多视角/交叉验证时划算；线性任务用 workflow 更好」 |
| 「我用 AutoGen 搭了几个 Agent」 | 「编排层是我手写的：共享状态 + 依赖图调度 + 策略分发」（除非真用过） |
| 「共享上下文让它们协作」 | 「共享**结构化状态**，不是共享全部上下文 —— 否则退化成单 Agent」 |
| 「投票就能聚合」 | 「同质 Agent 会虚假共识；要制造差异 + 规则仲裁」 |
| 「多 Agent 就是并行加速」 | 「并行只是副产物，主要价值是上下文隔离与目标分工」 |

## 11. 自测（6 题）

:::qa 多 Agent 解决单 Agent 的哪三件事
上下文隔离、目标函数不同（分工）、可评测与并行。
:::

:::qa 什么情况下不该用多 Agent
任务线性步骤固定、上下文装得下、子任务目标一致、成本延迟敏感。
:::

:::qa 四种拓扑
Supervisor（默认）、Handoff（路由）、Group chat（多视角）、Hierarchical（大任务）。
:::

:::qa 共享黑板与消息传递的核心区别
黑板共享一份状态（易调试、需处理冲突）；消息传递天然隔离（信息易丢失、链难追）。
:::

:::qa 六种失败模式里最隐蔽的是哪个
**虚假共识** —— 同模型同证据会一致地错，看起来"大家都同意"。
:::

:::qa 你的项目对应哪种编排
共享黑板 + 依赖图调度（非固定主管），共享结构化证据状态；冲突由消解 Agent 按"先规则后模型"仲裁。
:::
