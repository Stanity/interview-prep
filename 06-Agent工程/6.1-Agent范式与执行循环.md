# 6.1 Agent 范式与执行循环（ReAct / Plan-Execute / Reflexion / ToT）

> **为什么这篇是 Agent 岗的第一篇**：面试官问"你了解哪些 Agent 范式"时，他想听的不是名字，而是**每个范式修了上一个的什么问题**。
> **配套**：`09-2026新高频/9.0` 的 §2 讲"Loop Engineering（循环怎么工程化）"，这篇讲"为什么是这些范式"。
> **标注**：`★★★`

---

## 1. 30 秒口述版

:::card 30 秒版
「Agent 范式的演进可以按"**上一个范式失败在哪**"来记：

**CoT** 让模型先写推理再给答案，解决了"直接答容易跳步"，但它**不能和外部世界交互** —— 全是脑补。
**ReAct** 把推理和动作交替起来：`Thought → Action → Observation` 循环，解决了"需要查证"，但它是**贪心**的，没有全局规划。
**Plan-and-Execute** 先出完整计划再执行，解决了"没有全局观"，但计划一旦错了就一路错（需要 replan）。
**Reflexion** 在执行后加一步自我反思（把失败教训写下来供下次参考），解决了"同一个坑反复踩"。
**ToT / GoT** 在每一步做**多分支探索 + 评估回溯**，解决了"单一路径无法回退"，代价是算力爆炸。

工程上最重要的是**执行循环的六要素**：状态、动作空间、观察解析、控制策略、终止判定、预算。面试如果让我设计一个 loop，我会先把这六件事定清楚再写代码。」
:::

## 2. 五个范式的演进（表 + 每条的失败点）

| 范式 | 核心做法 | 修了上一个什么 | 它自己的新问题 |
|---|---|---|---|
| **CoT** | 先写推理链再给答案 | 直接答容易跳步、不可解释 | **不能与外部交互**（纯脑补，无法查证） |
| **ReAct** | `Thought → Action → Observation` 交替 | 无法查证、无法用工具 | **贪心**：没有全局规划，容易在局部打转 |
| **Plan-and-Execute** | 先出完整计划，再逐步执行 | 缺少全局视角 | 计划错误会**一路错**，需要 replan 机制 |
| **Reflexion** | 执行后自我反思，把教训存入记忆 | 同一类错误反复犯 | 反思质量依赖模型；可能**过度自我怀疑** |
| **ToT / GoT** | 每步展开多个分支、评估后保留最优、可回溯 | 单路径无法回退 | **算力爆炸**（分支数 × 深度） |

:::card 一句话串起来
> 「**CoT 学会想，ReAct 学会查，Plan 学会先规划，Reflexion 学会复盘，ToT 学会回溯。** 每一层都是用更多算力换更强的决策能力。」
:::

## 3. 执行循环的六要素（面试让你"设计一个 loop"就按这个答）

:::card 六个必须定清楚的东西
| 要素 | 要回答的问题 | 工程要点 |
|---|---|---|
| **① 状态 State** | 当前知道什么、做到哪了 | 显式结构（不要靠 prompt 里的自然语言记忆） |
| **② 动作空间 Action** | 能做什么 | 工具 schema + 权限分级；工具多时要**动态暴露子集** |
| **③ 观察解析 Observation** | 工具返回怎么进上下文 | 截断、结构化、**错误归一化**（不要把原始异常丢给模型） |
| **④ 控制策略 Control** | 下一步做什么 | 规则 + 模型混合（不要 100% 交给模型） |
| **⑤ 终止判定 Termination** | 什么时候停 | **四类终止**（见 §4） |
| **⑥ 预算 Budget** | 花多少 | token / 步数 / 时间 / 成本，四维独立 |
:::

:::card 白板版伪代码（面试可直接写）
```python
state = init_state(task)
budget = Budget(tokens=100_000, steps=30, wall=600)

while not budget.exhausted():
    obs = build_context(state)                 # ③④ 组装上下文
    action = policy(obs, tools=state.tools)    # ④ 决策（规则 + LLM）

    if is_terminal(state, action):             # ⑤ 终止判定（四类）
        break

    if is_repeated(action, state.history):     # 防打转
        state.force_change_strategy()
        continue

    result = execute(action)                   # ② 执行（沙箱 + 超时 + 重试）
    state = update(state, action, normalize(result))
    budget.consume(action)

    if no_progress(state, k=3):                # 无进展检测
        break
return finalize(state)
```
:::

## 4. 四类终止条件（必须能背）

:::card 四类
1. **任务完成（可验证）**：最有价值的一类 —— 有测试、有 schema 校验、有断言
2. **预算耗尽**：token/步数/墙钟/成本任一触顶 → 停并**返回部分结果 + 说明为什么停**
3. **无进展**：动作重复 / 状态不变 / 观察相似（见 §5）
4. **外部中断**：用户取消、审批拒绝、上游失败

**面试话术**：「**只靠模型自己说"完成了"是最危险的** —— 它永远会说完成了。所以优先设计**可验证的完成条件**：能跑测试就跑测试，能校验 schema 就校验，实在不行才退回"模型自评 + 人工确认"。」
:::

## 5. 六种失败模式（面试问"Agent 会怎么坏"）

:::card 现象 + 触发条件 + 对策
| 失败模式 | 现象 | 触发条件 | 对策 |
|---|---|---|---|
| **振荡（oscillation）** | A→B→A→B 来回 | 两个动作互相"撤销" | 动作去重 + 状态单调性 |
| **过早终止** | 还没做完就说完成 | 终止判定太依赖模型自评 | 可验证的完成条件 |
| **上下文膨胀** | 越跑越慢、越跑越贵 | 全量历史都塞进 context | 摘要/压缩 + 只留结论 |
| **动作空间漂移** | 调了不存在的工具/参数 | 工具太多、schema 模糊 | 工具分组 + 动态暴露 + 参数校验 |
| **观察解析失败** | 工具报错但模型当成成功 | 错误没有归一化 | 统一错误格式 + 明确标记失败 |
| **无限重试** | 同一个失败动作反复重试 | 没有重试上限 | 指数退避 + 上限 + 换策略 |
:::

## 6. Plan-and-Execute 的两个关键设计（面试常追问）

:::card ① 什么时候 replan
三个触发点：
- **执行失败**（某步持续失败）→ 局部重规划
- **观察到与计划假设矛盾**（查到的信息和预期不符）→ 全局重规划
- **预算过半但进度落后** → 降级计划（做最重要的子目标）

**反模式**：每步都 replan → 退化成 ReAct，还多花了规划的 token。
:::

:::card ② 计划用什么形式
| 形式 | 优点 | 缺点 |
|---|---|---|
| 自然语言步骤列表 | 简单、模型友好 | 难以检查依赖 |
| **DAG（依赖图）** | 能表达并行与依赖、可调度 | 需要模型结构化输出 |
| 状态机 | 可控、可验证 | 编写成本高 |

**加分句**：「我倾向用**依赖图**而不是线性列表 —— 因为真实任务里子目标之间常有依赖关系（必须先查 A 才知道查什么 B），线性列表表达不了这个。」（这正好对上你 2.3 里的事实依赖图）
:::

## 7. 十个追问预答

:::qa ReAct 和 CoT 的本质区别
CoT 只在**内部推理**，不与外界交互；ReAct 把推理与**动作+观察**交替，能查证。所以 CoT 是"想"，ReAct 是"想+做+看"。
:::

:::qa ReAct 的主要缺陷是什么
**贪心、无全局规划**：每步只看当前观察决定下一步，容易在局部打转、做重复动作、或在长任务里迷路。所以后来有 Plan-and-Execute。
:::

:::qa Plan-and-Execute 什么时候该 replan
三个触发：执行失败、观察到与计划假设矛盾、预算过半但进度落后。**不要每步都 replan**（那等于退化成 ReAct 还多花规划成本）。
:::

:::qa Reflexion 怎么落地？风险是什么
执行结束后让模型总结"哪里失败、下次注意什么"，写入记忆，下次任务作为上下文注入。风险是反思质量依赖模型、可能产生错误教训（负迁移），所以要有选择地保留。
:::

:::qa ToT 为什么在工程上很少直接用
分支数 × 深度的组合爆炸，每步都要多次模型调用和评估。所以实践里更多用"**小规模并行采样 + 打分选择**"（如 best-of-n）来近似它的收益。
:::

:::qa 【挂点】你项目里的循环和这些范式的关系
我的"规划—执行—评估"循环 ≈ ReAct 的变体（多角色 + 状态驱动），但我有**显式证据状态**和**依赖图调度**，所以更接近 **Plan-and-Execute 的图版本** + 状态驱动的 replan。
:::

:::qa 如果让你现在写一个 Agent loop，第一步做什么
先定**六要素**（状态/动作/观察/控制/终止/预算），尤其是**终止条件** —— 因为"能停下来"比"跑得好"更基础。然后写最小可跑版本，用 8 条固定任务做回归。
:::

:::qa 怎么判断一个 loop 是"真的在工作"而不是在空转
三个信号：**状态单调改善**（覆盖率/完成度上升）、**动作不重复**、**每步的 token 成本可解释**。如果状态不变但一直在调工具，就是空转。
:::

:::qa Agent 的"自我反思"会不会让效果变差
会。风险有两个：① 反思出**错误的教训**（把偶然失败归因为错误原因）；② 过度自我怀疑导致不敢动作。所以反思要**限定作用域**（只对同类任务生效）并且**可撤销**。
:::

:::qa 【挂点】你只有任务内循环，没有长程执行，怎么答
照实说：「我做的是单轮复杂任务内的规划—执行—评估循环，不涉及跨会话的长期记忆累积和断点恢复。这是我和生产级 harness 的差距，但**循环的控制结构（状态、终止、预算、防打转）我是手写过的**。」
:::

## 8. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「ReAct 就是让模型循环调用工具」 | 「ReAct 是 **Thought-Action-Observation 交替**，关键在把推理和查证耦合起来」 |
| 「Plan-and-Execute 比 ReAct 好」 | 「它有全局观但计划错了会一路错，需要 replan；复杂动态任务反而 ReAct 更灵活」 |
| 「让模型自己判断做完就行」 | 「**优先可验证的完成条件**，模型自评只能兜底」 |
| 「ToT 效果最好所以用它」 | 「ToT 算力爆炸，工程上用 best-of-n 近似」 |
| 「我有长程 Agent 经验」 | 「我做的是任务内循环；跨会话长程执行我没做过」 |

## 9. 自测（6 题）

:::qa 五个范式各修了上一个的什么问题
CoT（不可解释/跳步）→ ReAct（不能交互）→ Plan-Execute（无全局观）→ Reflexion（重复犯错）→ ToT（单路径不可回溯）。
:::

:::qa 执行循环的六要素
状态、动作空间、观察解析、控制策略、终止判定、预算。
:::

:::qa 四类终止条件
任务完成（可验证）、预算耗尽、无进展、外部中断。
:::

:::qa 六种失败模式里最隐蔽的是哪个
上下文膨胀（越跑越慢越贵）和振荡（A→B→A）—— 两者都不会报错，只是慢慢变差。
:::

:::qa Plan-and-Execute 该在什么时候 replan
执行失败、观察与假设矛盾、预算过半但进度落后。不能每步都 replan。
:::

:::qa 为什么"计划用依赖图而不是线性列表"
真实任务里子目标常有依赖（先查 A 才知道查 B），线性列表表达不了并行与依赖，无法调度也无法剪枝。
:::
