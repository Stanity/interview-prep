# 6.6 Agent 评测与可观测（"怎么评测一个 Agent"标准答案）

> **为什么这篇权重最高**：Agent 岗 JD 几乎都写"Agent 评测"（百度明确写成功率/延迟/成本/体验；有的还写 evaluator、失败模式、case replay、benchmark）。
> **这篇的核心交付**：给你一段**2–3 分钟的标准答案**，被问"怎么评测一个 Agent"时直接讲。
> **你的优势**：你做过完整评测（Macro-F1 / ASR / Retrieval F1 / Complete Success），这块你有实盘经验。
> **标注**：`★★★`

---

## 1. 30 秒口述版

:::card 30 秒版
「评测 Agent 和评测模型最大的区别是：**Agent 有轨迹**。

模型只看"输入→输出对不对"，Agent 还要看"**它是怎么做到的**" —— 用了多少步、选对工具没有、参数对不对、有没有绕远路、成本多少。所以同一个成功率背后可能是完全不同的质量。

我的评测框架分三层：
**结果层**（任务成功率、pass^k）、**轨迹层**（工具选择准确率、参数准确率、步数效率、错误恢复率）、**系统层**（延迟、成本、稳定性）。

而且我特别看 **pass^k** 而不是 pass@k —— 因为 Agent 要的是**稳定可靠**，k 次全成功的概率才反映生产可用性。

另外所有评测都必须有 **trace**：没有逐步记录，出了问题根本不知道是模型错还是工具错。」
:::

---

## 2. 标准答案：怎么评测一个 Agent（2–3 分钟版，背下来）

:::card 完整口述稿（按这个顺序讲，逻辑最顺）
**① 先分层，否则说不清**
> 「我分三层：**结果、轨迹、系统**。结果层看任务成不成，轨迹层看它怎么做的，系统层看成本延迟稳不稳。只看结果层会掩盖'蒙对'和'绕远路'。」

**② 结果层**
> 「主指标是**任务成功率**，但我会用 **pass^k**（同一个任务跑 k 次全成功的概率），而不是 pass@k（k 次里成功一次）。因为生产要的是稳定，pass@k 允许偶发成功，会掩盖不稳定性。」

**③ 轨迹层（这是 Agent 特有的）**
> 「我会拆成几项：**工具选择准确率**（选对工具没）、**参数准确率**（参数对不对）、**步数效率**（相对最优步数）、**错误恢复率**（失败后能不能自愈）、**无效动作率**（重复/空转）。这些能从 trace 里自动算。」

**④ 系统层**
> 「**TTFT/端到端延迟、每任务 token 成本、工具调用次数、失败率分布**。因为 Agent 的成本可能差一个数量级，必须盯。」

**⑤ 可靠性**
> 「除了常规任务，我会做**扰动测试**：换个说法、加噪声、让工具偶尔超时 —— 看成功率掉多少。Agent 在扰动下比模型脆弱得多。」

**⑥ 最后一句定调**
> 「**关键是所有评测都要有 trace 支撑** —— 没有逐步记录，你只能知道'失败了'，不知道'哪一步失败的'。所以我会先做可观测，再做评测。」

**这段话的价值**：结构清晰（三层 + 可靠性 + trace），而且每一层都点出"为什么"，不是罗列指标。
:::

## 3. 十层指标表（面试要细节时用）

:::card 从结果到鲁棒
| # | 层级 | 指标 | 怎么算 |
|---|---|---|---|
| 1 | **最终结果** | 任务成功率 / **pass^k** | 人工或程序判定任务是否完成 |
| 2 | **规划** | 计划正确率 | 计划是否覆盖必要子目标（人工/LLM 判定） |
| 3 | **工具选择** | Tool Selection Accuracy | 该用的工具用了吗、没用的调了吗 |
| 4 | **参数** | 参数准确率 | 关键字段（如 query、id）是否正确 |
| 5 | **检索** | Recall@k / nDCG | 见 5.5 |
| 6 | **轨迹** | 步数效率、无效动作率 | 实际步数 / 最优步数；重复动作占比 |
| 7 | **可靠性** | 失败率、**错误恢复率** | 失败中能自愈的比例 |
| 8 | **成本** | 每任务 token / 工具调用数 | 直接统计 |
| 9 | **效率** | TTFT、端到端延迟 | 埋点 |
| 10 | **鲁棒性** | 扰动下的成功率保持率 | 改写/加噪/工具超时后重测 |
:::

## 4. 结果级 vs 轨迹级（核心区分）

:::card 为什么必须两个都看
| | 结果级 | 轨迹级 |
|---|---|---|
| 回答什么 | 任务成了吗 | **怎么成的** |
| 优点 | 直观、对齐用户价值 | 能定位问题、能被自动计算 |
| 缺点 | **掩盖过程问题**（蒙对/绕远路/成本爆炸都看不出来） | 本身不代表用户价值 |
| 典型指标 | 成功率、pass^k | 工具准确率、步数、恢复率 |

**一句话**：「**结果级用来验收，轨迹级用来优化。**」
:::

:::card 一个真实的反例（讲出来很有说服力）
两个 Agent 任务成功率都是 70%，但：
- Agent A：平均 5 步，token 2k，工具错误率 5%
- Agent B：平均 18 步，token 12k，工具错误率 40%，靠"多试几次"蒙对

**如果只看成功率，两者等价；但 B 在生产里会亏死、而且用户等不了。** 这就是为什么要看轨迹。
:::

## 5. 基准全景（知道各自测什么就够）

:::card 六个主流基准
| 基准 | 测什么 | 特点 |
|---|---|---|
| **τ-bench** | 多轮**工具对话**（如客服场景），要遵守业务规则 + 调 API | 用 **pass^k** 衡量稳定性；贴近生产 |
| **BFCL**（Berkeley Function Calling Leaderboard） | **函数调用**能力：选对函数、参数正确、并行调用 | 专门测工具调用，分层很细 |
| **SWE-bench** | 真实 GitHub issue 修复（跑单测判定） | 结果可验证，最难也最硬 |
| **WebArena** | 浏览器里的多步任务（购物、论坛操作） | 环境真实但慢、有快照漂移问题 |
| **GAIA** | 通用助理任务（需要多工具组合） | 难度分层（1–3 级），人类很简单但 Agent 很难 |
| **AgentBench** | 多环境综合（OS/DB/知识图谱/卡牌游戏） | 覆盖面广，但单任务深度有限 |
:::

**面试话术**：「这些基准测的东西不同：**BFCL 测调用准确性、τ-bench 测多轮稳定性、SWE-bench 测真实工程能力、GAIA 测组合工具解决开放问题**。选基准要看你想证明什么能力，不能只报一个总分。」
:::

## 6. pass@k vs pass^k（**高频且容易答错**）

:::card 一句话区分
- **pass@k**：跑 k 次，**至少成功一次**的概率 → 衡量"能力上限"
- **pass^k**：跑 k 次，**全部成功**的概率 → 衡量"可靠性"

**为什么 Agent 要看 pass^k**：生产里用户不会给你 k 次机会。一个"50% 成功率"的 Agent，pass^5 只有约 3%（如果独立）。
:::

:::card 一个可以现场算的例子
假设单次成功率 `p = 0.7`，k = 3：
- `pass@3 = 1 − (1−0.7)³ = 1 − 0.027 = 97.3%`（看起来很好）
- `pass^3 = 0.7³ = 34.3%`（真实可靠性）

**这个对比在面试里非常有冲击力** —— 同一个 Agent，两种指标差 60 多个点。
:::

## 7. LLM-as-judge 在 Agent 场景的特殊问题

:::card 比评模型时更麻烦的三点
1. **轨迹太长**：judge 看不完完整轨迹 → 容易只看结果不看过程
2. **中间步骤难判**：某一步"选了次优工具但最终成功"，judge 往往判对
3. **价格与位置偏差**：长轨迹里靠前/靠后的动作权重不同

**对策**：
- **分步判**（每步单独问"这一步合理吗"）而不是整体判
- **规则优先**：能从 trace 算的（步数、工具名、参数）就不要用 judge
- **人工锚点校准**：标注 100–200 条，算与 judge 的一致性

**一句话**：「能用规则算的就别用 LLM judge —— Agent 的很多指标（工具准确率、步数）本来就是确定性的。」
:::

## 8. 可观测性（先有 trace，再谈评测）

:::card trace 里必须记什么
| 字段 | 为什么 |
|---|---|
| **每次模型调用**（输入 token 数、输出、耗时、模型版本） | 定位是模型问题还是逻辑问题 |
| **每次工具调用**（工具名、参数、返回值、耗时、是否成功） | 定位工具层问题 |
| **状态快照**（关键状态字段的变化） | 看"哪一步开始偏离" |
| **成本与预算消耗** | 定位成本爆炸 |
| **决策原因**（为什么选这个动作） | 复盘必需（可以是模型输出的 thought） |

**结构建议**：对齐 **OpenTelemetry 的 GenAI 语义约定**（`gen_ai.*` 属性），这样能直接接现有 APM（如 Langfuse、Phoenix、Jaeger）。
:::

:::card 三个派生能力（有 trace 才能做）
1. **回放（replay）**：拿历史 trace 重新跑，验证修复是否有效
2. **失败样本回流**：线上 badcase 自动进评测集
3. **回归基线**：每次改动跑同一批 case，比成功率/步数/成本
:::

## 9. 线上评测怎么做（面试常问"上线后怎么保证质量"）

:::card 四件事
1. **固定回归集**：覆盖高频 + 历史 badcase（每次发版必跑）
2. **灰度 + AB**：小流量先上，比成功率/延迟/成本
3. **线上抽样人工评**：程序只能测"成没成"，测不了"体验好不好"
4. **监控分布而非均值**：成功率均值不变但**长尾变长**（某些任务突然崩）是常见倒退信号

**加分句**：「我会盯**分布变化**而不是只看均值 —— 比如 P95 步数、拒答率、工具错误率。均值掩盖长尾，而长尾往往才是用户投诉的来源。」
:::

## 11. 八个追问预答

:::qa 怎么评测一个 Agent（简版 60 秒）
三层 + 一个可靠性：结果层（成功率、**pass^k**）、轨迹层（工具准确率、参数准确率、步数效率、错误恢复率）、系统层（延迟、token 成本、工具调用数）、外加扰动下的鲁棒性。**前提是所有评测都要有 trace 支撑。**
:::

:::qa 为什么看 pass^k 不看 pass@k
pass@k 允许"k 次里成功一次"，掩盖不稳定；生产要稳定可靠。例：p=0.7 时 pass@3≈97%，pass^3≈34%。
:::

:::qa 结果级评测的问题是什么
掩盖过程问题：蒙对、绕远路、成本爆炸都看不出来。同样 70% 成功率，5 步 vs 18 步是两个完全不同的系统。
:::

:::qa τ-bench 和 BFCL 测的东西有什么不同
τ-bench 测**多轮工具对话**（遵守业务规则 + 调 API，用 pass^k）；BFCL 测**单轮/并行函数调用**的准确性（选函数、参数、并行）。前者偏系统级，后者偏接口级。
:::

:::qa Agent 场景下 LLM-as-judge 有什么额外问题
轨迹太长（judge 只看结果）、中间步骤难判（次优但成功）、位置偏差。对策：分步判、规则优先、人工锚点校准。
:::

:::qa trace 里必须记什么
模型调用（输入输出/耗时/版本）、工具调用（名/参数/返回/耗时/成功）、状态快照、成本预算、决策原因。建议对齐 OpenTelemetry 的 GenAI 语义约定。
:::

:::qa 上线后怎么持续保证质量
固定回归集（含 badcase）+ 灰度 AB + 线上抽样人工评 + **监控分布（P95 步数/拒答率/工具错误率）而不是只看均值**。
:::

:::qa 你会怎么测一个 Agent 的鲁棒性
扰动测试：改写用户说法、注入噪声/错别字、让工具随机超时或返回空、增加无关上下文。看成功率保持率与恢复率 —— Agent 在扰动下比模型脆弱得多。
:::

## 12. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「评测 Agent 就是看任务成不成」 | 「要分**结果/轨迹/系统**三层，否则掩盖过程和成本问题」 |
| 「pass@k 高就说明效果好」 | 「Agent 要看 **pass^k**（稳定可靠），pass@k 允许偶发成功」 |
| 「用 LLM 当 judge 就行了」 | 「能从 trace 算的指标（工具名/参数/步数）就别用 judge」 |
| 「上线后看成功率就行」 | 「要看**分布**（P95 步数、拒答率、工具错误率），均值会掩盖长尾」 |
| 「我们做了 trace」 | 「trace 要能支撑回放与回归，否则只是日志」 |
