# 6.8 框架横向对比与话术（没用过框架怎么答）

> **这篇解决你最大的一个"❌"**：你的 JD 自查表里 `LangChain / LlamaIndex / AutoGen` 全是 ❌。硬伤不在技术，在**怎么答才不被判定为"没做过系统"**。
> **核心思路**：**把你手写的编排逐项映射到框架的抽象上**，证明"框架要解决的问题我踩过坑"，只是没用过它的 API。
> **标注**：`★★★`（话术部分必背）

---

## 1. 30 秒口述版

:::card 30 秒版
「主流 Agent 框架解决的其实是同一组问题：**怎么把状态、节点、边、工具、记忆串起来，并支持中断恢复和可观测**。它们的差别主要在抽象粒度和调度方式。

- **LangChain**：以 **Chain/Runnable** 为核心，偏"把调用串成管道"，生态最广但对复杂控制流笨重。
- **LangGraph**：以 **共享 State + 节点/条件边 + checkpointer** 为核心，本质是**状态机/图**，最适合有多轮循环、分支、需要中断恢复的场景。
- **AutoGen**：以 **对话式多 Agent** 为核心（Actor 模型 + 群聊），适合"多个角色讨论"。
- **CrewAI**：以 **角色 + 任务** 为核心，声明式、上手快，适合流程相对固定的团队式协作。
- **LlamaIndex**：以 **数据/索引** 为核心（index / query engine / workflow），RAG 生态最完整。

**我的实现和 LangGraph 最像**：共享状态 + 条件分支 + 依赖图调度 —— 只是我是自己写的，不是用它的 API。」
:::

## 2. 框架抽象 ↔ 你的手写实现（**这张表是核心**）

| 框架里的概念 | 它解决什么 | 你的对应实现 |
|---|---|---|
| **State / 共享状态** | 多步之间传数据 | **证据状态**（子目标覆盖、证据池、冲突、预算） |
| **Node（节点）** | 一个处理单元 | 三类子 Agent（补全 / 反驳 / 消解）+ 检索动作 |
| **Edge / 条件边** | 根据状态决定下一步走哪 | **策略层分发**（按覆盖率/冲突/边际收益选动作） |
| **Checkpointer（断点）** | 中断后恢复 | ⚠️ **你没有**（诚实说） |
| **Tool / ToolNode** | 工具注册与调用 | 你的**策略定义 + 代码层校验**（中间实体/关系校验） |
| **Memory** | 长期记忆 | ⚠️ 只有任务内工作记忆 |
| **Tracing（LangSmith）** | 可观测 | ⚠️ 你只有实验结果记录，没有逐步 trace |
| **Human-in-the-loop / interrupt** | 人工介入 | ⚠️ 没有 |

:::card 怎么用这张表（话术逻辑）
1. **先说相同点**（状态、节点、条件边、工具路由）→ 证明"框架的核心抽象我都手写过"
2. **主动说不同点**（checkpointer、trace、human-in-the-loop）→ 证明"我知道自己缺什么"
3. **给出学习成本判断** → 「缺的是 API 熟悉度，不是设计能力」

**为什么主动暴露缺口反而加分**：因为面试官最怕的是"你连自己缺什么都不知道"。
:::

## 3. 五个框架的定位（一句话 + 适用场景）

:::card 逐个
| 框架 | 一句话定位 | 什么时候选它 | 主要问题 |
|---|---|---|---|
| **LangChain** | 大而全的组件库 + 管道抽象（LCEL） | 快速拼装、需要大量现成集成 | 抽象层厚、调试困难、复杂控制流写得别扭 |
| **LangGraph** | **有状态的图/状态机**，支持循环、条件边、checkpoint、中断 | 多轮循环、需要断点恢复、需要人工介入 | 学习曲线比 Chain 陡 |
| **AutoGen** | **对话驱动的多 Agent**（Actor 模型、群聊） | 多角色讨论、代码解释器等 | 群聊成本高、不易控制收敛 |
| **CrewAI** | **角色 + 任务**的声明式团队协作 | 流程相对固定、想快速搭出多角色 | 灵活控制流受限 |
| **LlamaIndex** | 以**索引/数据**为中心（RAG 最强） | RAG/文档问答为主 | Agent 编排能力相对 LangGraph 弱 |
:::

:::card 如果被问"你会选哪个"
按场景答，不要站队：
- **RAG 为主** → LlamaIndex（数据接入与索引最成熟）
- **多轮循环 + 需要断点恢复** → LangGraph
- **多角色讨论、研究原型** → AutoGen
- **流程固定的团队式协作** → CrewAI
- **只是想快速拼个 demo** → LangChain

**加分句**：「框架选型我看三件事：**控制流的复杂度、是否需要断点/人工介入、以及可观测生态**。像我们这种需要多轮循环和状态调度的，LangGraph 的抽象最贴合；纯 RAG 就用 LlamaIndex。」
:::

## 4. 三套诚实话术（按被问的深度选）

:::card ① 完全没用过（最常用）
> 「LangChain / LangGraph / AutoGen 我**没有实际用过**。
> 但我的编排层是手写的：**共享状态、角色分工、条件分发、依赖图调度、终止条件**都是我自己实现的 —— 也就是 LangGraph 里 State + 条件边 + 子图那套东西。
> 所以框架要解决的坑（状态怎么存、循环怎么停、失败怎么回退、并发怎么共享上下文）我踩过。**真要上框架，我的成本是 API 熟悉度，不是设计能力。**」
:::

:::card ② 看过文档但没写过项目
> 「我看过文档，理解它的抽象（State / Node / 条件边 / checkpointer），也照着跑过 toy example，但没有在真实项目里用过。
> 我自己的项目是手写编排，所以对"状态管理"和"循环控制"有实感。**如果给我一周，我大概能把现有实现迁移过去。**」
:::

:::card ③ 想说"我做过等效的事"（最有力）
> 「我做的是**与框架等价的手写实现**：三类子 Agent 共享一份证据状态（= State），由策略层根据覆盖率/冲突决定下一步（= 条件边），用事实依赖图决定执行顺序（= 子图调度）。
> 我也清楚它**缺什么**：没有 checkpointer 做断点恢复，没有逐步 trace，没有 human-in-the-loop。**这三块是框架能立刻补上的，也是我想学的部分。**」
:::

:::card ❌ 绝对不要说的三句
- ❌「我很熟悉 LangChain」（一问细节就穿）
- ❌「框架只是封装，我自己写更灵活」（显得轻视工程，且回避问题）
- ❌「没用过也没关系，原理都一样」（太傲慢，且不承认工程价值）
:::

## 5. 六个反向提问（面试官问"你会用框架吗"之后可以反问）

:::card 用来把话题引到你强的地方
1. 「团队现在是用现成框架还是自研 harness？如果是自研，主要解决了什么问题？」
2. 「如果用 LangGraph，你们怎么处理 checkpoint —— 存全量消息还是只存关键状态？」
3. 「多 Agent 场景下你们的上下文隔离是怎么做的？是共享状态还是传消息？」
4. 「工具调用这块，你们有做 schema 治理或者动态暴露吗？」
5. 「trace 用的是 LangSmith 这类托管服务，还是自建接 APM？」
6. 「如果让我入职，你希望我前三个月先把现有 harness 摸熟，还是直接接一个新模块？」
:::

**这些问题的作用**：既显得你懂，又把面试官从"你会不会用 X"引导到"这活怎么干"。

## 6. 十个追问预答

:::qa LangChain 和 LangGraph 的关系
LangChain 是组件库 + 管道抽象（LCEL），LangGraph 是它生态里专门做**有状态图/状态机**的库。复杂控制流（循环、条件分支、断点恢复）用 LangGraph 更合适。
:::

:::qa LangGraph 的核心抽象是什么
**共享 State + 节点（处理单元）+ 条件边（按状态路由）+ checkpointer（断点恢复）+ interrupt（人工介入）**。本质是把 Agent 循环建模成一张状态机图。
:::

:::qa AutoGen 的核心是什么
**对话驱动的多 Agent**：Agent 之间用消息对话，支持群聊、代码执行器。优点是贴近"多角色讨论"，缺点是成本高、收敛难控。
:::

:::qa CrewAI 适合什么
**角色 + 任务**的声明式编排，上手快，适合流程相对固定的团队式协作（如"调研员→写手→审校"）。灵活控制流不如 LangGraph。
:::

:::qa LlamaIndex 的强项
**数据/索引侧**：各种文档加载器、索引结构、query engine、检索策略最完整，做 RAG 最省事。Agent 编排能力弱于 LangGraph。
:::

:::qa 【挂点】你手写的编排对应框架里的什么
State=证据状态，Node=三类子 Agent，条件边=策略层分发，子图=事实依赖图调度，Tool 校验=代码层的路径校验。**缺 checkpointer / trace / human-in-the-loop。**
:::

:::qa 为什么不用 LangChain 而自己写
（如果被这么问）：「我的场景是"状态驱动的多轮检索"，控制流不是线性管道而是**依赖图 + 状态分支**。当时手写更直接，也方便做消融（要能精确控制每个角色和行为）。**但如果现在重做，我会考虑 LangGraph** —— 它的 State + 条件边正好对上我的结构。」
:::

:::qa 你觉得自己能多快上手一个框架
给一个有依据的估计：「核心抽象我都实现过，主要成本在 API 与生态（回调、tracing、部署）。**我估计一周能做出一版可跑的迁移，一个月能接手现有代码。**」
:::

:::qa 框架会不会限制你的实现
会，尤其**要精细控制的时候**：框架的抽象层可能屏蔽掉你想调的细节（比如自定义路由、精确的上下文裁剪）。所以我的判断是：**原型用框架，追求极致控制时必要时下沉**。
:::

:::qa 面试官说"我们这里不用框架，全自研"
那正好是你的优势区：「那和我的经验比较接近 —— 我的编排是手写的，所以我对状态管理、循环控制、终止条件这些"框架内部要处理的问题"有实感。」
:::

## 8. 自测（6 题）

:::qa 五个框架各一句话定位
LangChain（组件库+管道）、LangGraph（有状态图/状态机+checkpoint）、AutoGen（对话式多 Agent）、CrewAI（角色+任务声明式）、LlamaIndex（数据/索引最强）。
:::

:::qa LangGraph 的五个核心抽象
State、Node、条件边、checkpointer、interrupt。
:::

:::qa 你的实现对应 LangGraph 的哪些概念，缺哪些
有：State（证据状态）、Node（三类子 Agent）、条件边（策略分发）、子图（依赖图）。缺：checkpointer、trace、human-in-the-loop。
:::

:::qa 「完全没用过框架」的三句话话术
① 承认没用过；② 说明自己手写过哪些等价抽象；③ 主动说清缺什么 + 学习成本判断（API 熟悉度而非设计能力）。
:::

:::qa 框架选型看哪三件事
控制流复杂度、是否需要断点/人工介入、可观测生态。
:::

:::qa 为什么主动说框架能补上你缺的 checkpointer 反而加分
因为它证明你**知道自己缺什么**，而不是以为"自研已经完美"——后者才是面试官最担心的。
:::
