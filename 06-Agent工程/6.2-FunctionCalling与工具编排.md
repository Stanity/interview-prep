# 6.2 Function Calling 与工具编排（schema 设计、错误处理、工具路由）

> **为什么这篇是 Agent 岗的核心**：工具调用是 Agent 的"手"，而它的可靠性**90% 取决于 schema 和错误处理设计**，不是模型。
> **你的处境**：你**没有用过模型原生的 function calling 接口**，但做过"检索策略的动态选择与分发" —— 这篇会给你**等价的映射话术**。
> **标注**：`★★★`；MCP 协议见 6.3

---

## 1. 30 秒口述版

:::card 30 秒版
「Function Calling 的完整链路是：**下发工具定义 → 模型返回 tool_call（名字 + JSON 参数）→ 本地执行 → 把结果作为 tool_result 回填 → 模型继续生成**。

关键在于：**模型不执行任何东西，它只输出"我想调用谁、参数是什么"** —— 真正的执行、鉴权、校验都在你的代码里。所以工具调用的可靠性主要取决于三件事：

**① schema 写得好不好**：名字要见名知意，描述要写清"什么时候用、什么时候别用"，参数要有类型、枚举、必填约束。**描述就是 prompt**，含糊的描述直接导致选错工具。
**② 错误怎么回传**：工具报错时不要把原始异常丢给模型，要归一化成"失败了，原因是 X，你可以试试 Y"。
**③ 参数幻觉怎么防**：用 schema 校验 + 报错回传 + 必要时用**约束解码**保证 JSON 合法。

我没用过 OpenAI 原生接口，但我实现过等效的**工具路由**：根据任务状态在多个检索动作之间做动态选择和分发 —— 那就是手写的 tool router。」
:::

## 2. 完整链路（必须能画出四步）

```
① 请求：tools = [{name, description, parameters(JSON Schema)}]  +  用户消息
                    ↓
② 模型返回：tool_calls = [{id, name, arguments(JSON 字符串)}]     ← 模型不执行，只"点菜"
                    ↓
③ 本地执行：参数校验 → 权限检查 → 真正调用 → 拿到结果（或错误）
                    ↓
④ 回填：把 {tool_call_id, content} 作为 tool 角色的消息追加，再请求模型
                    ↓
⑤ 模型基于结果继续生成（可能继续调用，也可能给出最终答复）
```

:::card 三个容易忽略的细节
1. **`tool_call_id` 必须回填**：并行调用时模型靠 id 对应结果，错了就串结果
2. **参数是字符串**：`arguments` 常以 JSON **字符串**返回，需要自己 `json.loads`（可能失败 → 要有容错）
3. **可以并行**：模型一次返回多个 tool_call → 本地并发执行 → 一次性回填多个 tool_result
:::

## 3. JSON Schema 设计（可靠性第一杠杆）

:::card 六个要点
| 要点 | 反例 | 正例 |
|---|---|---|
| **名字动宾清晰** | `search` | `search_documents_by_keyword` |
| **描述写"何时用/何时不用"** | "搜索文档" | "按关键词检索内部知识库。当用户问事实性问题且需要引用来源时使用；**不要**用于闲聊或需要实时股价的场景" |
| **参数给类型和枚举** | `type: string` | `type: string, enum: ["title", "full_text"]` |
| **标明必填** | 全可选 | `required: ["query"]` |
| **给默认值/边界** | 无约束 | `top_k: {type: integer, default: 5, minimum: 1, maximum: 20}` |
| **嵌套要克制** | 三层嵌套对象 | 扁平化，或拆成多个工具 |
:::

:::card 为什么"描述"这么重要（面试高频）
模型**只能靠 description 判断该不该调、调哪个**。你写"搜索文档"，它不知道和另一个"查数据库"的区别；你写清"什么时候用/不用"，等于**在提示词层面做路由**。

**一句话**：「**工具描述是最被低估的 prompt。** 我调工具失败率的第一优化手段不是换模型，而是重写描述。」
:::

## 4. 错误处理（这块最能体现工程成熟度）

:::card 五种错误 + 对策
| 错误类型 | 表现 | 对策 |
|---|---|---|
| **参数非法** | 缺字段、类型错、枚举外 | schema 校验 → **把校验错误原文回传给模型让它自己改**（这是最有效的自愈手段） |
| **工具名幻觉** | 调了不存在的工具 | 严格白名单校验 → 回传"可用工具是 X/Y/Z" |
| **业务失败** | 查不到、无权限 | 归一化成结构化错误（`{ok:false, reason, suggestion}`） |
| **超时 / 限流** | 网络或下游问题 | 指数退避重试 + 上限；超限后降级（换工具/告知用户） |
| **副作用失败** | 写操作部分成功 | **幂等键** + 补偿/回滚 |
:::

:::card 一个高价值技巧：把错误当成"一种观察"
不要把异常抛给上层的 try/except 就完事，而是**归一化成模型能理解的信息**：
```
❌ 原始异常：KeyError: 'user_id'
✅ 归一化后：{"ok": false, "error": "missing_parameter", "detail": "缺少 user_id",
             "hint": "请先调用 get_current_user 获取 user_id"}
```
**这样模型有机会自我修复**，而不是整个流程崩掉。这是"Agent 能自愈"的关键。
:::

## 5. 权限分级与副作用控制（安全底线）

:::card 三级
| 级别 | 例子 | 策略 |
|---|---|---|
| **只读** | 搜索、查询 | 直接执行，限流即可 |
| **可逆写** | 创建草稿、加标签 | 执行 + 审计日志 |
| **不可逆 / 高危** | 删除、转账、发邮件、执行任意代码 | **必须人工确认** + 沙箱 + 额度限制 |

**面试话术**：「我的原则是**按副作用分级授权**：只读的放开，可逆写的审计，不可逆的一律人工确认。这条比"模型多聪明"重要得多 —— 因为模型一定会犯错的。」
:::

## 6. 工具太多怎么办（真实系统的必然问题）

:::card 四种策略
| 策略 | 做法 | 适用 |
|---|---|---|
| **分组 + 动态暴露** | 按场景只暴露 5–10 个相关工具（先做意图分类） | 工具 >20 个时**必做** |
| **层级化** | 先给"工具类别"，选定后展开该类工具 | 工具成百上千 |
| **路由到子 Agent** | 主 Agent 只负责分派，子 Agent 各自持有自己的工具集 | 多领域（客服/运维/研发） |
| **工具检索（tool RAG）** | 用 embedding 检索相关工具描述 | 超大规模工具库 |

**为什么必须做**：工具越多，**schema 占的上下文越多**、**选错的概率越大**。实测工具数从 10 涨到 50，准确率明显下降。

**一句话**：「工具编排的核心不是"能不能调"，而是"**在正确的时机只让模型看到一部分工具**"。」
:::

## 7. 【挂点】你的"策略分发"怎么映射成 tool router

:::card 这个映射能救你的面试
| Function Calling 概念 | 你的对应实现 |
|---|---|
| 工具定义（name + description + schema） | 你的**检索策略定义**（直接检索 / 查询改写 / 对抗检索 / 冲突消解），每个策略有自己的触发条件 |
| 模型选择工具 | 你的**状态驱动分发**（覆盖率低 → 改写；冲突 → 消解；置信度低 → 对抗检索） |
| 参数校验 | 你的 query 生成 + 校验（中间实体与关系要在代码层校验） |
| 错误回填 | 你的"检索无结果 → 换策略"逻辑 |
| 并行调用 | 你的子 Agent 并行检索 |

**诚实话术（背下来）**：
> 「我没用过模型原生的 function calling 接口 —— 我用的是**规则 + 状态驱动的工具路由**：在多个检索动作之间根据证据状态做选择和分发，参数和路径在代码层校验。
> 如果换成原生接口，我的实现相当于把"路由决策"从规则换成模型输出 `tool_call`，其余（校验、执行、错误回填、并行）完全一样。**所以缺的是接口熟悉度，不是设计能力。**」
:::

## 8. 十个追问预答

:::qa 模型为什么会调错工具
四个原因：① **描述含糊**（和别的工具难以区分）；② **工具太多**（选择空间大）；③ **参数 schema 不清**（不知道要传什么）；④ **上下文里没有足够信息**（不知道该调哪个）。
**对策优先级**：改描述 > 减少暴露数量 > 参数约束 > 换更强模型。
:::

:::qa 怎么减少参数幻觉（编造参数值）
三层：
① **schema 约束**（枚举、必填、类型、范围）；
② **校验 + 报错回传**（把校验错误原文给模型，让它自己改，实测非常有效）；
③ **约束解码**（把 schema 编译成语法，非法 token 置 -inf），从生成层面保证合法。
:::

:::qa 并行工具调用要注意什么
① 结果要按 `tool_call_id` 正确回填；② 只对**无依赖**的调用并行（有依赖的必须串行）；③ 并行时错误处理要独立（一个失败不能拖垮一批）；④ 注意下游限流。
:::

:::qa 工具调用失败了你怎么办
先分类：参数错 → 回传校验错误让模型重试；业务失败 → 归一化成结构化错误 + 提示；超时 → 退避重试/降级；不可重试 → 终止并上报。
**关键原则**：让模型**看到失败原因**，而不是直接抛异常终止。
:::

:::qa 写操作怎么保证安全
三级授权：只读直接执行；可逆写执行 + 审计；不可逆必须人工确认。再加**幂等键**（防重复提交）和沙箱（限制文件/网络/进程）。
:::

:::qa 工具很多（比如 100 个）怎么处理
必须做**动态暴露**：先意图分类/工具检索，只把相关 5–10 个给模型；或层级化（先选类别）；或按领域路由到子 Agent。原因是 schema 占上下文且选择空间大→准确率下降。
:::

:::qa Function Calling 和 MCP 什么关系
**正交的两层**：Function Calling 是"模型怎么选择并表达要调用什么"（模型侧接口）；MCP 是"应用怎么标准化地发现和连接工具与上下文"（工具供应侧协议）。两者常搭配，但解决的问题不同（详见 6.3）。
:::

:::qa 怎么评测工具调用的质量
分层指标：**工具选择准确率**（选对没）、**参数准确率**（参数对不对）、**调用成功率**、**端到端任务成功率**、**平均调用次数**（效率）、**错误恢复率**。只看端到端会掩盖前两层的问题。
:::

:::qa 模型连续调错三次你会怎么改
先看 trace：是描述不清、缺上下文、还是 schema 有问题。**优先改描述和补上下文**，而不是加"重试三次就放弃"的硬规则。如果确实是能力问题，再考虑换模型或加 few-shot 示例。
:::

:::qa 【挂点】你没用过原生 function calling，怎么答
按 §7 的话术：说明你实现的是**规则+状态驱动的工具路由**（等价于 tool router），缺的是接口熟悉度；并主动说出原生接口的四个环节（下发/返回/执行回填/再生成），证明你懂链路。
:::

## 9. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「模型会自己调用工具」 | 「模型只输出 tool_call（名字+参数），**执行在校验/鉴权后的本地代码里**」 |
| 「工具描述随便写就行」 | 「**描述是最被低估的 prompt**，要写清何时用/何时不用」 |
| 「报错直接抛异常就行」 | 「要把错误**归一化成模型能理解的信息**，它才有机会自愈」 |
| 「工具越多模型越强」 | 「工具越多，schema 占上下文越多、选错概率越大，必须动态暴露」 |

## 10. 自测（6 题）

:::qa Function Calling 的四步链路
下发工具定义 → 模型返回 tool_call → 本地校验执行 → 回填 tool_result → 模型继续生成。
:::

:::qa 工具描述应该写什么
不只是"功能是什么"，还要写"**什么时候用、什么时候不用**"，以及和相似工具的区别。
:::

:::qa 减少参数幻觉的三层手段
schema 约束（枚举/必填/类型）→ 校验后把错误原文回传给模型 → 约束解码（非法 token 置 -inf）。
:::

:::qa 为什么要把错误归一化
因为模型只能通过文本理解发生了什么。结构化错误（ok/reason/hint）能让模型自我修复，而原始异常会让流程直接崩。
:::

:::qa 写操作的安全原则
按副作用分级：只读放开、可逆写审计、不可逆人工确认；配合幂等键与沙箱。
:::

:::qa 工具太多时怎么办
动态暴露（意图分类/工具检索只给 5–10 个）、层级化、按领域路由到子 Agent、tool RAG。
:::
