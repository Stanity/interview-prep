# 7.2 系统设计万能模板 + 4 道真题

> **为什么这篇对你最实用**：清昴 JD 的"参与自研 Agent Harness 框架的核心模块设计与开发"几乎就是**系统设计题**；而且 Agent 岗越来越爱问"设计一个 XX Agent"。
> **本文给你两样东西**：① 一个可复用的**答题骨架**；② 四道可直接背诵的**完整设计**。
> **标注**：`★★★`（Agent 岗必准备）

---

## 1. 万能模板（背下来，任何 Agent 系统设计题都能套）

:::card 十段式骨架
```
User → Intent → Planner → Memory → RAG → Tool Router → Tools → Executor → Reflection → Response
```

| 段 | 要回答的问题 | 关键取舍 |
|---|---|---|
| **① 需求澄清** | 用户是谁、任务边界、能不能人工兜底 | 先问清再画，别急着上架构 |
| **② 容量估算** | QPS、token/请求、并发、成本 | 决定模型选型与部署方式 |
| **③ Intent** | 意图识别/路由（简单对话 vs 复杂任务） | 不是所有请求都值得走 Agent |
| **④ Planner** | 拆解子任务、决定并行/串行 | 规则 or 模型；要不要依赖图 |
| **⑤ Memory** | 工作记忆 + 长期记忆（用户偏好/历史） | 写入策略、冲突、遗忘 |
| **⑥ RAG** | 知识检索（混合检索 + rerank） | 上下文预算、引用 |
| **⑦ Tool Router** | 工具选择与参数（schema 治理、动态暴露） | 工具多时的分层/检索 |
| **⑧ Tools/Executor** | 沙箱、超时、重试、幂等、权限 | 副作用分级 |
| **⑨ Reflection** | 结果校验、失败重试、拒答 | 可验证优先于模型自评 |
| **⑩ Response** | 输出格式、引用、置信度、兜底 | 不确定时怎么说 |
:::

:::card 四维权衡（**每段都要点一句，这是拿高分的关键**）
| 维度 | 你要主动说的 |
|---|---|
| **效果** | 检索质量、模型能力、prompt/schema 设计 |
| **延迟** | TTFT / 端到端；哪些步骤能并行、能流式 |
| **成本** | token、工具调用次数、缓存（prompt cache）、降级到小模型 |
| **可靠性** | 重试/降级/熔断、拒答、人工兜底、可回滚 |

**一句话**：「设计 Agent 系统时我按这四维逐项过 —— **因为绝大多数设计题的分差不在'能不能跑通'，而在'你考虑了多少边界'**。」
:::

## 2. 题一：设计一个企业级 RAG 问答服务

:::card ① 澄清三个问题
- **用户范围**：内部员工还是外部客户？（决定权限模型）
- **知识源**：多少个系统、更新频率？（决定索引与增量策略）
- **能接受"不知道"吗**？（决定要不要拒答机制）
:::

:::card ② 架构（七段）
```
文档源(Confluence/PDF/工单)
   → 解析(表格/多栏) → 清洗去重 → 切块(+元数据:doc_id/标题/页码/权限)
   → Embedding → 向量库(带 metadata filter)
                                              ↓
用户 → 意图/改写 → 混合检索(向量+BM25) → RRF融合 → Rerank(top-n)
                                              ↓
                        权限过滤(检索时做!) → 上下文组装(去重/压缩/排序)
                                              ↓
                                   LLM 生成(约束+逐句引用)
                                              ↓
                          引用回填校验 → 置信度判定 → 输出 / 拒答
                                              ↓
                          trace + 反馈 → badcase 回流 → 回归集
```
:::

:::card ③ 四个关键取舍
1. **权限过滤必须在检索时做**（metadata filter），不能 top-k 后再过滤（召回崩 + 泄露风险）
2. **父子块**：小块检索保精度、父块生成保上下文
3. **必须允许拒答**：检索分低或证据冲突时输出"无法确认"，否则一定幻觉
4. **增量更新用 doc_id + 版本**：更新时删旧块插新块，否则新旧矛盾
:::

:::card ④ 失败模式与对策
| 失败 | 对策 |
|---|---|
| 检索不到 | 混合检索 + 查询改写 + 埋点监控 Recall |
| 模型不用证据 | 提示限定 + 逐句引用 + 先抽取后回答 |
| 长文档超上下文 | 父子块 + 压缩 + 分层检索 |
| 索引陈旧 | 版本化 + 增量同步 + 定期全量重建 |
| 成本高 | prompt cache（固定前缀）+ 缓存热点 query + 小模型分流 |
:::

**面试官会追加**：「怎么评估？」→ 用 5.5 的两层评测：检索 Recall@k + 生成 faithfulness；线上看拒答率与引用准确率。

## 3. 题二：设计一个 Agent 执行框架（**对上清昴 JD，重点准备**）

:::card ① 需求澄清
- 谁提供工具？（内部工具 or 第三方 → 决定要不要 MCP 这类协议）
- 允许多大自主权？（决定 L1/L2/L3 分级）
- 是本地执行还是云端多租户？（决定沙箱强度）
:::

:::card ② 架构（八模块，对上 Harness 八组件）
```
                 ┌──────────── Harness ────────────┐
用户/API → 接入层 │ ① 会话与鉴权                      │
                 │ ② Context 装配（system/tools/mem/history）│
                 │ ③ Loop 控制器（状态/预算/终止/防打转）   │
                 │ ④ Tool Registry（schema/权限分级/动态暴露）│
                 │ ⑤ Executor（沙箱:文件/网络/进程/资源）   │
                 │ ⑥ Memory（工作记忆 + 长期记忆）          │
                 │ ⑦ Telemetry（trace/span/成本）          │
                 │ ⑧ 评测与回归（离线集 + 线上抽样）        │
                 └──────────────────────────────────┘
                          ↓
                   模型（可替换）
```
:::

:::card ③ 五个关键设计（每个都要能展开）
**1. Loop 控制器的四类终止**
可验证完成（测试/schema）、预算耗尽、无进展（动作重复/状态不变）、外部中断。**外加动作去重防振荡。**

**2. 工具注册与权限分级**
按副作用分三级：只读（放开）、可逆写（审计）、不可逆（**人工确认 + 额度 + 熔断**）。
schema 要有 name/description（写清何时用/不用）/参数约束；工具多时**动态暴露**（先意图分类只给 5–10 个）。

**3. 执行器与沙箱**
隔离四维度：文件系统（只读 + 白名单目录）、网络（默认禁/白名单）、进程（namespace）、资源（cgroup + 超时）。
本地用 Bubblewrap/Seatbelt，云端不可信用微虚拟机。

**4. Context 装配（最容易被忽略但最影响效果）**
固定前缀（system + tool schema）在前 → 变化内容在后（命中 **prefix cache**）；
记忆与检索结果按预算裁剪；**最关键的证据放结尾附近**（lost in the middle）。

**5. Telemetry**
每次模型调用/工具调用都要结构化记录（耗时、token、成败、参数），对齐 OpenTelemetry GenAI 约定，支持**回放**与失败样本回流。
:::

:::card ④ 失败处理（面试官最爱追问这块）
| 场景 | 处理 |
|---|---|
| 工具超时/失败 | 退避重试（仅幂等操作）→ 降级换工具 → 告知模型（它可能换路径） |
| 模型陷入循环 | 动作哈希去重 + 状态单调性检查 → 强制换策略 → 终止并上报 |
| 任务跑到一半崩了 | **checkpoint**：消息轨迹 + **副作用记录** + 待办进度 + 预算 |
| 高危动作 | 人工确认 + 预览 diff + 可回滚 |
| 下游打爆 | 限流 + 熔断 + 并发上限 |
:::

**加分收尾**：「如果只能先做三件事，我会做 **① tool schema 规范化 ② trace ③ 终止与预算** —— 它们都不需要改模型，但立刻决定成功率和成本可控性。」

## 4. 题三：设计一个 Agent 评测平台

:::card 设计要点
**数据侧**
- 任务集：分层（简单/中等/难）+ 覆盖高频场景 + **历史 badcase 回流**
- 环境：**可重置、可并行、可确定（seeded）** —— 否则结果不可比

**执行侧**
- 每条 case 跑 k 次（算 **pass^k**），并行跑，记录完整 trace
- 支持**批量回归**（发版必跑）与**定向对比**（A/B 两个版本）

**指标侧（三层）**
结果（成功率/pass^k）、轨迹（工具准确率/参数准确率/步数效率/恢复率）、系统（延迟/成本/调用次数）。
**能用规则算的不用 LLM-judge**；必须用 judge 时做分步判 + 人工锚点校准。

**运营侧**
badcase 一键入库、失败原因分类统计、版本对比看板、回归门禁（低于基线不允许发布）。
:::

:::card 一个容易被忽略的设计点
**评测环境必须与生产同构**：工具的超时、限流、返回格式最好一致。否则"评测通过、上线崩"。
**做法**：用同一套工具适配层（mock 只在单测里用，评测走真实或高保真影子环境）。
:::

## 5. 题四：设计一个 RAG 投毒检测系统（**接你的论文**）

:::card 设计思路（把 attack 研究反用）
**核心洞察**：投毒的典型特征是"**对大量不同 query 都高分命中**"+"**答案高度依赖某一篇文档**"。

**检测三层**
| 层 | 手段 |
|---|---|
| **入库前** | 来源可信度分级、内容审核、注入模式过滤、签名/哈希去重 |
| **检索时** | 命中统计（某文档被高频命中 → 告警）、来源多样性检查、来源权重 |
| **生成后** | **可逆干预回归**（你的方法）：破坏支撑关系看答案是否消失；修复看是否恢复 → 判"知识依赖" |

**为什么可逆干预有用**：如果系统"改什么都答得出来"，说明它**不依赖证据**（可能在凭先验瞎答）——这本身就是风险信号。
:::

**面试话术**：「我在论文里做的就是关系级可逆性度量，可以直接搬来做**回归测试**：每加一层防御，测可逆性有没有下降。这样防御的效果是**可量化**的，而不是'感觉安全了'。」

## 6. 场景题速答骨架（四种常见）

| 题目 | 骨架要点（30 秒版） |
|---|---|
| **旅游 Agent** | 意图（机票/酒店/行程）→ 工具（搜索/预订/日历）→ 约束（预算/时间/偏好存 Memory）→ 高危（**支付必须确认**）→ 兜底（无票时给备选而非硬编） |
| **智能客服** | 意图分类 → 知识库 RAG → 工单工具 → **升级人工**的条件（情绪/连续失败/金额阈值）→ 全量审计（合规） |
| **Research Agent** | 计划（拆子问题）→ 多源检索 → **交叉验证**（同一结论需多源）→ 引用 → 报告结构化输出 → 失败时给"未找到"而非编造 |
| **Coding Agent** | 仓库检索 → 改动计划 → **沙箱执行 + 跑测试**（可验证完成）→ diff 预览 → 人工确认 → 回滚机制 |

**共同点**：① 都要有**可验证的完成条件**；② 高危动作都要**确认**；③ 都要能**优雅失败**（拒答/升级人工，而不是硬编）。

## 7. 八个追问预答

:::qa 系统设计题你一般怎么开头
先**澄清需求**（用户、边界、能否人工兜底、规模），再**容量估算**，然后画架构。**直接开始画组件是最容易失分的开头**，因为你不知道约束。
:::

:::qa 怎么保证 Agent 系统"能停下来"
四类终止：可验证完成（测试/schema）、预算耗尽（token/步数/时间/成本）、无进展（动作重复/状态不变）、外部中断。**优先设计可验证的完成条件**，别只靠模型自评。
:::

:::qa 沙箱要隔离什么
文件系统（只读+白名单）、网络（默认禁/白名单）、进程（namespace）、资源（cgroup+超时）。本地用 Bubblewrap/Seatbelt，云端不可信用微虚拟机。
:::

:::qa 高危动作怎么处理
三级授权：只读放开、可逆写审计、不可逆**人工确认**；再配额度上限、预览 diff、可回滚、熔断。
:::

:::qa 长任务崩了怎么办
checkpoint 存四样：消息轨迹、**副作用记录**、待办进度、预算消耗。副作用记录最关键 —— 否则重跑会重复写。
:::

:::qa 评测平台最容易忽略什么
**评测环境与生产同构**（工具超时/限流/返回格式一致），否则会出现"评测通过、上线崩"。另外评测集要能持续吸收线上 badcase。
:::

:::qa 怎么让 RAG 系统在证据不足时"优雅失败"
三件事：检索分阈值 + 拒答机制 + 输出置信度。**宁说"无法确认"，不要硬编** —— 幻觉的代价远大于"不知道"。
:::

:::qa 【挂点】你的研究能直接用在这些设计里吗
能：① CausalPoison 的可逆干预可做**投毒检测的回归测试**；② RePref-Fact 的偏好学习可用于**答案一致性判别**；③ 多智能体的证据状态可做**工作记忆**。但都要说明"这是设计，我没在生产环境验证过"。
:::

## 8. 自测（6 题）

:::qa 系统设计题的第一句话应该是什么
不是画架构，而是**澄清需求**（用户/边界/规模/能否人工兜底）+ 容量估算。
:::

:::qa 万能模板的十段
User → Intent → Planner → Memory → RAG → Tool Router → Tools → Executor → Reflection → Response。
:::

:::qa 四维权衡
效果、延迟、成本、可靠性 —— 每段设计都要点一句。
:::

:::qa Agent 执行框架里最影响效果的两个模块
Context 装配（前缀缓存友好 + 证据放结尾）和 Loop 控制器（终止/预算/防打转）。
:::

:::qa 高危动作的三级授权
只读放开、可逆写审计、不可逆人工确认（+额度、diff 预览、可回滚）。
:::

:::qa 投毒检测的三层
入库前（来源/审核/签名）、检索时（命中统计/来源多样性）、生成后（**可逆干预回归**）。
:::
