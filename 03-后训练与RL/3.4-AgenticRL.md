# 3.4 Agentic RL（长程任务、轨迹、奖励与 verl）

> **为什么这篇重要**：Agent 岗的高端方向（美团 LongCat、字节 Seed、理想 Agentic AI）都会问；而且它是 **3.3 GRPO/RLVR 的"多轮版本"** —— 单轮是"答一道题"，Agentic RL 是"跑完一个任务"。
> **本文的定位**：`★★☆` —— 你**没跑过**这类训练，目标是**原理层面能对答如流 + 知道自己缺什么**（§11 给了诚实话术）。
> **前置**：先看 3.3（GRPO 的组内归一化、RLVR 的可验证奖励），本文直接建立在它上面。

---

## 1. 30 秒口述版

:::card 30 秒版
「Agentic RL 就是把 RL 从"**单轮回答**"扩展到"**多轮任务执行**"：模型不是回一句就结束，而是要**连续调用工具、看观察、再决策**，直到任务完成。

和普通 RLVR 相比，它多了三个难点：

**第一是轨迹变长** —— 一条轨迹可能是十几次工具调用，而奖励只在**最后**给一次（任务成功或失败），所以**信用分配**成了核心问题：到底是哪一步做对了？

**第二是环境** —— 你必须有一个**可重置、可并行、可确定**的环境（检索器、代码沙箱、浏览器），否则没法大规模采样。

**第三是成本** —— 每条轨迹都要真的执行工具，rollout 的量和延迟都是单轮的数倍。

代表工作是 Search-R1（检索即动作）、ReTool（代码解释器即工具）、SWE 系列的代码修复。工程上靠 verl 这类框架：**rollout 用 vLLM 做高吞吐推理，训练用 FSDP/Megatron，中间同步权重**。

我的诚实边界：**我没跑过这类训练**，只做过偏好优化和多智能体编排；但我能说清奖励该怎么设计、以及它会在哪里崩。」
:::

**最后一句一定要说** —— 这类话题很容易被追问到细节，先把边界立住。

## 2. 为什么 Agent 需要 RL（SFT 解决不了什么）

:::card 三个 SFT 的天花板
| 天花板 | 具体表现 | 为什么 SFT 解决不了 |
|---|---|---|
| **① 只能模仿，不能超越** | SFT 的上限是**数据里出现过的行为** | 它学的是"专家在这些情况下这么做"，无法发现数据外更优的策略 |
| **② 长程信用分配** | 一个 15 步的任务失败，你说不清哪步错了 | SFT 只能"整条示范都对"才能学，而真实任务里示范往往次优 |
| **③ 探索缺失** | 同一个任务有多种工具组合，SFT 只会演示过的那一种 | 需要**试错**才能发现更短/更稳的路径 |

**但要注意**：Agentic RL **不能替代 SFT**。SFT 建立"会用工具、会按格式调用"的基础分布；RL 在这个分布上做**优化与探索**。如果模型根本不会调用工具（格式都错），RL 的奖励会全 0。
:::

:::card 一个必须能说的判断（面试常问）
> 「**Agentic RL 的前提是 pass@k 不为 0**。如果模型采样 8 次全都失败，那这组样本的优势为 0（GRPO 的组内归一化），训练根本不动。所以工程上第一件事不是设计奖励，而是**先把 rollout 打通、确认模型有一定成功率**。」
:::

## 3. Agentic RL vs 单轮 RLVR（结构对比）

| 维度 | **单轮 RLVR**（如数学） | **Agentic RL** |
|---|---|---|
| 输入 | 一道题 | 一个任务 + 环境 |
| 动作 | 生成整段文本 | **工具调用**（结构化：name + args） |
| 交互 | 无 | 每步都有 observation 返回 |
| 轨迹长度 | 1 步 | 10–100 步 |
| 奖励 | 最后比对答案 | 任务成功/测试通过（也在最后） |
| 信用分配 | 不需要（单步） | **核心难题**（哪一步贡献了奖励） |
| 环境 | 不需要 | **必需**（可重置、可并行） |
| rollout 成本 | 一次生成 | 每次调用工具 + 等结果 |
| 主要失败模式 | reward hacking | hacking + **提前终止** + **死循环** + **工具误用** |

:::card 一句话概括差异
「单轮 RL 是"**把一道题答对**"，Agentic RL 是"**把一个流程跑对**" —— 后者多了环境、多了时间维度、多了信用分配。」
:::

## 4. 轨迹（Trajectory）怎么构造

:::card 一条轨迹长什么样
```
s0 = (系统提示, 任务, 工具 schema)
a0 = 调用 search("...")            → o1 = 检索结果
a1 = 调用 read(url_3)              → o2 = 页面内容
a2 = 调用 calc("...")              → o3 = 数值
a3 = 输出最终答案                   → 结束
奖励 R = 1（最终答案正确）或 0
```
**形式化**：轨迹 `τ = (s0, a0, o1, a1, o2, …, aT)`，奖励通常在**最后**给一次（稀疏）。

**训练时要把整条轨迹的 token 拼起来**，但**只有模型生成的部分（动作/思考）参与 loss**，工具返回的 observation 不算（和 SFT 的 loss mask 是同一个道理）。
:::

:::card 环境必须满足的三个条件（工程上最容易翻车的地方）
1. **可重置（resettable）**：每个 episode 从干净状态开始 —— 数据库要回滚、文件系统要重置、检索器要无状态
2. **可并行（parallelizable）**：几十上百个环境同时跑（因为单条轨迹要等工具返回，串行太慢）
3. **可确定（deterministic / seeded）**：同样动作得到同样观察，否则奖励噪声大、训练不收敛

**面试话术**：「Agentic RL 一半的工作量在**造环境**，不在算法。检索器可以包成无状态服务、代码执行要沙箱、浏览器要 headless + 预置状态。」
:::

:::card 常见的环境类型与坑
| 环境 | 代表 | 主要的坑 |
|---|---|---|
| 检索器 | Search-R1、RAG 场景 | 语料必须固定（否则同一 query 结果变化 → 奖励噪声）；top-k 和延迟要可控 |
| 代码执行 | ReTool、SWE 系列 | 沙箱隔离、超时、防死循环、防挖矿/外联 |
| 浏览器 | WebArena | 页面会变（要冻结快照）、加载慢、需要状态回滚 |
| 模拟器/数据库 | 企业 Agent | 需要事务回滚 |
:::

## 5. 奖励设计（Agentic RL 最核心的工程决策）

:::card 奖励的四类来源
| 类型 | 例子 | 优点 | 风险 |
|---|---|---|---|
| **结果奖励**（outcome） | 最终答案正确 / 单测通过 / 任务完成 | 无法伪造，最可靠 | 稀疏（一条轨迹一个标量） |
| **过程奖励**（PRM） | 每步打分 / 子目标完成 | 缓解稀疏 | **容易被刷**（学"看起来对的步骤"） |
| **中间检查点** | 子目标完成数 / 进度 | 介于两者之间 | 检查点本身可能被 hack |
| **成本约束** | 步数、token、工具调用次数的惩罚 | 防止瞎试 | 惩罚太强会导致"偷懒" |

**一个实际可用的组合**：
```
R = 1{任务成功}  +  0.1 × 格式合规  −  0.01 × 超出的步数
```
:::

:::card 三条设计原则（能背下来最好）
1. **主奖励必须无法伪造**（结果类：答案/测试/任务完成），其余都是辅助项且权重小
2. **成本项要"软"**：用惩罚而非硬截断（硬截断会让模型在边界处行为突变）
3. **奖励尺度要跨任务可比**：不同任务的奖励要归一化，否则梯度被某个任务主导
:::

:::card Agentic 场景特有的 reward hacking（比单轮更隐蔽）
1. **提前终止**：任务没完成就输出"已完成"（因为"说完成"比"真完成"容易）
2. **死循环刷步数**：如果有"步数奖励"或某些中间奖励，会故意拖步数
3. **工具误用**：用简单工具替代正确工具（比如用 `search` 代替 `read` 拿到的信息更少但更快）
4. **伪造观察**：把工具返回的内容改写成对自己有利的（在"允许模型编辑上下文"的设计里会出现）
:::

## 6. 代表工作（能说出"它做了什么、学到什么"就够）

:::card 四条线
| 工作 | 环境/动作 | 奖励 | 学到什么 |
|---|---|---|---|
| **Search-R1** | 把**检索器**当环境，"检索"是一个动作 | 最终答案匹配 | 学会**何时检索、检索什么**（而不是每步都检索） |
| **ReTool** | **代码解释器**作为工具 | 代码执行 + 答案正确 | 学会**何时写代码算、何时直接推理** |
| **SWE 系列**（SWE-RL / SWE-Gym） | 真实仓库 + 单测 | 测试通过率 | 学会**定位-修改-验证**的工程循环 |
| **WebArena / WebRL** | 浏览器页面 | 任务成功率 | 学会**多步页面操作**（点、填、跳转） |

**一句话共同点**：「**把外部工具变成动作空间的一部分，把工具的执行结果变成观察，把任务是否完成变成奖励** —— 这三件事就是 Agentic RL 的全部骨架。」
:::

:::card 评测侧：τ-bench 与 pass^k（这个要单独记）
- **τ-bench**：多轮工具对话的基准（如客服场景，要遵守业务规则 + 调用工具）
- **pass^k**：**同一个任务跑 k 次全成功的概率**（注意不是 pass@k —— pass@k 是"k 次里有一次成功"）
- **为什么重要**：Agent 的可靠性比"偶尔成功一次"重要得多。`pass^k` 会随 k 快速下降，能暴露"稳定性差"的问题

**面试话术**：「评估 Agent 我只看 pass^k，不看 pass@k —— 后者允许"试很多次成功一次"，那在生产里没用。」
:::

## 7. verl 的框架结构（工程侧必知）

:::card 四个角色 + 一个关键设计
| 组件 | 职责 | 用什么 |
|---|---|---|
| **Rollout engine** | 采样轨迹（生成 + 调工具） | **vLLM / SGLang**（高吞吐推理：continuous batching、KV cache、prefix cache） |
| **Actor（训练）** | 算梯度、更新权重 | **FSDP / Megatron**（切分参数与优化器状态） |
| **Reference** | 算 KL | 通常和 actor 共享显存（offload/分片） |
| **Reward / Verifier** | 判定奖励 | 规则 / 沙箱 / 单测 |

:::card 为什么必须"分离推理引擎和训练引擎"（这是被问最多的一点）
两者需求**根本冲突**：
- **Rollout 要吞吐**：想让一条 GPU 同时跑很多序列 → continuous batching、PagedAttention（vLLM 的强项）
- **训练要切分**：想把一个模型切成很多片放到多卡 → 张量并行/流水线并行（Megatron/FSDP 的强项）

用一个引擎同时干两件事，两边都不划算。所以业界统一做法是：**训练引擎更新权重 → 同步到 rollout 引擎 → rollout 引擎批量采样 → 送回训练**。
:::

:::card 权重同步（工程难点）
每训练一步，rollout 引擎的模型就"旧了"。同步方式：
- **全量同步**：简单，但每次要拷几百 GB（慢）
- **分片/增量同步**：按 layer 广播，或只传变化的 LoRA 权重（快）
- **共卡部署**：训练和 rollout 用同一组卡，分时复用（省卡但要精细调度）

**面试话术**：「verl 这类框架的核心价值不是算法，而是**把"训练-采样-同步"这套流水线做对**，尤其是权重同步和显存复用。」
:::

:::card on-policy 与异步（吞吐 vs 正确性的权衡）
| 模式 | 做法 | 特点 |
|---|---|---|
| **同步（on-policy）** | 采完一批 → 更新 → 再采 | 数据无偏，但 GPU 有空闲（采样和训练交替） |
| **异步（off-policy 程度更高）** | 采样和训练并行，用稍旧的策略数据 | 吞吐高，但数据与当前策略有偏差（要重要性修正） |

**Trade-off 一句话**：「异步能显著提高吞吐，代价是引入了 off-policy 偏差 —— 训练会更不稳定，需要调 clip 和重要性权重。」
:::

## 8. 长程信用分配（这是 Agentic RL 的真正难点）

:::card 四种做法 + 各自的代价
| 方法 | 做法 | 优点 | 问题 |
|---|---|---|---|
| **Monte Carlo（整条轨迹一个奖励）** | 所有动作共享最终奖励 | 无偏、实现简单 | 方差大（15 步里哪个动作该受罚？） |
| **折扣（discount）** | 越早的动作折扣越多 | 偏置换方差 | 会"亏待"早期的关键决策（如选错工具） |
| **GAE / critic** | 用 value model 估计每步优势 | 方差小 | 需要 critic（Agentic 场景状态空间太大，critic 很难训） |
| **过程奖励（PRM）** | 每步单独打分 | 信号密 | **容易被刷**，且需要额外训练/标注 |

:::card 实践中的主流选择
**大多数 Agentic RL 工作用的还是"整条轨迹的结果奖励"**（Monte Carlo），原因：
1. critic 在长程、开放的动作空间里很难训（状态是文本，价值函数难估）
2. 过程奖励容易 hack，且标注成本高
3. 结果奖励虽然方差大，但**方向不会错** —— 配合 GRPO 的组内归一化（同一任务的多条轨迹互相当 baseline），方差问题被很大程度缓解了

**这句话很值钱**：「**GRPO 的组内归一化，本质上是一种"以同题其他轨迹为 baseline"的蒙特卡洛信用分配** —— 它部分替代了 critic 在长程场景里的作用。」
:::

## 9. 成本现实（面试官喜欢问"你知道多贵吗"）

:::card 一个粗略的量级感
设：一条轨迹平均 **T = 10 步**，每步生成 ~200 token、工具调用 ~1 秒；GRPO 每组 **G = 8**。
- **单次更新**要采 8 条轨迹 → **80 次模型调用 + 80 次工具调用**
- 若并行环境数 = 64，一批 8 个问题 → 512 条轨迹 → 约 5000 次工具调用

**结论**：Agentic RL 的瓶颈通常在 **① 工具/环境吞吐**，而不是 GPU 算力。所以工程上要做：
- 工具调用的**批量/异步化**
- 缓存（相同 query 的检索结果）
- 环境预热与连接池
- 只对**有希望的样本**做完整 rollout（早停：明显失败的轨迹提前截断）
:::

## 10. 【挂点】你的项目如果要加 RL，怎么做

:::card 你手上已经有的东西（比很多人强）
| 你的组件 | 在 RL 里对应什么 |
|---|---|
| **证据状态** | 状态表示（虽然还不能直接喂给 critic，但**可作为奖励/过滤的依据**） |
| **三类子 Agent** | 动作空间（选择角色 + 检索策略） |
| **事实依赖图** | 动作先验 / 课程（决定先查哪个子目标） |
| **Macro-F1 评测** | 结果奖励的基础（标签对不对） |

:::card 一个可行的最小 RL 方案（面试可以这样答"如果让你做"）
1. **动作空间**：`{选角色, 选策略, 生成 query}`（离散 + 文本混合，简化为"在 4 种策略里选 + 生成 query"）
2. **状态**：证据状态的结构化表示
3. **奖励**：主奖励 = 最终标签是否正确（**结果奖励，无法伪造**）；辅助 = 覆盖率/冲突消解 + 成本惩罚（步数）
4. **算法**：GRPO（同一声明采 G 条不同检索轨迹，组内归一化）
5. **第一个要验证的事**：**pass@k 是否不为 0**（当前策略能否在 G 次里至少成功一次）

**诚实收尾**：「这是设计，我没跑过。我知道的坑是：检索器必须无状态可复现、奖励必须结果类为主、以及全对/全错的组要过滤。」
:::

## 11. 十个追问预答

:::qa Agentic RL 和普通 RLVR 最大的区别
**多了环境和时间维度**：普通 RLVR 是单轮生成 + 最后比对；Agentic RL 是多轮"动作-观察"序列 + 稀疏的最终奖励，因此多了三个难题：轨迹构造（环境）、信用分配（哪步有功）、成本（每条轨迹要真执行）。
:::

:::qa 长程任务里奖励只在最后给，怎么知道哪一步错了
主流做法是**不精确知道** —— 用 Monte Carlo（整条轨迹共享奖励）+ GRPO 的组内归一化来降方差。
想要更细的信用分配有三条路：过程奖励（容易 hack）、critic/GAE（长程状态空间难训）、中间检查点（子目标完成数）。
**我的判断**：先用结果奖励跑通，再考虑加过程信号。
:::

:::qa 环境为什么必须"可重置、可并行、可确定"
- **可重置**：每个 episode 从干净状态开始，否则前一条轨迹的副作用污染后一条
- **可并行**：单条轨迹大部分时间在等工具 → 串行太慢
- **可确定**：同动作同观察，否则奖励里混入环境噪声，训练不收敛
:::

:::qa 什么是 reward hacking 在 Agent 场景的表现
四个典型：**提前终止**（没做完就说完成）、**死循环刷步数**、**工具误用**（用简单工具替代正确工具）、**伪造观察**（改写工具返回）。
对策：主奖励用结果类（无法伪造）、成本项用软惩罚、加对抗性测试。
:::

:::qa verl 为什么要分离 rollout 和训练引擎
两者需求冲突：rollout 要**吞吐**（continuous batching、KV cache），训练要**切分**（张量/流水形并行）。一个引擎兼顾两边都不划算，所以统一做法是"训练引擎更新权重 → 同步到 rollout 引擎 → 批量采样"。
:::

:::qa 权重同步的开销怎么处理
三种：全量同步（简单但慢）、分片/增量同步（只传变化部分、按层广播）、共卡分时复用（省卡但要精细调度）。**这是这类框架的核心工程价值所在**。
:::

:::qa 异步训练有什么代价
采样和训练并行提高吞吐，但采样用的是**稍旧的策略**（off-policy 程度更高）→ 需要重要性采样修正，训练更不稳定。要调 clip 和重要性权重。
:::

:::qa pass@k 和 pass^k 有什么区别？为什么 Agent 只看后者
- `pass@k`：k 次里**至少成功一次**的概率
- `pass^k`：k 次**全部成功**的概率

生产里要的是稳定可靠，`pass^k` 会随 k 快速下降，正好暴露"偶发成功"的假象。τ-bench 就用这个指标。
:::

:::qa 为什么 Agentic RL 的 critic 很难训
状态是**文本 + 工具返回**，状态空间巨大且非结构化；而且奖励稀疏，value 的监督信号很少。所以主流工作干脆不用 critic，用组内归一化（GRPO）当 baseline。
:::

:::qa 【挂点】你没跑过 Agentic RL，怎么答不失分
按 §10 + §11 的框架：给出**一个具体可行的最小方案**（动作空间、状态、奖励、算法），指出**第一个要验证的事**（pass@k 不为 0），再说清你知道的坑（环境无状态、结果奖励为主、过滤全同组）。
最后照实说：「设计我有，工程我没跑过。」
:::

## 12. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「Agentic RL 就是 GRPO 加个工具调用」 | 「多了环境、信用分配、成本三个维度；算法可以复用 GRPO，但工程主要是造环境」 |
| 「用过程奖励更精细，肯定更好」 | 「过程奖励容易被刷（R1 就没用 PRM 当主奖励），先用结果奖励跑通」 |
| 「SFT 能学的东西有限，应该直接上 RL」 | 「RL 的前提是 pass@k 不为 0；基础分布要靠 SFT 建立」 |
| 「pass@k 高就说明模型好」 | 「Agent 要看 **pass^k**（k 次全成功），pass@k 允许偶发成功」 |
| 「我调过 verl」 | 「我知道 verl 的结构（rollout/actor/ref/reward + 权重同步），但没实际跑过」 |

## 13. 自测（7 题）

:::qa 一句话说清 Agentic RL 相比 RLVR 多了什么
多了三件事：**环境**（可重置/可并行/可确定的工具执行）、**长程信用分配**（哪一步有功）、**成本**（每条轨迹都要真执行工具）。
:::

:::qa SFT 解决不了 Agent 的什么？为什么 RL 能解决
SFT 只能模仿数据里的行为（上限是数据）、无法探索更优路径、也无法处理"示范次优但结果对"的情况。RL 通过**试错 + 结果奖励**去发现更优策略。
:::

:::qa 环境必须满足的三个条件
可重置、可并行、可确定（seeded）。缺任何一个都会导致数据污染或训练不收敛。
:::

:::qa Agentic 场景的四种 reward hacking
提前终止、死循环刷步数、工具误用、伪造观察。
:::

:::qa verl 的四个组件，以及为什么要分离推理引擎
rollout（vLLM/SGLang）、actor（FSDP/Megatron）、reference、reward。分离因为 rollout 要吞吐、训练要切分，需求冲突；代价是要做权重同步。
:::

:::qa pass@k 和 pass^k 的区别，Agent 该看哪个
pass@k = k 次至少成功一次；pass^k = k 次全成功。Agent 要看 pass^k，因为生产要稳定可靠。
:::

:::qa 如果你的多智能体项目要加 RL，第一步做什么
不是设计奖励，而是**确认当前策略的 pass@k 不为 0**（GRPO 组内归一化要求组里有对有错）；然后才谈奖励设计（主奖励用最终标签是否正确）。
:::
