# 4.7 PyTorch 实操与排错（能排错才是真上手）

> **为什么这篇有实操价值**：面试官问"你写过训练脚本吗"，靠的不是背原理，而是**你知不知道为什么 OOM、为什么 loss 不动**。
> **素材来源**：全部是真实高频故障模式，可直接对照你跑 RePref-Fact 时的经历。
> **标注**：`★★☆` 但**极易被追问细节**，建议对照自己的代码过一遍

---

## 1. 30 秒口述版

:::card 30 秒版
「PyTorch 排错我按"**先定位类别，再定位具体位置**"来做。

**显存 OOM** 先算账：权重、梯度、优化器状态、激活、框架开销五块，看哪块异常。最常见的误判是"以为模型太大"，其实是**激活**爆了（batch 或 seq_len 太大）。
**loss 不降**先分清是"根本没学到"（lr、mask、数据、标签）还是"学到了但评估不对"（eval 模式、指标实现）。
**速度慢**先分清是 compute-bound 还是 dataloader 瓶颈（GPU 利用率、num_workers）。

三个最常见的隐形 bug：**loss 没 mask**（把 prompt 也算了）、**评测忘了 `model.eval()`**（dropout 还在生效）、**多卡没配 DistributedSampler**（每张卡读一样的数据）。」
:::

## 2. 显存 OOM 排查（八步，按顺序）

:::card 八步排查法
**① 先算账，别猜**
```
总显存 ≈ 权重 + 梯度 + 优化器状态（Adam 8 bytes/可训练参数）+ 激活 + 框架开销(1~2GB)
```
算一遍，看理论上该占多少。差很多 → 是代码问题；差不多 → 确实不够。

**② 用 `torch.cuda.memory_allocated()` 和 `memory_reserved()` 区分**
- `allocated`：真正被张量占用的
- `reserved`：PyTorch 向 CUDA 申请的总量（含缓存）
- **reserved 远大于 allocated** → 是**碎片**，不是真的不够（可用 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`）

**③ 判断是"权重级"还是"激活级"**
- 把 batch 降到 1、seq_len 降到一半，如果 OOM 消失 → **激活问题**
- 还是 OOM → 权重/优化器问题

**④ 激活的四个降法（按代价从低到高）**
降 batch → 开梯度检查点（`gradient_checkpointing_enable()`，省显存但慢 20–30%）→ 降 seq_len/截断 → 上 FlashAttention

**⑤ 优化器状态**
全参训练时 Adam 的 `m`、`v` 是 fp32（8 bytes/参数）。可用 8-bit Adam、或改 LoRA（只对少量参数建状态）。

**⑥ 检查有没有"忘记 detach"的累积**
在循环里 `loss += ...` 但没 `.item()` → **整个计算图被保留** → 显存随步数线性涨（典型的手写日志 bug）。

**⑦ 检查有没有缓存没释放**
评测阶段累积了所有输出张量（如把所有 logits 存进 list 再算指标）→ 显存随样本数涨。**要在 `torch.no_grad()` 里并转成 CPU/numpy。**

**⑧ 多卡时看是不是只有卡 0 爆**
常见于"指标计算/保存模型只在 rank 0 做、却把所有数据 gathered 到 rank 0"。
:::

## 3. 混合精度（AMP）

:::card 正确写法 + 两个坑
```python
scaler = torch.cuda.amp.GradScaler()

for batch in loader:
    with torch.cuda.amp.autocast(dtype=torch.bfloat16):   # 前向用低精度
        loss = model(**batch)
    scaler.scale(loss).backward()      # 放大 loss 防 fp16 梯度下溢
    scaler.step(optimizer)
    scaler.update()
    optimizer.zero_grad(set_to_none=True)
```

**坑 1：bf16 不需要 GradScaler**
bf16 动态范围与 fp32 相同，不会下溢 → **可以去掉 scaler**（更简单也更快）。只有 fp16 才需要。
**判断**：Ampere 及以后优先 bf16。

**坑 2：不要把不该低精度的算子在 autocast 里算**
如 loss 里的 `log_softmax`、数值敏感的 reducel 操作。autocast 会自动把一部分算子提回 fp32，但**自定义 loss 要自己注意**（必要时 `with torch.autocast(enabled=False)` 包一段）。
:::

## 4. DataLoader 的四个坑

:::card 逐个
| 坑 | 现象 | 解决 |
|---|---|---|
| **`num_workers` 太小** | GPU 利用率低、等数据 | 调到 CPU 核数的 1/2~1，配合 `persistent_workers=True` |
| **`pin_memory=False`** | H2D 拷贝慢 | 设 True（配 non_blocking） |
| **每个 epoch 重建 DataLoader** | worker 反复启动 | `persistent_workers=True` |
| **自定义 collate 里做重活** | 单线程瓶颈 | 把重活放到 worker（dataset 里）或预计算 |

**判断数据瓶颈的方法**：看 `nvidia-smi` 的 GPU 利用率 —— 忽高忽低（比如 30% 抖动）通常是 dataloader 供不上；稳定 95%+ 才是算力瓶颈。
:::

## 5. 五个 dtype / device 的隐形 bug

:::card 高频清单
1. **`expected scalar type Half but found Float`**：模型 bf16 但输入是 fp32 → 统一 `.to(dtype)`
2. **`Expected all tensors to be on the same device`**：某个张量忘了 `.to(device)`（常见于 label、position_ids、自定义 mask）
3. **mask 的 dtype**：`attention_mask` 要 long/bool；`-inf` 填充的 causal mask 要和 logits 同 dtype（否则 autocast 下报错或精度错）
4. **整数标签不能转 half**：`labels` 必须 long，`CrossEntropyLoss` 不接受浮点标签
5. **`torch.tensor(...)` 在 GPU 上创建了 CPU 张量**：要用 `device=` 参数，否则多一次拷贝
:::

## 6. 梯度相关的四个开关

:::card 什么时候用哪个
| API | 作用 | 用在哪 |
|---|---|---|
| `requires_grad_(False)` | 冻结参数 | 冻结 backbone（LoRA 场景） |
| `torch.no_grad()` | 不建计算图 | 评测/推理（但**仍会分配激活**） |
| `torch.inference_mode()` | 更彻底的推理模式（不记录版本计数） | **纯推理首选**，比 no_grad 更快更省 |
| `detach()` | 切断某个张量的梯度 | 累积日志、目标网络、stop-gradient |

**常见错误**：评测时只写了 `model.eval()` 但**忘了 `no_grad`/`inference_mode`** → 显存随 batch 累积、速度慢一倍。
:::

## 7. 梯度累积与梯度检查点

:::card 梯度累积的正确写法
```python
for step, batch in enumerate(loader):
    loss = model(**batch).loss / accum_steps     # ← 除以累积步数
    loss.backward()
    if (step + 1) % accum_steps == 0:
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
```
**两个细节**：
1. **loss 要除以 accum_steps**（否则等效学习率被放大）
2. **最后一个不完整周期要补一次 step**（否则丢掉尾部梯度）

**梯度检查点**：`model.gradient_checkpointing_enable()`
- 效果：不存中间激活，反向时重算 → 显存大降
- 代价：慢 20–30%
- **要用** `use_reentrant=False`（新版本默认），否则和 gradient accumulation / 自定义 forward 容易冲突
:::

## 8. DDP 最小可用 + 三个坑

:::card 最小骨架
```python
torch.distributed.init_process_group("nccl")
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
model = DDP(model.to(local_rank), device_ids=[local_rank])
# 关键：DistributedSampler + set_epoch
sampler = DistributedSampler(dataset, shuffle=True)
loader = DataLoader(dataset, sampler=sampler, ...)
for epoch in range(epochs):
    sampler.set_epoch(epoch)      # ← 忘了这句，每个 epoch 的切分都一样
    ...
```
**三个坑**：
1. **没加 `DistributedSampler`** → 每张卡读全量数据（等于 batch 变大 k 倍，且梯度重复）
2. **忘了 `sampler.set_epoch(epoch)`** → 每个 epoch 的数据顺序/切分不变，shuffle 失效
3. **只在 rank 0 保存模型，但没加 barrier** → 其他 rank 提前进入下一步，导致 hang 或读到半写文件
:::

## 9. 可复现性（三个层次）

:::card 从松到严
```python
# ① 基础
random.seed(42); np.random.seed(42); torch.manual_seed(42); torch.cuda.manual_seed_all(42)

# ② 关掉 cudnn 自动调优（卷积类更相关，Transformer 影响小）
torch.backends.cudnn.benchmark = False

# ③ 严格确定性（会变慢，且有些算子不支持）
torch.use_deterministic_algorithms(True)
```
**现实**：即使全设，**多卡 + 某些 kernel 仍可能有微小差异**。所以工程上：
- **实验结论**要看多次运行的均值/方差，不要相信单次差异小的提升
- 记录 `seed` 和所有超参到日志

**这句话面试能用**：「我的对比实验都跑多个 seed 报均值，因为单次运行的抖动可能比方法本身的提升还大。」
:::

## 10. 调试四板斧

:::card 工具与方法
| 手段 | 用来查什么 |
|---|---|
| **forward hook** 打印每层输出的 mean/std | 哪一层开始出现 NaN/inf、激活爆炸 |
| **梯度范数** `torch.nn.utils.clip_grad_norm_` 的返回值 | 梯度爆炸（>10 就要警惕）、梯度消失（≈0） |
| **`torch.profiler`** | 哪一步耗时最多（前向/反向/dataloader/H2D） |
| **小样本过拟合测试** | 拿 8 条数据训 100 步，能否 loss→0。**不能 → 代码有 bug，不是调参问题** |

**最后这条最有用**：`loss 不降` 时，先用 8 条样本过拟合。如果过拟合不了，一定是**代码 bug**（mask、标签、lr、数据对齐），而不是"模型不够好"。
:::

## 11. 十个追问预答

:::qa 训练时 OOM，你怎么定位
先算账（权重+梯度+优化器+激活+开销），再用 allocated vs reserved 区分"真不够"还是"碎片"。然后把 batch 降到 1 看是否消失 → 消失就是**激活问题**，按"降 batch → 梯度检查点 → 降 seq → FlashAttention"处理。
:::

:::qa 为什么 Adam 的优化器状态这么大
每个可训练参数要存 `m` 和 `v` 两个 fp32 状态 = **8 bytes/参数**。8B 模型全参就是 64 GB。这是全参微调显存的大头（超过权重本身）。
:::

:::qa 评测时忘了 torch.no_grad() 会怎样
会继续建计算图 → 显存随 batch 累积（可能几个 batch 就 OOM）、速度慢一倍。更彻底的是 `inference_mode()`。
:::

:::qa bf16 需要 GradScaler 吗
不需要。bf16 动态范围与 fp32 相同，不会梯度下溢；只有 fp16 才需要 scaler。
:::

:::qa 梯度累积要不要把 loss 除以累积步数
要。否则等效学习率被放大 accum_steps 倍。另外要注意最后一个不完整周期补 step。
:::

:::qa DDP 里最容易忘的两件事
① 用 `DistributedSampler`（否则每卡读全量）② 每个 epoch 调 `sampler.set_epoch(epoch)`（否则 shuffle 失效）。
:::

:::qa loss 不降，你的排查顺序
① 用 8 条样本过拟合（过拟合不了 → 代码 bug）；② 查 loss mask 是否只算了 answer；③ 查 lr 与 warmup；④ 查标签与输入是否对齐；⑤ 查是否 eval 模式没切回来（dropout 仍在）。
:::

:::qa 怎么判断瓶颈在数据还是算力
看 GPU 利用率：忽高忽低（抖动）通常是 dataloader 供不上；稳定高位才是算力瓶颈。也可以用 profiler 看 H2D 与 dataloader 时间占比。
:::

:::qa 梯度检查点的代价是什么
显存大降（不存中间激活）但慢 20–30%（反向要重算）。新版本要用 `use_reentrant=False`。
:::

:::qa 你怎么保证实验可复现
三层：固定所有 seed、关 cudnn benchmark、必要时开 deterministic algorithms；并且**所有对比跑多 seed 报均值**，因为单次抖动可能大于方法收益。
:::

## 12. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「OOM 就是模型太大」 | 「先算五块账；把 batch 降到 1 看是否消失，多半是**激活**问题」 |
| 「评测加 no_grad 只是省显存」 | 「还显著省时间；纯推理首选 `inference_mode`」 |
| 「bf16 也要 GradScaler」 | 「bf16 动态范围和 fp32 相同，不需要；只有 fp16 需要」 |
| 「梯度累积就是多跑几步再 step」 | 「**loss 要除以累积步数**，否则等效学习率被放大」 |
| 「多卡就是把 batch 分摊」 | 「必须配 `DistributedSampler` + `set_epoch`，否则数据重复」 |

## 13. 自测（6 题）

:::qa OOM 排查的第一步是什么
算账（权重+梯度+优化器状态+激活+框架开销），再用 `memory_allocated` vs `memory_reserved` 判断是真不够还是碎片。
:::

:::qa 怎么快速判断是激活爆了还是权重爆了
把 batch 降到 1、seq 减半；OOM 消失 → 激活问题；仍 OOM → 权重/优化器问题。
:::

:::qa Adam 状态占多少？8B 全参是多少
8 bytes/参数（m、v 各 fp32）→ 8B × 8 = **64 GB**。
:::

:::qa `no_grad` 和 `inference_mode` 的区别
前者不建计算图但仍分配激活并记录版本计数；后者更彻底，纯推理更快更省。
:::

:::qa DDP 的两个必做设置
`DistributedSampler` + 每 epoch `sampler.set_epoch(epoch)`。
:::

:::qa loss 不降时最有效的第一个实验
用 8 条样本过拟合 100 步：过拟合不了 → 代码 bug（mask/标签/lr/eval 模式），不是调参问题。
:::
