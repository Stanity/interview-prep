# 4.4 推理优化（KV cache / PagedAttention / 连续批处理 / 投机解码）

> **为什么这篇是必背**：字节 Top20 里「KV Cache 显存计算」是五星；而且大模型岗几乎必问"vLLM 为什么快"。
> **本文目标**：prefill/decode 的区别能讲透、KV cache 能手算、PagedAttention 和连续批处理能说清"解决什么问题"、投机解码能讲"为什么无损"。
> **和第 4.1 的关系**：4.1 讲了 KV cache 的**公式**，这篇讲**怎么把它管好**。

---

## 1. 30 秒口述版

:::card 30 秒版
「LLM 推理分两个阶段：**prefill** 和 **decode**，它们的瓶颈完全不同。

**prefill** 一次处理整个 prompt，矩阵乘密集，是 **compute-bound**（算力受限），决定**首 token 延迟 TTFT**。
**decode** 逐 token 生成，每一步只算一个 token，但要**把全部权重和 KV cache 从显存读一遍** —— 算术强度极低，是 **memory-bound**（带宽受限），决定**每 token 延迟**。

所以优化方向也不同：
- 对 prefill：提升算力利用率（更大的 batch、chunked prefill）
- 对 decode：**减少要读的数据量**（量化、GQA 缩小 KV cache）**或者一次验证多个 token**（投机解码）**或者把权重读取摊给更多序列**（连续批处理）

工程上最出名的是 vLLM 的两个设计：**PagedAttention**（把 KV cache 分页管理，显存浪费从 60%+ 降到几%）和**连续批处理**（每步重组 batch，不让短请求等长请求）。」
:::

## 2. Prefill vs Decode（这一节的对比必须能背）

:::card 两阶段对比
| 维度 | **Prefill** | **Decode** |
|---|---|---|
| 处理什么 | 整个 prompt（n 个 token） | 每次 1 个新 token |
| 计算形态 | 大矩阵乘（`n × d` 乘 `d × d`） | 矩阵-**向量**乘（`1 × d` 乘 `d × d`） |
| 瓶颈 | **compute-bound**（算力） | **memory-bound**（显存带宽） |
| 为什么 | 一次有 `n` 个 token 可并行，算力吃满 | 每步只处理 1 个 token，但要读全部权重 + KV |
| 决定什么指标 | **TTFT**（首 token 延迟） | **TPOT / ITL**（每 token 延迟） |
| 优化方向 | 更大 batch、chunked prefill、更好的 kernel | 量化、GQA/MLA、投机解码、提高并发 |
:::

:::card 为什么说 decode 是 memory-bound（这是核心洞察）
一次 decode 步要做的事：读 8B 参数的权重（bf16 = **16 GB**）+ 读 KV cache，然后只做**一次**矩阵-向量乘（约 `2 × 8B` FLOP）。

**算术强度** ≈ `16 GFLOP / 16 GB` ≈ **1 FLOP/byte**。

而现代 GPU（如 A100）的算力/带宽比约为 **150+ FLOP/byte**。也就是说：**算力被闲置了 99% 以上，瓶颈完全在"搬数据"**。

**结论**：
- **想加速 decode，就不要想着"算得更快"，而要想"少搬点数据"或"一次搬完多用几次"**
- "一次搬完多用几次" = **增大 batch**（权重读一次，摊给 32 个序列用）→ 这就是连续批处理的价值
:::

## 3. KV Cache 的容量规划（手算，**五星高频**）

:::card 公式（和 4.1 一致，这里加容量规划）
```
KV 字节数 = 2 × layers × n_kv_heads × d_head × seq_len × batch × bytes_per_elem
```
:::

:::card 完整算例：一台 80 GB 卡能跑多大 batch
**设定**：Llama-3.1-8B（32 层 / 8 KV 头 / d_head=128）、fp16、上下文 8k、权重 bf16

**① 权重**：8B × 2 = **16 GB**

**② 单序列 KV**：
```
2 × 32 × 8 × 128 × 8192 × 2 = 1.07 GB ≈ 1 GB
```

**③ 可用给 KV 的空间**（80 GB 卡）：
```
80 − 16（权重） − ~4（激活 + 框架/CUDA context 开销） ≈ 60 GB
```

**④ 最大并发序列数**：
```
60 GB / 1 GB = 约 60 条并发
```

**⑤ 如果上下文从 8k 降到 2k**：
```
单序列 KV ≈ 0.25 GB → 可并发约 240 条
```

:::card 这张算例的面试价值
它能一次回答三个问题：
1. **"8B 模型能支持多少并发？"** → 8k 上下文约 60 路（单卡 80G）
2. **"为什么上下文越长越贵？"** → KV 与 seq 线性增长，但挤占的是并发数
3. **"为什么长上下文要配 GQA/MLA？"** → 把 KV 缩小 4 倍 = 并发数翻 4 倍

**答题模板**：「先算权重，再用剩余显存除以单序列 KV。8B/8k/fp16 下单序列约 1 GB，80G 卡大约能并发 60 路。」
:::

## 4. PagedAttention（vLLM 的核心创新）

:::card 它解决什么问题
**传统做法的痛点**：KV cache 要在显存里占**连续**的一大块，而且通常按 `max_seq_len` **预分配**：
- **内部碎片**：实际生成 200 token，但按 8k 预分配 → 浪费 97%
- **外部碎片**：不同长度的连续块把显存切碎，大块申请不到
- **无法共享**：同一个 prompt 的多个采样（best-of-n、beam search）要各存一份 KV

**实测浪费可达 60%–80%** —— 也就是 80G 卡里有一大半在闲置。
:::

:::card PagedAttention 怎么做的（用"虚拟内存"类比最好讲）
**做法**：把 KV cache 切成固定大小的 **block**（如每个 block 存 16 个 token 的 K/V），用一张 **block table** 记录"逻辑块 → 物理块"的映射。

这就是操作系统的**分页虚拟内存**思想：
- 逻辑上连续，物理上可以分散
- **按需分配**（来一个 token 才占一块）→ 内部碎片最多浪费最后一个 block
- **块可以共享**（多个序列指向同一物理块，写时复制）

**收益**：
- 显存浪费从 60%–80% 降到 **< 4%**
- 吞吐提升 **2–4 倍**（同样的卡能跑更多并发）
- 天然支持**前缀共享**（同 prompt 的多路采样共用块）
:::

## 5. 连续批处理（Continuous Batching）

:::card 静态批处理 vs 连续批处理
**静态批处理（static batching）**
- 一个 batch 提交后，所有序列**一起跑**，直到**最长的那个**结束
- 问题：生成长度差异大时，短序列早就结束却仍占着 batch 位置（**padding 空转**）

**连续批处理（continuous / in-flight batching）**
- **每一次 decode 迭代都重新组批**
- 有序列结束 → 立刻移出，**新请求立刻补进来**
- 收益：GPU 利用率大幅提升，长尾请求不再拖累整批

**一句话**：「静态批处理是"整批同生共死"，连续批处理是"**随到随走**"。」
:::

:::card 连续批处理和 PagedAttention 的关系（容易被问）
它们是**互补**的：
- **连续批处理**要求"随时能插入新序列" → 但新序列需要新的 KV 空间
- 如果 KV 必须**连续预分配**，新序列就插不进来（找不到足够大的连续块）
- **PagedAttention 让 KV 可以按块分配** → 连续批处理才真正可行

**一句话**：「**分页让 KV 能"零散地要"，连续批处理才能"随时地加"。**两者是配套的。」
:::

## 6. Chunked Prefill（解决"长 prompt 阻塞短请求"）

:::card 问题
一个 32k 的 prompt 做 prefill 要占很长时间的算力。如果它和一堆短请求混在一批里，**所有短请求的 TPOT 都会抖动**（因为要等这个巨型 prefill 算完）。

**这就产生了经典的取舍**：
- 优先 prefill → TTFT 好，但 TPOT 抖动
- 优先 decode → TPOT 稳，但 TTFT 差
:::

:::card 做法
**把长 prefill 切成若干 chunk**，每个 chunk 和 decode 请求**混在同一个 batch 里**一起算。
- 每次迭代都做"一小块 prefill + 一批 decode"
- 结果：TTFT 略增（因为被切成几段），但 **TPOT 非常平稳**

**一句话**：「chunked prefill 是**用一点 TTFT 换 TPOT 的稳定性** —— 对聊天这类流式输出场景（用户感知的是 TPOT）非常值得。」
:::

## 7. Prefix Caching（跨请求复用相同前缀）

:::card 要点（和 09 号补丁的 §4 呼应，这里只讲推理侧）
- **命中条件**：从第一个 token 开始**逐 token 完全一致**
- **收益最大的场景**：Agent（工具 schema 是几千 token 的固定前缀）、多轮对话（历史天然是前缀）
- **实现**：PagedAttention 的块天然可复用（相同前缀的块直接共享）
- **注意**：缓存有 TTL，且"写缓存贵、读缓存便宜"（商业 API 的计费不同）

**面试话术**：「prefix cache 和 PagedAttention 是同一套块管理能力的两个用法：一个是**同一序列内**复用，一个是**跨请求**复用。」
:::

## 8. 投机解码（Speculative Decoding）

:::card 基本流程
1. 用一个**小的 draft 模型**自回归地快速生成 `k` 个候选 token
2. 用**大的 target 模型**对这 `k` 个 token **一次并行验证**（一次前向，相当于 batch 长度 k）
3. 按规则接受/拒绝，接受的部分直接输出；被拒绝的位置由 target 模型给出正确的 token

**关键**：因为 verification 是并行的，所以"验证 k 个 token"的耗时**接近生成 1 个 token**（decode 是 memory-bound，多算几个 token 不增加多少时间）。
:::

:::card 为什么是"无损"的（必答）
接受规则不是"看起来合理就收"，而是**按概率比接受**：
```
对 draft 建议的 token x：以概率 min(1, p_target(x) / p_draft(x)) 接受
被拒绝时，从"残差分布" (p_target − p_draft)₊ 归一化后重新采样
```
这个规则（来自 speculative sampling）可以严格证明：**最终输出的分布与直接用 target 模型采样完全一致**。

**一句话**：「投机解码**不是近似**，它是无损加速 —— 因为接受/拒绝用的是概率修正，保证输出分布不变。」
:::

:::card 加速比取决于什么
- **接受率 `α`**：draft 与 target 的一致性。α 高 → 加速明显
- **草稿长度 `k`**：太大则被拒的多（浪费），太小则并行度不够
- **draft 模型成本**：draft 太大就不划算了

**典型收益**：α ≈ 0.7–0.8 时，加速 1.5–2.5 倍。

**变体**（知道名字和思路即可）：
| 方法 | 草稿从哪来 |
|---|---|
| Medusa | target 模型自己加多个预测头 |
| EAGLE | 用特征层预测，接受率更高 |
| Lookahead / n-gram | 从 prompt 或历史里抠候选，不用额外模型 |
:::

## 9. 四个延迟/吞吐指标（必须分得清）

:::card 定义
| 指标 | 全称 | 含义 | 由什么决定 |
|---|---|---|---|
| **TTFT** | Time To First Token | 从请求发出到第一个 token 出来 | **prefill 时间 + 排队** |
| **TPOT / ITL** | Time Per Output Token / Inter-Token Latency | 后续每个 token 的间隔 | **decode 每步时间** |
| **TPS** | Tokens Per Second | 吞吐（可指单序列或全系统） | batch × 并行度 |
| **QPS / 并发** | — | 每秒请求数 / 同时处理的请求数 | 显存（KV cache）限制 |

**端到端延迟公式**：
```
总延迟 ≈ TTFT + TPOT × (输出 token 数 − 1)
```

**SLO 举例**（不同业务不同标准）：
- 流式聊天：TTFT < 500 ms，TPOT < 50 ms（≈ 20 token/s 的阅读速度）
- 离线批处理：只关心总吞吐 TPS，不在意单请求延迟
:::

## 10. 十二个追问预答

:::qa prefill 和 decode 的瓶颈分别是？为什么
prefill **compute-bound**（一次处理 n 个 token，矩阵乘密集）；decode **memory-bound**（每步只算 1 个 token，却要读全部权重 + KV，算术强度约 1 FLOP/byte，而 GPU 的算力/带宽比是 150+）。
:::

:::qa 为什么说"decode 时 GPU 算力被浪费了"
一次 decode 步要读 16 GB 权重（8B/bf16）只做约 16 GFLOP → 算术强度 ≈ 1，远低于 GPU 的 ~150 → 算力利用率极低，瓶颈在带宽。
**所以 decode 优化要么少读（量化/GQA），要么一次搬完多用几次（大 batch），要么一次验证多个 token（投机解码）。**
:::

:::qa vLLM 为什么快？两个原因
① **PagedAttention**：KV cache 按块分配 + 块表映射，显存浪费从 60%–80% 降到 <4%，同样的卡能跑更多并发
② **连续批处理**：每步重组 batch，完成的移出、新的补进，GPU 利用率大幅提升
**两者是配套的**：分页让 KV 能零散申请，连续批处理才能随时插新序列。
:::

:::qa PagedAttention 和操作系统的虚拟内存有什么相似
几乎一样：逻辑连续、物理离散；块表做映射；按需分配；块可共享（写时复制）。所以"KV cache 的分页"就是把 OS 的页表思想搬过来了。
:::

:::qa 静态批处理的问题是什么
一个 batch 里所有序列要等**最长的那个**结束；短序列早就完成却仍占位（padding 空转），长尾请求拖累整批 → GPU 利用率低。
:::

:::qa chunked prefill 解决什么问题？代价是什么
长 prompt 的 prefill 会阻塞同批的 decode，导致 TPOT 抖动。切成块与 decode 混批 → TPOT 平稳。**代价是 TTFT 略增**。
:::

:::qa 投机解码为什么无损？接受规则是什么
按 `min(1, p_target/p_draft)` 接受、拒绝时从残差分布重采样 —— 可严格证明输出分布与直接采样一致。所以是**无损加速**，不是近似。
:::

:::qa 投机解码的加速比取决于什么
接受率 α、草稿长度 k、draft 模型成本。α ≈ 0.7–0.8 时加速 1.5–2.5 倍。k 太大浪费、太小并行度不够。
:::

:::qa TTFT 和 TPOT 分别由什么决定
TTFT = prefill 时间 + 排队；TPOT = decode 每步时间。端到端 ≈ `TTFT + TPOT × (输出长度 − 1)`。
:::

:::qa 8B 模型 8k 上下文，一张 80G 卡能跑多少并发
权重 16 GB，剩约 60 GB；单序列 KV ≈ 1 GB → **约 60 路**。上下文降到 2k 则约 240 路。
:::

:::qa 长上下文推理的关键成本是什么
**KV cache**，不是权重。KV 随 `seq × batch` 线性增长，直接决定并发上限。所以长上下文要么减 KV（GQA/MLA）、要么减精度（KV 量化）、要么加卡。
:::

:::qa 如果线上 TPOT 抖动严重，你会先查什么
三个方向：
① **是不是长 prefill 在抢算力** → 上 chunked prefill
② **是不是 batch 里序列长度差异大** → 检查调度策略、是否开了连续批处理
③ **是不是 KV cache 快满了导致频繁换出/重算** → 看显存利用率和抢占次数
:::

## 11. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「推理慢是因为算力不够」 | 「decode 是 **memory-bound**：算力被闲置，瓶颈在读权重和 KV」 |
| 「vLLM 快是因为 kernel 优化」 | 「主要是 **PagedAttention（省显存）+ 连续批处理（提利用率）**」 |
| 「PagedAttention 只是省显存」 | 「它同时让**连续批处理**可行、支持**块级共享**（前缀复用/多路采样）」 |
| 「投机解码会损失精度」 | 「它是**无损**加速，接受规则保证输出分布不变」 |
| 「TTFT 和 TPOT 是一回事」 | 「TTFT 由 prefill 决定，TPOT 由 decode 决定；端到端 = TTFT + TPOT×(n−1)」 |
| 「长上下文贵在权重」 | 「贵在 **KV cache**，它随 seq×batch 线性增长并挤占并发」 |

## 12. 自测（8 题）

:::qa prefill 和 decode 的瓶颈分别是什么？为什么
prefill compute-bound（n 个 token 并行，算力吃满）；decode memory-bound（每步 1 个 token 但要读全部权重 + KV，算术强度 ≈1 FLOP/byte）。
:::

:::qa 写出 decode 的算术强度估算（8B/bf16）
读 16 GB 权重做约 16 GFLOP → 约 1 FLOP/byte，而 GPU 约 150 FLOP/byte，算力闲置 99%。
:::

:::qa vLLM 快的两个原因，以及它们为什么配套
PagedAttention（块级 KV 管理，浪费 <4%）+ 连续批处理（每步重组 batch）。分页让 KV 能零散申请，连续批处理才能随时插新序列。

:::qa PagedAttention 用 OS 的什么思想
虚拟内存分页：逻辑连续、物理离散、块表映射、按需分配、块可共享（写时复制）。
:::

:::qa 静态批处理的问题
要等 batch 内最长的序列结束，短序列 padding 空转，长尾拖累整批。
:::

:::qa chunked prefill 的取舍
用 TTFT 略增换 TPOT 平稳（把长 prefill 切块与 decode 混批）。

:::qa 投机解码为什么无损？加速比取决于什么
