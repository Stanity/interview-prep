# 4.3 MoE 与主流结构（稀疏专家、路由、专家并行）

> **为什么单独一篇**：MoE 是当前大模型的主流架构（DeepSeek、Qwen、Mixtral 都是），面试常问"MoE 省的是算力还是显存"、"负载均衡怎么做"。
> **前置**：4.1 的注意力变体（MLA 是 DeepSeek 的另一半创新）+ 4.4 的推理成本（MoE 的推理特性很特殊）。
> **标注**：`★★☆` 能讲清机制与取舍即可

---

## 1. 30 秒口述版

:::card 30 秒版
「MoE（混合专家）的做法是：**把 FFN 层拆成多个"专家"，每个 token 只激活其中少数几个**。

一个标准配置是：256 个路由专家 + 1 个共享专家，每个 token 选 top-8。路由由一个小的 gating 网络算出来。

它的核心价值是**解耦"总参数量"和"每 token 计算量"**：
- 总参数可以做到 671B（容量大、知识多）
- 但每个 token 只算 37B（算力接近 37B 的稠密模型）

所以一句话：**MoE 省的是"计算量"，不省"显存"** —— 因为所有专家都得驻留在显存里，只是不全用。

代价是工程复杂度：**负载均衡**（不能让所有 token 都挤到同一个专家）、**专家并行**（all-to-all 通信）、以及微调时专家利用率不均是难点。」
:::

**"省算力不省显存"这句是面试的分水岭**，很多人答错成"省显存"。

## 2. MoE 的基本机制

### 2.1 结构：替换什么

:::card 只替换 FFN，attention 保持共享
```
标准 Transformer block：
    x = x + Attention(Norm(x))        ← 共享（所有 token 都走同一套参数）
    x = x + FFN(Norm(x))              ← 替换成 MoE

MoE block：
    h = Norm(x)
    scores = Router(h)                ← 小线性层：d → 专家数
    idx = topk(scores, k)             ← 选 k 个专家
    out = Σ_{iinidx} w_i · Expert_i(h) ← 加权求和（w_i 来自 scores 归一化）
    x = x + out
```

**为什么只替换 FFN**：FFN 占了参数量的约 2/3，是"知识存储"的主要位置（见 4.1 §7）；attention 负责 token 间信息流动，通常共享就够。
:::

### 2.2 稀疏激活：总参数 vs 激活参数

:::card 两个数字要分清
| 概念 | 含义 | 决定什么 |
|---|---|---|
| **总参数量**（total params） | 所有专家的参数加起来 | **显存占用**（推理要全部驻留） |
| **激活参数量**（activated params） | 每个 token 实际算到的参数 | **计算量 / 延迟** |

**典型配置**：
| 模型 | 总参数 | 激活参数 | 路由配置 |
|---|---|---|---|
| Mixtral 8×7B | 46.7B | 12.9B | 8 专家，top-2 |
| DeepSeek-V2 | 236B | 21B | 细粒度专家 + 共享专家 |
| **DeepSeek-V3** | **671B** | **37B** | **256 路由专家 + 1 共享专家，top-8** |
| Qwen3-235B-A22B | 235B | 22B | top-8 一类 |

**面试话术**：「671B 总参数、37B 激活 —— 参数量比 37B 稠密模型大 18 倍，但计算量差不多。这就是 MoE 的全部卖点。」
:::

### 2.3 MoE 到底省什么、不省什么

:::card 三句话讲清
| 资源 | 省吗 | 为什么 |
|---|---|---|
| **计算量（FLOPs）** | ✅ **省** | 每 token 只算 k 个专家 |
| **显存** | ❌ **不省** | 所有专家都要放显存（否则 offload 就慢死） |
| **通信** | ❌ **更贵** | 专家分布在不同 GPU，要做 all-to-all |
| **训练难度** | ❌ **更高** | 负载均衡、路由稳定性、专家塌缩 |

**这就是为什么 MoE 是"大厂架构"**：它用通信和工程复杂度，换来了"用同样的算力跑更大的模型"。
:::

## 3. 负载均衡（MoE 最核心的工程问题）

:::card 问题：路由塌缩（routing collapse）
如果不管，训练会很快退化成"MVP 通吃"：
- 少数几个专家被越来越多 token 选中 → 它们训得更好 → 更容易被选中（**正反馈**）
- 其他专家收不到梯度 → 一直很差 → 更不会被选中

**结果**：实际只有少数专家在工作，MoE 退化成小模型，白占显存。
:::

:::card 四种对策（按出现顺序）
**① 辅助损失（auxiliary loss）** —— 经典做法
在训练损失上加一项，惩罚不均衡：
$$
\mathcal{L}_{\mathrm{aux}}=\alpha\cdot N\cdot\sum_i\big(f_i\cdot P_i\big)
$$
- `f_i`：分给专家 i 的 token 比例（实际负载）
- `P_i`：路由器给专家 i 的平均概率（倾向）
- 系数 `α` 通常很小（**0.01 量级**）—— 大了会损害主任务

**② 容量因子（capacity factor）**
给每个专家设一个**容量上限**（如 `capacity = factor × tokens / num_experts`）。
超出的 token 会被**丢弃**（drop）或走残差直通。
- factor > 1 → 留余量，少丢 token，但浪费算力
- factor < 1 → 更省算力，但丢 token 多

**③ 专家选择的反向思路（expert choice）**
不是"token 选专家"，而是"**专家选 token**"（每个专家取自己最想要的若干个）→ 天然均衡，但实现复杂。

**④ 无辅助损失（auxiliary-loss-free）** —— DeepSeek-V3 的做法
不用 aux loss，而是给每个专家维护一个**偏置项 `b_i`**：
- 某专家负载过高 → 训练时把它的 `b_i` 稍微调低
- 某专家负载过低 → 调高

这个偏置**只影响路由选择，不影响 gating 权重**，所以不会干扰主任务的梯度。
**好处**：避免了 aux loss 的"为了均衡牺牲效果"问题。
:::

## 4. 专家并行（Expert Parallelism, EP）

:::card 为什么需要、怎么做
**为什么需要**：671B 参数（FP8 约 671 GB）**一张卡放不下**，必须把专家分散到多张卡。

**做法**：
1. 每个 GPU 放一部分专家（如 256 个专家分到 16 卡，每卡 16 个）
2. 前向时每个 token 要送到"它选中的专家所在的那张卡" → **all-to-all 通信**
3. 算完再把结果**送回来** → 再一次 all-to-all

**通信量估算（面试常问）**：
```
每个 token 的通信量 ≈ 2 × k × hidden_size × bytes    （去 + 回）
```
以 `hidden = 7168`、`k = 8`、FP8 估算，每 token 单层约 **100+ KB**；再乘层数（61 层）和 token 数 —— 这就是为什么 MoE 训练**对网络带宽极度敏感**（需要 NVLink / 高速互联）。
:::

:::card EP 与其他并行的组合
| 并行方式 | 切什么 | 在 MoE 里的角色 |
|---|---|---|
| 数据并行 DP | batch | 常规 |
| 张量并行 TP | 单层矩阵 | 专家内部也可切 |
| 流水线并行 PP | 层 | 常规 |
| **专家并行 EP** | **专家** | MoE 特有，通信最重 |

实际训练是 **DP × PP × EP（× TP）的组合**，调度的核心是"让 all-to-all 尽量落在同一节点内"。
:::

## 5. DeepSeek-V3 的架构要点（现在最常被当例子问）

:::card 五个关键设计
| 设计 | 是什么 | 解决什么 |
|---|---|---|
| **MLA**（Multi-head Latent Attention） | KV 压缩成低秩 latent | KV cache 大降（见 4.1 §9.3） |
| **DeepSeekMoE：细粒度专家** | 专家更多但每个更小（256 个小专家而非 8 个大专家） | 组合空间更大，专业化更细 |
| **共享专家（shared expert）** | 1 个专家**所有 token 都走** | 承载通用知识，减少路由专家的"重复学习" |
| **Auxiliary-loss-free 负载均衡** | 用偏置项调路由，不用 aux loss | 均衡的同时不牺牲效果 |
| **MTP**（Multi-Token Prediction） | 一次预测多个未来 token | 提高训练信号密度、可做投机解码的草稿 |

**规模**：671B 总参 / 37B 激活 / 61 层 / 256 路由专家 + 1 共享专家 / top-8。
:::

:::card 为什么"细粒度专家 + 共享专家"是重要改进
- **细粒度**：8 个大专家选 2 个，组合数是 `C(8,2)=28`；256 个小专家选 8 个，组合数是 `C(256,8)` —— **组合空间爆炸式增长**，专业化更细
- **共享专家**：总有一些知识（语法、常识）**所有 token 都需要**。让一个专家专职承载这些，路由专家就不用重复学 → 提高参数效率
:::

## 7. MoE 的三类代价（面试问"有什么缺点"时用）

:::card 逐个说清
**① 训练**
- all-to-all 通信开销大（对带宽敏感）
- 负载均衡难（塌缩、丢 token）
- 路由不稳定（早期训练容易抖）
- 需要更多卡才能装下（671B 至少几十张 H800）

**② 推理**
- **显存必须装全部专家**：671B/FP8 ≈ 671 GB → 至少 8×80G 才放得下权重（还没算 KV）
- 但**算力只花 37B** → 单请求延迟低，**适合高吞吐场景**（大 batch 摊薄权重读取），不适合小并发低延迟
- batch 小时专家利用率低（有的专家完全没被用到）→ 卡在"等待"

**③ 微调**
- 专家利用率不均：某些专家很少被激活 → 微调时它们几乎不更新，导致任务适配不充分
- 常见对策：只训 attention + 共享专家、或加路由正则、或对专家做重均衡
:::

:::card 一个反直觉的结论（答出来很加分）
**MoE 的推理特性是"高吞吐友好、低延迟不友好"**：
- 大 batch 时，虽然每 token 只算 37B，但**所有专家的权重都要从显存读一遍**（因为不同 token 走不同专家）→ 有效权重读取量接近稠密 671B
- 所以 MoE 在**离线批处理/高并发**场景性价比高，在**单用户低延迟**场景不一定划算

**这也是"MoE 省算力不省显存"的进一步推论**：省的是 FLOPs，但显存带宽压力反而更大。
:::

## 8. 十个追问预答

:::qa MoE 省的是算力还是显存？一句话
**省算力（FLOPs），不省显存。** 所有专家都要驻留显存，只是每个 token 只走其中 k 个。
而且带宽压力反而更大（不同 token 走不同专家，权重读取不集中）。
:::

:::qa MoE 为什么能提升效果？本质是什么
**解耦了总参数量和计算量**：可以用 18 倍的参数容量（更多知识），但每 token 只花接近稠密小模型的计算。
另一个角度是**条件计算（conditional computation）**：不同 token 用不同参数，等于让模型对输入"分工"。
:::

:::qa 路由怎么做？为什么需要 top-k 而不是 top-1
router 是一个小的线性层 + softmax，取分数最高的 k 个专家并归一化权重。
**top-1 的问题**：太难均衡（一个 token 只能给一个专家，负载极不均衡）、且路由错误没有缓冲。top-2/top-8 提供了"组合"和"容错"。
:::

:::qa 什么是路由塌缩？怎么解决
少数专家被过度选择、其余收不到梯度 → MoE 退化。
对策：**辅助损失**（惩罚负载不均，系数 0.01 量级）、**容量因子**（超限丢弃）、**专家选 token**、**无 aux loss 的偏置调整**（DeepSeek-V3）。
:::

:::qa 容量因子（capacity factor）是什么？大了小了会怎样
给每个专家设容量上限 `factor × tokens / num_experts`。
- factor 大 → 少丢 token，但浪费算力
- factor 小 → 省算力，但丢 token 多（丢的 token 走残差直通，信息损失）
:::

:::qa DeepSeek-V3 的"无辅助损失负载均衡"是怎么做的
给每个专家维护一个偏置 `b_i`，根据负载动态微调（过载调低、闲置调高）。偏置**只影响路由选择，不参与 gating 权重和梯度** → 均衡但不干扰主任务，避免了 aux loss 的"为均衡牺牲效果"。
:::

:::qa 专家并行（EP）的通信是什么样？为什么贵
前向要做**两次 all-to-all**：把 token 送到目标专家所在的卡、再把结果送回来。
每 token 单层通信量约 `2 × k × hidden × bytes`，乘层数后非常大 → 需要 NVLink/高速互联，且要尽量让通信落在节点内。
:::

:::qa 细粒度专家 + 共享专家为什么有效
细粒度：专家更多更小 → 组合空间从 `C(8,2)` 涨到 `C(256,8)`，专业化更细。
共享专家：承载所有 token 都需要的通用知识（语法/常识），让路由专家不必重复学 → 参数效率更高。
:::

:::qa MoE 模型微调有什么坑
专家利用率不均：部分专家几乎不被激活 → 微调时基本不更新，任务适配不充分。
对策：只训 attention + 共享专家、加路由正则、或做专家重均衡。
:::

:::qa 671B 的 MoE 要多少显存才能推理
FP8 下权重约 671 GB → **至少 8×80G**（还没算 KV cache 和激活）。所以 MoE 的部署门槛主要在显存，而不是算力。
:::

## 9. 陷阱

| ❌ 别这么说 | ✅ 换成这么说 |
|---|---|
| 「MoE 省显存」 | 「MoE **省算力不省显存**；所有专家要驻留，带宽压力还更大」 |
| 「MoE 就是多个小模型集成」 | 「MoE 是**条件计算**：每个 token 只走少数专家，参数共享同一个 block」 |
| 「top-1 路由最省」 | 「top-1 太难均衡，容易塌缩；实践中 top-2~top-8 更稳」 |
| 「辅助损失是必须的」 | 「DeepSeek-V3 用**偏置调整**实现了无 aux loss 的均衡」 |
| 「MoE 一定比稠密好」 | 「MoE 用通信和工程复杂度换参数效率；低延迟单用户场景不一定划算」 |

## 10. 自测（6 题）

:::qa 一句话说清 MoE 省什么不省什么
省 FLOPs（每 token 只算 k 个专家），不省显存（全部专家要驻留），且**带宽压力更大**。
:::

:::qa 总参数和激活参数分别决定什么
总参数 → 显存占用；激活参数 → 计算量/延迟。DeepSeek-V3 是 671B / 37B。
:::

:::qa 路由塌缩的原因和三种对策
原因是"被选中的专家训得更好→更易被选中"的正反馈。对策：辅助损失、容量因子、专家选 token（以及 DeepSeek 的偏置调整）。
:::

:::qa 容量因子的作用和取舍
限制每个专家的 token 上限。大 → 少丢 token 但浪费算力；小 → 省算力但丢 token。
:::

:::qa 专家并行贵在哪
前向两次 all-to-all（分发 token + 收回结果），通信量随层数与 hidden 线性增长，依赖高速互联。
:::

:::qa 为什么细粒度专家 + 共享专家是好设计
细粒度提升组合空间（专业化更细）；共享专家承载通用知识，减少路由专家的重复学习。
:::
