## 1. Context Engineering（上下文工程）★★★

:::card 一句话定义（先记住这句）
**把"有限的 context window 里放什么、按什么顺序放、怎么压缩、怎么隔离"当成一门工程来做。**
它是 Prompt Engineering 的超集 —— Prompt 工程关心"怎么问"，Context 工程关心"**给模型看什么**"。
:::

### 1.1 为什么 2026 年突然变高频

三个原因叠加：
1. **长上下文模型出现**（Gemini 1.5 Pro 的 1M、"128k 起步"），于是面试题变成"**长上下文能不能取代 RAG**"；
2. **Agent 场景下 context 爆得很快**：工具 schema + 检索证据 + 多轮工具结果，几轮就塞满；
3. **成本与延迟**：context 长度 ≈ 成本，也是首 token 延迟的主因。

### 1.2 context 里到底有哪些成分（预算要按类分配）

| 成分 | 典型占比（Agent 场景） | 变化频率 | 能否缓存 |
|---|---|---|---|
| System prompt / 角色指令 | 5–10% | 极低 | ✅ 可缓存 |
| **工具 schema（tools）** | 10–30% | 低 | ✅ 可缓存 |
| Memory / 事实（用户画像、历史结论） | 5–15% | 中 | 部分 |
| 检索证据（RAG 结果） | 30–50% | 高 | ❌ |
| 对话/轨迹历史 | 20–40% | 高 | 增量可缓存 |
| 当前输入 | 小 | — | ❌ |

**面试话术**：「我会先给每类成分定配额，比如工具 schema 不超过 20%、检索证据不超过 40%，超了就**按重要性裁剪**而不是无脑截断 —— 因为不同位置的信息价值差异巨大。」

### 1.3 六条核心原则（能背下来最好）

:::card Context Engineering 六原则
1. **预算分配**：按成分定配额，避免"检索结果把工具定义挤掉"
2. **位置效应**：模型对**开头和结尾**更敏感（lost in the middle）→ 最重要的指令放开头，最强证据放结尾附近
3. **压缩**：摘要（小结代替原文）、抽取（只留关键句）、结构化（表格代替段落）
4. **隔离**：子 Agent 各自独立 context，只把**结论**回传给主 Agent（这是多 Agent 最大价值之一）
5. **可溯源**：每段证据带 id，答案要能指回原文（幻觉定位 + 用户信任 + 评测）
6. **缓存友好**：**稳定内容放前面、变化内容放后面**（直接对接 §4 的 Prompt Caching）
:::

### 1.4 "长上下文能否取代 RAG" —— 这是最可能被问的一道

:::card 标准答法（四维度，缺一不可）
**结论**：不能取代，是互补关系。四个理由：

1. **成本**：把 100 万 token 的语料每次塞进 context，成本比一次向量检索高几个数量级；RAG 是"只付相关部分的钱"。
2. **时效**：长上下文里的是**静态快照**；RAG 可以接实时更新的知识库。
3. **可溯源**：RAG 天然带出处（chunk id → 原文）；纯长上下文里模型说不清"这句话来自哪里"。
4. **注意力稀释**：即使窗口够大，**有效利用**仍然随长度下降（lost in the middle），证据越多不一定越好。

**加分收尾**：「我的判断是：**长上下文降低了对 RAG 精度的要求，但提高了对 RAG 排序质量的要求** —— 以前要"只召回对的"，现在允许"多召回一些"，但**顺序**必须对。」
:::

### 1.5 高频追问

:::qa context 快满了怎么办？压缩还是丢弃
先判断**信息类型**再决定：
- **指令/约束类**（不能丢）→ 重写压缩成要点，保留
- **工具结果**（可复原）→ 只保留结论 + 一个引用 id，原始输出丢弃（需要时可按 id 重新取）
- **失败轨迹**（有价值）→ 压缩成"尝试过 X，失败原因是 Y"一行
- **闲聊/无关**→ 直接丢

一句话：「**能重新取回的东西就丢，取不回来的东西就压缩。**」
:::

:::qa 你怎么判断 context 组装得好不好
三层验证：
1. **离线**：做 A/B —— 同一批任务，不同组装策略的通过率与平均 token 消耗
2. **在线**：看"同一任务的平均步数"和"因缺信息导致的失败率"
3. **可诊断**：所有 trace 里记录"本次 context 由哪几部分构成、各占多少"，出问题能归因
:::

:::qa 【挂点】你的项目里有没有 context engineering
有，而且是你最值钱的那部分：
- 你的**证据状态（Evidence State）**本质上是"**结构化的工作记忆**"，你决定"哪些证据进 context、哪些只留标记"，这就是 context 工程
- 你的**事实依赖图调度**决定了"**检索顺序**"，等价于"context 里证据的**排列顺序**"（对应原则 2：位置效应）
- 你的三类子 Agent **共享证据状态**而不是共享全部上下文，正是原则 4（隔离）的一个实例

**话术**：「我没用 Context Engineering 这个词，但我做的事就是它 —— 我用状态决定什么进上下文，用依赖图决定顺序。」
:::

## 2. Loop Engineering（循环工程）★★★

:::card 一句话定义
**Agent 的执行循环不是"写个 while + 调工具"，而是一套让它可以跑长任务、跑不崩、跑完能验证的工程体系。**
相关概念：`Agent Loop`（循环本体）→ `Loop Engineering`（怎么把循环工程化）。
:::

### 2.1 循环的六要素（先给结构，再谈工程）

| 要素 | 要解决的问题 | 工程化要点 |
|---|---|---|
| **状态 State** | 当前知道什么、做到哪 | 显式结构（不要靠 prompt 里的自然语言记忆） |
| **动作空间 Action** | 能做什么 | 工具 schema + 权限分级，**动态暴露子集** |
| **观察 Observation** | 工具返回怎么进 context | 截断、结构化、错误归一化 |
| **控制 Control** | 下一步做什么 | 规则 + 模型混合（不全靠模型决策） |
| **终止 Termination** | 什么时候停 | **四类终止**（见 2.2） |
| **预算 Budget** | 花多少 | token / 步数 / 时间 / 金钱，四维独立 |

### 2.2 四类终止条件（面试必问"循环怎么停"）

:::card 必须能说出这四类
1. **任务完成（可验证）**：最有价值的一类 —— 有测试、有 schema 校验、有断言。
   > 这正是 **RLVR（可验证奖励）** 和"任务可验证完成"在工程上的对应物。
2. **预算耗尽**：token / 步数 / 墙钟时间 / 成本，任一触顶即停，并**交回部分结果 + 说明为什么停**。
3. **无进展（no-progress detection）**：见 2.3。
4. **外部中断**：用户取消、审批拒绝、上游依赖失败。

**话术**：「只靠模型自己说'完成了'是最危险的做法 —— 因为它永远会说完成了。所以我优先设计**可验证的完成条件**：能跑测试的跑测试，能校验 schema 的校验 schema，实在不行才退回'模型自评 + 人工确认'。」
:::

### 2.3 无进展检测（防"转圈"，这是长任务最大的坑）

:::card 三种检测手段（可以叠加）
1. **动作重复检测**：把 (工具名 + 归一化参数) 做哈希，最近 N 步里出现 ≥2 次即告警
2. **状态不变检测**：关键状态字段（证据数、覆盖率、剩余预算）连续 k 步无变化
3. **观察相似度检测**：连续两次工具返回的语义相似度超阈值（说明在重复同一查询）

**触发后做什么**（按顺序）：
① 强制改策略（换检索词 / 换工具 / 分解子目标）→ ② 降级（用已有证据作答并标注不确定）→ ③ 终止并上报（把轨迹交给人）
:::

### 2.4 预算设计：四维 + 分阶段

:::card 预算不是"一个数"，是"四维 + 分段"
| 维度 | 建议阈值（示意） | 触顶动作 |
|---|---|---|
| token | 单任务 40k–100k | 压缩 history，保留结论 |
| 步数 | 20–50 步 | 强制收敛 |
| 墙钟时间 | 5–10 分钟 | 返回部分结果 |
| 成本（$） | 按业务定 | 降级到小模型 |

**分阶段**：探索期给宽（前 30% 预算可以"乱试"），收敛期给紧（后 30% 只允许"确认性动作"）。很多 Agent 的失败不是预算不够，而是**预算花在了探索上、没留给收敛**。
:::

### 2.5 状态快照与断点恢复（长任务必备）

:::card checkpoint 里必须写什么
1. **消息/轨迹**（可裁剪，但关键决策要留）
2. **工具调用的副作用记录**（哪些写操作已经生效，避免重跑时重复写）
3. **待办与进度**（哪些子目标已完成）
4. **预算消耗**（已用 token/步数，恢复后接着算）
5. **随机种子 / 版本号**（可复现）

**为什么重要**：没有 checkpoint，一次 50 步的任务在第 49 步崩了就得从头再来（而且会**重复执行副作用**）。
:::

### 2.6 高频追问

:::qa Agent 跑 200 步还没完成，你怎么排查
按"三层归因"回答：
1. **目标层**：任务本身不可验证 / 目标表述含糊 → 先看是不是任务定义的问题
2. **控制层**：没有无进展检测 / 预算没分阶段 → 看轨迹里有没有重复动作、有没有"越查越远"
3. **工具层**：工具返回信息不足或错误被吞掉 → 看工具错误率与观察质量

**加分**：「我会先看**第几步开始偏离**，因为长任务崩掉往往是某个早期错误没被发现，后面全在错误的前提上继续。」
:::

:::qa 【挂点】你的项目有循环工程吗
有，虽然规模小：
- **终止条件**：你设计了"证据充分 / 预算耗尽 / 边际收益为负"三类，这正是 2.2 的工程化版本
- **无进展处理**：你的"事实依赖图 + 子目标覆盖检查"天然避免了对同一事实反复检索
- **状态隔离**：三类子 Agent 共享**证据状态**而非共享全部上下文

**诚实边界**：「我没做过跨会话的长程执行（long-horizon）和断点恢复，这是我和生产级 Harness 的差距；但循环的**控制结构**我是手写过的。」
:::

## 3. Harness Engineering（Agent = Model + Harness）★★★

:::card 一句话定义
**Harness = 模型之外的一切：工具、权限、沙箱、循环控制、状态管理、可观测、评测、上下文装配。**
业界共识：**同一个模型，harness 不同，任务完成率能差一个量级。**
:::

### 3.1 为什么这个词突然火了

- **证据**：SWE-bench 上同样的基础模型，不同 scaffold（脚手架）能差 10 分以上 —— 模型不是瓶颈，**怎么装它才是**
- **JD 信号**：清昴智能的 Agent 研发 JD 原文就是"参与自研 **Agent Harness 框架**的核心模块设计与开发"
- **一句话总结**：**Agent = Model + Harness**，模型是"大脑"，harness 是"身体 + 制度"

### 3.2 Harness 的八个组件（这张表建议背下来）

| # | 组件 | 作用 | 缺了会怎样 |
|---|---|---|---|
| 1 | **工具注册与 schema** | 定义能做什么、参数约束 | 模型乱调、参数幻觉 |
| 2 | **执行器与沙箱** | 真正执行 + 隔离风险 | 删库、越权、资源打爆 |
| 3 | **循环控制器** | 何时继续/终止（§2） | 转圈或早停 |
| 4 | **状态与记忆** | 任务状态、长期记忆 | 健忘、重复劳动 |
| 5 | **上下文装配** | 决定给模型看什么（§1） | 信息过载或缺信息 |
| 6 | **可观测（trace/telemetry）** | 每次调用结构化记录 | 出问题无法归因 |
| 7 | **权限与审批** | 分级自主、人工介入 | 不可控的自主性 |
| 8 | **评测与回归** | 改一版会不会变差 | 越改越烂而不自知 |

### 3.3 如果只能做三件事

:::card 被问"给你一个模型，你要怎么搭 harness，先做什么"
1. **工具 schema 规范化**（最高性价比）：名字见名知意、描述写"什么时候用/什么时候不要用"、参数有类型和枚举 —— 这一步能立刻降低调用错误率
2. **Trace**：每次模型调用、工具调用都记录输入输出、耗时、token、错误 —— **没有 trace 就无法改进**
3. **终止与预算**：先保证"不会无限跑、不会把预算烧光"，再谈能力

**收尾**：「这三件事的共同点：它们都不需要改模型，但都能立刻影响成功率。」
:::

### 3.4 高频追问

:::qa 【挂点】你没用过 LangChain/AutoGen，怎么讲 Harness
把"我手写过等效逻辑"翻译成 harness 的语言：
| Harness 组件 | 你的对应实现 |
|---|---|
| 工具注册与 schema | 你的**策略层**（直接检索/查询改写/对抗检索/冲突消解）有明确的触发条件，等价于"工具 schema + 选择描述" |
| 循环控制器 | 你的"规划—执行—评估"循环 + 三类终止条件 |
| 状态与记忆 | **证据状态**（结构化的工作记忆） |
| 上下文装配 | 依赖图决定检索顺序 → 决定证据进入 context 的顺序 |
| 可观测 | ⚠️ 这是你**真正缺的**：你记录的是实验指标，不是逐步 trace |
| 沙箱/权限 | ⚠️ 完全没有 |
| 评测 | ✅ 你有 BingCheck / FacTool-KBQA 端到端评测 |

**话术**：「我的编排层是手写的，所以 harness 里 1/3/4/5 我踩过坑；2 和 6（沙箱、trace）我没有生产经验，这块我知道自己缺。」
:::

:::qa 为什么说"harness 比模型更重要"，举个例子
同一模型下：
- 工具描述写得含糊 → 模型选错工具
- 没有终止条件 → 转圈烧钱
- 没有 trace → 出了 badcase 无法定位是模型错还是工具错
- 没有沙箱 → 一次误操作把数据删了

**所以 harness 的价值不是"让模型更聪明"，而是"让模型的能力可靠地发挥出来"** —— 前者提升上限，后者决定下限，而面试里被问的多是下限。
:::

## 4. Prompt Caching / Prefix Caching（成本工程）★★★

:::card 一句话区分（最容易混淆的一题）
- **KV Cache**：**单次请求内部**，decode 阶段复用已算过的 K/V，避免重复计算历史 token
- **Prefix Caching / Prompt Caching**：**跨请求**，复用"**相同前缀**"已经算好的 KV，避免重复 prefill

**一句话**：「KV cache 解决"同一句话里不要重复算"，prefix cache 解决"不同请求间不要重复算开头"。」
:::

### 4.1 命中条件（工程上最关键的约束）

:::card 必须从第一个 token 开始逐 token 匹配
- **前缀完全一致**才算命中（不是"包含就行"）
- 所以：**任何在开头插入的变化内容，都会让整个缓存失效**
  - ❌ 在 system prompt 开头插入当前时间戳/请求 ID
  - ❌ 把检索证据放在 system prompt 之前
  - ✅ 稳定内容（system + 工具 schema + 长文档）在前，变化内容（用户问题、检索结果）在后
- 缓存有 **TTL**（各厂商不同，常见 5 分钟 ~ 1 小时级），过期要重算
- 计费上通常"**写缓存贵、读缓存便宜**"（如 1.25× 写入、0.1× 读取的量级），所以**前缀要够长、复用次数要够多**才划算
:::

### 4.2 Agent 场景为什么高价值

一个 Agent 会话的**天然稳定前缀**包括：
- system prompt（角色 + 规则）
- **工具 schema 列表**（通常几千 token，且一个会话内不变）
- 长文档 / few-shot 示例

这些东西在**每一轮**都要重发一遍。有 prefix cache 后，第 2 轮开始只需 prefill"新增部分"，成本与首 token 延迟都大降。

:::card 面试可以给一个估算
假设：工具 schema + system = **8k token**，会话跑 **20 轮**，每轮新增约 500 token。
- 无缓存：总 prefill ≈ `8k + (8k+0.5k) + …` 呈**二次增长**
- 有缓存：前缀只算一次，后续每轮只算新增 → 接近**线性**

**话术**：「Agent 场景下 prefix cache 的收益比普通对话更大，因为它的**固定前缀特别长**（工具定义），而且**轮次特别多**。」
:::

### 4.3 高频追问

:::qa 为什么只缓存 K 和 V，不缓存 Q？
- 推理时每个 token 的 **K/V 是历史信息**，会被所有后续 token 复用
- 而 **Q 只用于当前这个 token 自己去算注意力**，算完就没用了
- 所以缓存 K/V 有收益，缓存 Q 没有

**加一句**：「这也是为什么 KV cache 的显存公式是 `2 × 层数 × 头数 × 头维 × 序列长 × batch × 精度字节` —— 那个 **2 就是 K 和 V**。」
:::

:::qa prefix cache 和多轮对话的 KV cache 是一回事吗
不完全：
- 多轮对话里，**同一会话的 KV 可能被服务端保留**（vLLM 的 prefix caching 会命中）
- 但**跨会话/跨用户**只有前缀一致才命中；而且**不同用户的对话内容不同**，只有 system + tools 那段能共享

**所以工程上**：把"可跨用户共享的部分"（system、工具）放在最前，"用户私有部分"放后面 —— 命中率最高且不串数据。
:::

## 5. 向量检索工程（HNSW / LSH / PQ / ANN）★★☆

:::card 为什么需要 ANN
精确检索是 O(n·d)（n 个向量逐个算距离）。10 亿条 × 768 维，单次查询就要百亿级浮点运算 → 必须用**近似最近邻（ANN）**换速度。
:::

### 5.1 三类主流索引

| 索引 | 原理一句话 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **HNSW** | 分层可导航小世界图，上层稀疏"跳远"、下层稠密"精找" | 召回率最高、延迟低 | **内存占用大**（图结构全在内存） | 中小规模、高召回要求 |
| **IVF-PQ** | 先聚类分桶（IVF），桶内向量用**乘积量化**压缩（PQ） | 内存极省（可压到 1/8~1/32） | 有量化误差，召回略降 | 超大规模、内存受限 |
| **LSH** | 用哈希函数让"相近的向量更可能撞到同一个桶" | 理论简单、可并行 | 想高召回需要很多表 → 内存/时间反弹 | 特定场景（去重、近似匹配） |

### 5.2 HNSW 的关键参数（面试常问怎么调）

:::card 三个参数
- **`M`**：每个节点的最大连接数。越大 → 图越密 → 召回↑ 但内存↑、构建慢。常用 16–64
- **`efConstruction`**：建图时的候选队列大小。越大 → 图质量越好 → 构建越慢
- **`efSearch`**：**查询时**的候选队列大小。越大 → 召回↑ 延迟↑（这是**线上唯一可调**的旋钮）

**回答模板**：「离线用较大 `M` 和 `efConstruction` 把图建好，线上只调 `efSearch` 做**召回–延迟**折中；如果召回不够，先加 `efSearch`，再考虑加 `M` 重建。」
:::

### 5.3 相似度阈值怎么定（工程必答）

:::card 三种定法
1. **标注集法**：拿一批 (query, 相关/不相关) 数据，画 PR 曲线，选 F1 最优点 —— **最靠谱**
2. **分数间隙法**：看 top-1 与 top-2 的分数差，差太小说明"没有明显最优"，可判为**拒识**（转人工/转追问）
3. **分位数法**：用线上历史分布的 P95/P99 当阈值 —— **最省事但最粗糙**

**加分点**：「阈值不是常数，应该**按查询类型分桶**（单跳 vs 多跳、实体类 vs 数值类），否则一定是两头不讨好。」
:::

## 6. 工程落地题：多租户隔离 & 长文档 OOM ★★☆

### 6.1 多租户 RAG 的权限隔离（国企/金融科技岗高频）

:::card 关键原则：**在检索时过滤，不是在生成后过滤**
| 层 | 做法 | 说明 |
|---|---|---|
| **存储层** | 按 tenant 分 partition / namespace / 物理库 | 隔离最彻底，成本最高 |
| **索引层** | 每个 chunk 带 `tenant_id` + `acl` 元数据 | 检索时**带过滤条件**（metadata filter） |
| **检索层** | 向量检索 + 元数据过滤联合执行 | ⚠️ **不能先 top-k 再过滤** —— 会把别人的内容取进来又丢掉，既浪费又泄露 |
| **生成层** | 引用回填 + 越权检测 | 最后一道闸 |
| **审计层** | 记录谁在什么时候检索了什么 | 合规要求 |

**为什么"先取后过滤"是错的**：如果 top-10 里有 8 条属于别的租户，你过滤完只剩 2 条，**召回直接崩**；而且那 8 条的内容已经进了你的服务内存/日志 → 潜在泄露。
:::

### 6.2 长文档 OOM / 超长输入怎么处理

:::card 五种手段（按推荐度）
1. **分块 + 流式**：按页/章节切，逐块 embedding 和入库，**不在内存里拼全文**
2. **父子块（small-to-big）**：检索用小块（精度高），生成时取父块（上下文完整）
3. **Map-Reduce 摘要**：对每块生成局部摘要，再对摘要做汇总（适合"总结全文"类问题）
4. **两阶段**：先用粗粒度（章节标题 + 摘要）定位，再精读局部
5. **限制单次 context**：给每块设 token 上限，超长就再切（不要指望模型自动截断）
:::

## 7. Vibe Coding / AI 编程（你的优势区）★★☆

:::card 它是什么、面试怎么问
**是什么**：用自然语言驱动写代码（Claude Code / Cursor / Copilot Agent 一类），人负责"要什么 + 验收"，AI 负责"写"。

**面试最常见的三个问法（技术岗越来越爱问）**：
1. 你平时怎么用 AI 编程？工作流是什么？
2. AI 写的代码你怎么保证正确？
3. 你觉得 AI 编程的能力边界在哪？
:::

:::card 你该怎么答（结合你的 ICPC 底子）
**你的优势**：竞赛训练让你**能快速判断一段代码对不对、复杂度够不够** —— 这是用 AI 编程最稀缺的能力。

**工作流（可以照这个说）**：
1. 我定**接口与边界**（函数签名、输入输出、异常约定）—— 这部分不交给 AI
2. AI 写模板/样板/测试用例 —— 这些是"结构确定、细节繁琐"的部分
3. 我审**复杂度和边界**（能不能过、会不会退化）
4. **测试先于信任**：核心逻辑必须有测试，AI 写的也要跑通

**边界（诚实说）**：
- AI 擅长：样板代码、单测、重构改名、跨语言翻译、读陌生库的用法
- AI 不擅长：**判断架构取舍**、理解业务约束、处理"没写下来的需求"、对性能退化的敏感

**收尾一句话**：「我把 AI 当**打字很快但不懂上下文的实习生**：活可以给它，验收必须我来。」
:::

## 8. 分布式训练与显存计算（选做，大模型岗偶尔问）★★

### 8.1 四种并行（能说清区别即可）

| 并行 | 切什么 | 解决什么 | 代价 |
|---|---|---|---|
| **数据并行 DP** | 切 batch | 吞吐 | 每卡一份完整模型 |
| **张量并行 TP** | 切单层内的矩阵 | 单层太大 | 通信量大（层内 all-reduce） |
| **流水线并行 PP** | 切层（按层分段） | 模型太深 | 有气泡（bubble） |
| **序列并行 SP/CP** | 切序列长度 | 长上下文 | 注意力通信复杂 |
| 混合（3D） | 三者组合 | 千亿级训练 | 调参极难 |

**ZeRO** 是数据并行的显存优化：ZeRO-1 切优化器状态、ZeRO-2 再切梯度、ZeRO-3 再切参数。

### 8.2 显存估算（面试的真考题）

:::card 记住这个加法：参数 + 梯度 + 优化器状态 + 激活
**全参微调 8B 模型（bf16 混合精度 + Adam）**：
| 项 | 算法 | 大小 |
|---|---|---|
| 权重（bf16） | 8B × 2B | **16 GB** |
| 梯度（bf16） | 8B × 2B | **16 GB** |
| Adam 状态（fp32 的 m + v） | 8B × 4B × 2 | **64 GB** |
| 合计（不含激活） | | **≈ 96 GB** |
| 激活 | 与 batch × 序列长相关 | 数 GB ~ 数十 GB |

→ **8B 全参微调至少要 2×80G，或 4×48G + ZeRO**。

**LoRA 微调 8B**：权重 16 GB（可 4bit 量化到 ~5 GB）+ LoRA 参数与梯度（很小）+ 激活 → **单卡 24G–40G 可跑**，这就是 LoRA 的实际价值。

**一句话答法**：「全参微调的显存大头不是权重，是 **Adam 的两个 fp32 状态（每个参数 8 字节）**；LoRA 省的是"梯度和优化器状态"，不是权重本身。」
:::

## 9. GRPO / PPO / DPO 三联对比（补齐五星高频）★★★

:::card 一张表打穿（字节 Top20 五星第一题）
| 维度 | **PPO** | **DPO** | **GRPO** |
|---|---|---|---|
| **需要 reward model** | ✅ 需要 | ❌ 不需要（隐式奖励） | ✅ 需要（或**规则/可验证奖励**） |
| **需要 value model（critic）** | ✅ 需要（4 个模型） | ❌ 不需要（2 个模型） | ❌ **不需要**（用组内均值当 baseline） |
| **在线 / 离线** | 在线采样 | **离线**（偏好数据集） | 在线采样（同一 prompt 采一组） |
| **显存** | 最高（actor+critic+ref+rm） | 低（policy+ref） | 中（policy+ref+rm） |
| **稳定性** | 最难调（critic 与 actor 互相拖累） | 稳定 | 中等（组内方差敏感） |
| **数据需求** | prompt + 在线 reward | **(prompt, chosen, rejected) 偏好对** | prompt + 可自动判定的奖励 |
| **典型场景** | 通用人类偏好对齐 | 有偏好标注、算力有限 | **数学/代码等可验证任务** |
:::

:::card 为什么 GRPO 能去掉 value model（必答的核心）
PPO 用 value model 估计 baseline `V(s)`，作用是**降低方差**。
GRPO 的做法：**对同一个问题采一组（G 个）回答**，用组内的**均值/标准差**做归一化当 baseline：
```
A_i = (r_i − mean(r_1..r_G)) / std(r_1..r_G)
```
- 优点：**省掉一个与 policy 同规模的 value model**（显存大降），且不需要训练 critic
- 代价：**必须一次采一组**（rollout 成本上升）；如果组内奖励全相同（全对/全错），优势为 0 → **这一组白采**

**一句话**：「GRPO 用"**同一题多采几次、互相当参照**"替代了"训练一个价值网络来预测平均表现"。」
:::

:::card 三者怎么选（决策树）
1. **奖励能不能自动判定**（数学答案对不对、代码过不过测试）？
   - 能 → **GRPO / RLVR**（省显存、可用规则奖励、适合 Agent 的工具调用）
   - 不能 → 下一步
2. **有没有成对的偏好数据**（chosen/rejected）？
   - 有 → **DPO**（便宜、稳定）
   - 没有 → 先人工/模型标注偏好，或走 **PPO + reward model**
3. **算力是否充足 + 是否要求在线探索**？
   - 充足且需要 → PPO
   - 有限 → DPO
:::

## 10. 自测（8 题，答不出回去看对应节）

:::qa 有人问"长上下文能不能取代 RAG"，你的四维度答法
成本（每次塞全文太贵）、时效（静态快照 vs 实时知识库）、可溯源（RAG 天然带出处）、注意力稀释（窗口够大不等于有效利用高）。收尾：长上下文降低了 RAG 的精度要求，但提高了排序质量要求。
:::

:::qa Agent 循环的四类终止条件
① 任务完成（可验证：测试/断言/schema）② 预算耗尽（token/步数/时间/成本）③ 无进展（动作重复/状态不变/观察相似）④ 外部中断（取消/审批拒绝）。
:::

:::qa Harness 是什么？如果只能做三件事你做什么
Harness = 模型之外的一切（工具、沙箱、循环控制、状态、上下文装配、trace、权限、评测）。三件事：**工具 schema 规范化 → trace → 终止与预算**，共同点是"不改模型也能立刻影响成功率"。
:::

:::qa KV cache 和 prefix cache 的区别
KV cache 是**单次请求内** decode 阶段复用历史 K/V；prefix cache 是**跨请求**复用相同前缀的 KV。前者省"重复算历史"，后者省"重复算开头"。
:::

:::qa 为什么只缓存 K/V 不缓存 Q
K/V 是历史信息会被后续所有 token 复用；Q 只服务当前 token 自身。KV cache 显存公式里的那个 ×2 就是 K 和 V。
:::

:::qa HNSW 线上只调哪个参数？阈值怎么定
线上只调 **`efSearch`**（召回–延迟折中），`M` 与 `efConstruction` 是离线建图参数。阈值用**标注集画 PR 曲线**定，别用固定常数；进阶做法是按查询类型分桶。
:::

:::qa 8B 模型全参微调要多少显存？大头是什么
权重 16GB(bf16) + 梯度 16GB + Adam 两个 fp32 状态 64GB ≈ 96GB，再加激活 → 至少 2×80G。**大头是优化器状态，不是权重**。LoRA 省的是梯度和优化器状态。
:::

:::qa GRPO 为什么不需要 value model？代价是什么
用"同一问题采一组回答"的**组内均值/标准差**做归一化 baseline，替代 PPO 里训练出来的 critic。代价是必须一次采一组（rollout 成本上升），且组内奖励全同时优势为 0、样本浪费。
:::
